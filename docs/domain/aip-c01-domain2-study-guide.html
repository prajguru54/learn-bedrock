    Chapter 1 · Task 2.1

    Implement Agentic AI Solutions and Tool Integrations

    A chatbot answers. An agent decides what to do next, calls tools, reads the results, and keeps going until the job is done. That freedom is the reason agents are useful and the reason they fail in production: they loop, call tools with bad arguments, hold more permissions than they need, and take irreversible actions with no one watching. This chapter covers how to build the agent, how to give it tools, and how to keep it inside safe limits.

    Exam skills covered

    • 2.1.1 autonomous systems with memory and state (Strands Agents, AWS Agent Squad, MCP)
    • 2.1.2 structured reasoning with ReAct and chain-of-thought on Step Functions
    • 2.1.3 safeguards: stopping conditions, timeouts, IAM boundaries, circuit breakers
    • 2.1.4 model coordination: specialist models, ensembles, selection frameworks
    • 2.1.5 human-in-the-loop review, approval, and feedback
    • 2.1.6 reliable tool integrations: function definitions, error handling, parameter validation
    • 2.1.7 model extension with MCP servers on Lambda and Amazon ECS

    How this task is examined

    The exam does not ask you to write agent code. It describes a situation and asks which AWS building block fits. A typical scenario reads: "An agent must call an internal order API, must never issue a refund above a limit without a manager's approval, and must stop if it cannot finish within a set number of steps." You are expected to match each requirement to a mechanism: a tool definition, a human-approval state, and a stopping condition.

    Hold one mental model of an agent throughout the chapter. Every agent, whatever framework runs it, is the same loop:

    flowchart LR
  U["User request"] --> M["Model call (Converse)"]
  M -->|"stopReason: tool_use"| T["Run the requested tool"]
  T -->|"toolResult appended to messages"| M
  M -->|"stopReason: end_turn"| A["Final answer"]

    The model never runs a tool itself. It returns a request ("call get_order_status with order_id=A-1042"), your code or a framework runs it, and the result goes back to the model as the next message. Everything in this chapter is a decision about who runs that loop (a framework, a managed service, or a state machine), what tools it can reach, what it remembers between turns, and what stops it.

    Backend analogy

    If you have written a LangGraph or LangChain agent, you have written this loop. The difference on AWS is that each piece has a managed counterpart. Tool servers become MCP servers on Lambda or ECS. Checkpointing becomes AgentCore Memory or a session manager. Conditional edges and human-approval nodes become Step Functions states. Your framework knowledge carries over, and the exam asks which AWS service plays each role.

    Agents with memory and state (2.1.1)

    An agent without memory forgets the first question by the time it answers the third. Two kinds of memory matter, and the exam keeps them apart.

    • Short-term memory (conversation state). The message list for the current session: what the user said, which tools ran, what they returned. It lives in the context window, so it is limited by the model's context size.
    • Long-term memory (knowledge across sessions). Facts extracted from past conversations, such as "this customer prefers email" or "this account has a custom contract". It is stored outside the context window and retrieved when relevant.

    Building a single agent with Strands

    Strands Agents is an open-source Python and TypeScript SDK from AWS. It uses a model-driven loop: you give the model a prompt and tools, and the model decides which tool to call and when to stop. A complete agent is short.

    from strands import Agent, tool
from strands.models import BedrockModel


@tool
def get_order_status(order_id: str) -> dict:
    """Look up the current status of a customer order.

    Args:
        order_id: The order identifier, for example "A-1042".
    """
    return {"order_id": order_id, "status": "shipped", "eta_days": 2}


model = BedrockModel(
    model_id="<inference-profile-or-model-id>",
    temperature=0.2,
    region_name="<your-region>",
)

agent = Agent(
    model=model,
    system_prompt="You are a support agent. Use tools to look facts up. Do not guess.",
    tools=[get_order_status],
)

result = agent("Where is order A-1042?")
print(result)

    The @tool decorator reads the function's type hints and docstring and turns them into the tool schema the model sees. A clear docstring is therefore part of the interface: the model chooses a tool by reading its description. BedrockModel calls the Converse API for you and accepts the same model ID or inference profile ID you used in Domain 1. It also accepts a guardrail_id and guardrail_version so a guardrail screens every prompt and response.

    Short-term state: conversation and session managers

    Strands separates two concerns. A conversation manager controls what stays in the context window. The default, SlidingWindowConversationManager, keeps a fixed number of recent messages (window_size) and can truncate oversized tool results. A session manager persists the conversation and agent state so a later invocation, perhaps on a different Lambda container, can restore it. Strands ships file-based and Amazon S3 session managers.

    from strands import Agent
from strands.agent.conversation_manager import SlidingWindowConversationManager

agent = Agent(
    conversation_manager=SlidingWindowConversationManager(window_size=20),
    # session_manager=...  # S3-backed manager restores state across invocations
)

    Watch out

    On Lambda, memory held in a Python variable disappears when the execution environment is recycled, and two requests from the same user may land on different containers. If an agent must remember anything between requests, state belongs in a store (S3, DynamoDB, or AgentCore Memory), keyed by a session ID that the client sends on every call.

    Long-term state: Amazon Bedrock AgentCore Memory

    AgentCore Memory is the managed store for both kinds. You write events (usually conversation turns) to a memory resource using an actorId (the user) and a sessionId. Events are kept as short-term memory. If the memory resource has a memory strategy, such as semantic facts, user preferences, or summaries, the service extracts insights from the events into long-term memory records stored under a namespace like /support/customer-42/preferences. Later sessions retrieve those records instead of replaying every old conversation.

    flowchart LR
  A["Agent turn"] -->|"write event (memoryId, actorId, sessionId)"| E["Short-term memory: raw events"]
  E -->|"memory strategy extracts"| L["Long-term memory: facts, preferences, summaries"]
  N["New session"] -->|"retrieve by namespace and query"| L
  L --> N

    When an agent runs on AgentCore Runtime, session IDs flow from the invocation into Memory. Runtime also offers two lifecycle models. A per-request agent is stateless, so a new instance serves each call. A per-session agent keeps state across calls in a session, and by default an idle session ends after 15 minutes and any session ends after 8 hours (both adjustable, check the current docs for limits on your compute type). Sessions run in isolated microVMs, so one user's state cannot leak into another's.

    Watch out

    Memory holds conversations, and conversations hold personal data. Use the shortest event retention that meets the use case, encrypt memory with a customer managed KMS key for regulated workloads, and scope the IAM permissions to the specific memory resource. Do not let a long-term memory strategy store secrets the user pasted into chat. Domain 3 covers the controls in depth.

    Multi-agent systems

    One agent with fifty tools chooses badly and carries a huge context. Splitting work across several specialist agents keeps each prompt short and each tool list small. The patterns the exam names fall into four groups.

    Exam tip

    For "intent routing across several domains with shared conversation history", think Agent Squad or a supervisor agent. For "a fixed process with branches", think a graph or Step Functions. For "the agent must be able to pick the next specialist on its own", think swarm or agents-as-tools. A distractor will offer one giant agent with every tool attached. Splitting by domain is almost always the better answer when tool count or context size is the stated problem.

    Reliable tool integrations (2.1.6)

    A tool is a function plus a contract the model can read. Most agent failures in production are tool failures: the model passes a string where a number was expected, the downstream API times out, or an exception text becomes the model's only clue about what went wrong. The tool layer is where you make those failures survivable.

    The contract: a function definition

    In the Converse API a tool is described in toolConfig with a toolSpec: a name, a description, and a JSON Schema for the input. When the model wants the tool it returns a toolUse block and the response's stopReason is tool_use. You run the tool and send back a toolResult block in the next user message. Writing the loop yourself once makes every framework easier to read:

    import boto3

bedrock = boto3.client("bedrock-runtime")
MAX_TURNS = 5

TOOL_CONFIG = {"tools": [{"toolSpec": {
    "name": "get_order_status",
    "description": "Look up the current status of a customer order by its ID.",
    "inputSchema": {"json": {
        "type": "object",
        "properties": {"order_id": {"type": "string", "pattern": "^A-[0-9]{4}$"}},
        "required": ["order_id"],
    }},
}}]}


def run_agent(question: str, model_id: str) -> str:
    """Run a bounded tool-use loop and return the final text."""
    messages = [{"role": "user", "content": [{"text": question}]}]
    for _ in range(MAX_TURNS):
        resp = bedrock.converse(
            modelId=model_id,
            messages=messages,
            toolConfig=TOOL_CONFIG,
            inferenceConfig={"maxTokens": 1024},
        )
        message = resp["output"]["message"]
        messages.append(message)
        if resp["stopReason"] != "tool_use":
            return "".join(b.get("text", "") for b in message["content"])
        results = []
        for block in message["content"]:
            if "toolUse" in block:
                use = block["toolUse"]
                results.append({"toolResult": {
                    "toolUseId": use["toolUseId"],
                    "content": [{"json": call_tool(use["name"], use["input"])}],
                }})
        messages.append({"role": "user", "content": results})
    raise RuntimeError("Agent stopped: turn limit reached")

    Notice the for loop has a ceiling. That one line is the simplest stopping condition, and it appears again in the safeguards section.

    Validate parameters at the tool, not in the prompt

    The model produces arguments. Treat them like input from an untrusted client, because a prompt injection in a retrieved document can steer them. Validate every argument inside the tool, and return a structured error that tells the model how to fix the call. A Lambda tool is a good place to do this because the validation runs outside the model's control.

    import json
from pydantic import BaseModel, Field, ValidationError


class RefundRequest(BaseModel):
    order_id: str = Field(pattern=r"^A-[0-9]{4}$")
    amount_cents: int = Field(gt=0, le=50_000)
    reason: str = Field(min_length=5, max_length=200)


def lambda_handler(event, context):
    """Validate tool arguments, call the backend, and return an error the model can act on."""
    try:
        req = RefundRequest(**event)
    except ValidationError as exc:
        return {"ok": False, "error_type": "invalid_arguments",
                "details": json.loads(exc.json()),
                "hint": "Fix the listed fields and call the tool again."}
    try:
        return {"ok": True, "refund_id": create_refund(req)}   # your backend call
    except TimeoutError:
        return {"ok": False, "error_type": "backend_timeout", "retryable": True}

    Three habits make tools reliable:

    • Return errors as data. A tool result with "ok": false and a reason lets the model correct itself. An unhandled exception either aborts the loop or gives the model a stack trace to guess from. In the Converse API you can also mark a toolResult with "status": "error".
    • Mark errors as retryable or not. A timeout is worth one retry. A permission error is not. Put that distinction in the result so the model does not hammer a tool that cannot succeed.
    • Make write tools idempotent. The model may call "create refund" twice after a timeout. Accept an idempotency key (for example a hash of order ID and amount) so a repeat call returns the first result instead of paying twice.

    Backend analogy

    A tool is an API endpoint whose client is a language model. You would never trust a public client to send valid input, so the same rules apply: schema validation, clear error responses, idempotency keys, and timeouts. FastAPI plus Pydantic is the right mental picture, and the Lambda above is that endpoint.

    Exam tip

    "The agent sometimes calls the API with malformed arguments" is answered by schema validation and structured error results in the tool (typically a Lambda function), not by a longer prompt or a larger model. "Standardized function definitions" in the skill list means the same JSON Schema contract everywhere, whether the tool is a Strands @tool, a Converse toolSpec, a Bedrock Agents action group schema, or an MCP tool.

    Model extension with MCP servers (2.1.7)

    The Model Context Protocol (MCP) is an open standard for how an agent discovers and calls tools. Without it, every framework needs its own adapter for every tool. With it, you write a tool server once, and any MCP client (a Strands agent, an IDE assistant, an AgentCore Gateway) can list its tools and call them. You already know FastMCP from your own work. This section is about where to host the server on AWS.

    An MCP server exposes tools over a transport. For remote servers the transport is streamable HTTP (a single /mcp endpoint). A server is either stateless (each request stands alone) or stateful (it keeps a session between requests). That distinction decides the hosting choice, and the exam tests it directly.

    HostFitsWhy
    AWS Lambda (stateless MCP server, or a Lambda function behind an AgentCore Gateway)Lightweight tools: look up a record, call a REST API, run a short calculation.No servers to run, scales to zero, pay per call, one function per tool or per small tool set. The 15-minute function limit and lost in-memory state between calls rule out long or stateful tools.
    Amazon ECS (on Fargate)Complex tools: long-running jobs, large dependencies, open connections, sessions, a local database or file system.A container you control keeps state and runs as long as needed. You own scaling and the load balancer.
    AgentCore Runtime (MCP protocol)MCP servers that need managed identity, session isolation, and scaling without running ECS yourself.Runtime serves the MCP endpoint (/mcp, port 8000) from an ARM64 container, with stateless HTTP mode available.
    AgentCore GatewayExposing many existing tools through one MCP endpoint.Turns Lambda functions, OpenAPI specs, Smithy models, and existing MCP servers into one consolidated tool list, with auth and semantic tool search.

    Lambda as a tool server

    Two common Lambda patterns exist. In the first, the Lambda function is a target of an AgentCore Gateway. You register the function with a tool schema, and the Gateway presents it as an MCP tool. The function receives the tool's arguments as its event, and the gateway passes the tool name in the Lambda context (the name is prefixed with the target name, so strip the prefix when you route). The Gateway invokes the function through its service role, so you grant that role lambda:InvokeFunction on this one function ARN and nothing broader.

    import boto3

gw = boto3.client("bedrock-agentcore-control")

gw.create_gateway_target(
    gatewayIdentifier="<gateway-id>",
    name="orders",
    targetConfiguration={"mcp": {"lambda": {
        "lambdaArn": "<function-arn>",
        "toolSchema": {"inlinePayload": [{
            "name": "get_order_status",
            "description": "Look up the status of an order by ID.",
            "inputSchema": {"type": "object",
                            "properties": {"order_id": {"type": "string"}},
                            "required": ["order_id"]},
        }]},
    }}},
    credentialProviderConfigurations=[{"credentialProviderType": "GATEWAY_IAM_ROLE"}],
)

    In the second pattern you host the MCP server itself on Lambda, for example by adapting a stdio server with the open-source run-model-context-protocol-servers-with-aws-lambda library. Each invocation starts fresh, so only stateless servers fit. Servers that keep data on disk or in memory (a SQLite server, a file system server, a git server) lose their state between calls and belong on ECS or AgentCore Runtime.

    ECS as a tool server

    Package the MCP server as a container, run it as an ECS service behind an Application Load Balancer, and give the task role only the permissions its tools need. Pick this when the tool has heavy dependencies, runs for minutes, holds a connection pool, or needs a session. In FastMCP terms the code is the same as on your laptop. What changes is the deployment: health checks, auto scaling on request count or CPU, and a stable HTTPS endpoint.

    Connecting an agent as an MCP client

    from strands import Agent
from strands.tools.mcp import MCPClient

mcp = MCPClient(
    url="https://<gateway-or-server>/mcp",
    headers={"Authorization": f"Bearer {access_token}"},  # token from your identity provider
)

with mcp:
    tools = mcp.list_tools_sync()
    agent = Agent(tools=tools)
    agent("What is the status of order A-1042?")

    Consistent access is the point. If every agent in the company uses an MCP client library to reach tools, then a new tool is a server registration, not a code change in every agent. The Strands MCPClient supports stdio, streamable HTTP, and SSE transports, and can send authentication headers or an OAuth credential. Check the current Strands documentation for the exact client constructor, because it has changed between releases.

    Watch out

    Tool descriptions are part of the prompt. An MCP server you did not write can describe a tool in a way that manipulates the agent (a form of prompt injection called tool poisoning). Only connect agents to servers you trust, give each agent the smallest tool set it needs, and put deterministic controls (IAM, AgentCore Policy) between the agent and anything dangerous.

    Note

    When an agent has hundreds of tools, listing them all in every prompt wastes tokens and confuses the model. AgentCore Gateway offers semantic tool search: the agent asks for tools by intent and receives only the relevant few. Strands describes the same idea with a retrieval tool over tool descriptions.

    Structured reasoning with ReAct on Step Functions (2.1.2)

    Models solve hard problems better when they work in steps instead of answering at once. Two techniques carry most of the exam's questions.

    • Chain of thought (CoT). The model writes out intermediate reasoning before the final answer. You trigger it with an instruction ("think through the steps, then answer"), by splitting a task into several prompts, or by using a model that supports built-in extended reasoning.
    • ReAct (Reason plus Act). The model alternates between a thought, an action (a tool call), and an observation (the tool result), and repeats until it can answer. The tool-use loop from the start of this chapter is a ReAct loop.

    You can leave the loop inside a framework, or you can make it explicit as a Step Functions state machine. The explicit version trades some model freedom for properties that matter in production: every step is logged in the execution history, each step has its own retry and timeout, the loop has a visible ceiling, and a human-approval step can sit anywhere in it.

    How the state machine works

    flowchart TD
  S["Start: question, messages, turn = 0"] --> C["CallModel (Lambda calls Converse once)"]
  C --> D{"stopReason = tool_use?"}
  D -->|"no"| F["Done: return final answer"]
  D -->|"yes"| L{"turn at or above maxTurns?"}
  L -->|"yes"| X["StoppedByLimit: structured result"]
  L -->|"no"| R["RunTools (Lambda runs each requested tool)"]
  R --> I["IncrementTurn"]
  I --> C
  C -.->|"error after retries"| E["StoppedByError"]
    1. The execution starts with the user's question, an empty message list, turn = 0, and a maxTurns value.
    2. CallModel is a Lambda task that sends the messages and the tool list to the model with one Converse call and returns the updated messages and the stopReason.
    3. A Choice state reads the stop reason. If the model asked for a tool and the turn count has reached the ceiling, the execution ends with a structured "stopped" result. If the model asked for a tool and there is room, RunTools runs it. Otherwise the model has answered and the execution ends.
    4. RunTools runs each requested tool, appends the results as a toolResult message, and the counter goes up by one. Control returns to CallModel.
    5. The caller sees either the final answer or {"status": "stopped", "reason": "iteration_limit"}, never an unbounded run.

    Watch out

    A Step Functions state carries a payload of at most 256 KB. A message list that includes large tool results will hit that limit after a few turns. Store big results in S3 or DynamoDB and put only a reference in the messages, or have the tool return a short summary. Also use a Standard workflow for this pattern. Express workflows run for at most five minutes and do not support the .waitForTaskToken pattern you need for human approval.

    Chain of thought as a workflow

    The same service implements CoT when you break a task into prompts and make each step visible: one state decomposes the problem, a Map state solves each sub-problem (possibly in parallel), and a final state combines and verifies the answers. Each state can use a different model, which is covered in the coordination section. This is also called prompt chaining, and Step Functions has an optimized integration that invokes Bedrock models directly from a state, without a Lambda function in between.

    Safeguarded AI workflows (2.1.3)

    The failure story of this section is easy to picture. A support agent calls the customer lookup tool, which is timing out. The model reads the error, decides to try again, and keeps trying. Each loop sends the growing message list to the model. After twenty minutes it has used a day's token budget and produced nothing. Safeguards exist so that this ends in a few seconds with a clear message.

    Safeguards fall into four families. A good design uses all four, because each catches what the others miss.

    SafeguardFailure it preventsAWS mechanism
    Stopping conditionsEndless loops and runaway token spendTurn ceiling in the loop (Step Functions Choice or a for bound), token budget per session, a "stop" tool the model can call, swarm limits (max_handoffs, max_iterations)
    TimeoutsOne slow call stalling the whole runLambda function timeout, Step Functions TimeoutSeconds and HeartbeatSeconds on tasks, client-side read timeout on the Bedrock call, execution and node timeouts in Strands multi-agent classes
    Resource boundariesAn agent reaching data or actions it was never meant to touchIAM policies on each tool's role, permissions boundaries, resource-scoped actions, AgentCore Policy (Cedar) at the Gateway, VPC placement of tool servers

    Stopping conditions

    Put a hard ceiling on iterations. A commonly cited production range is three to five loop iterations against a total token budget, after which the agent summarizes where it got and either escalates or asks the user what to do. Pick your own number from your task, but always have one. Then add a second kind of ceiling that counts tokens or cost, because three turns with huge tool results can cost more than ten short ones. The Step Functions version of the ceiling is the Choice state in the previous section. In a framework, use a hook that counts tool calls and stops the run, or the framework's own limits where it has them.

    Timeouts at every layer

    Set a timeout at each layer, and make each inner timeout shorter than the outer one. A tool Lambda that has a 10-second timeout, inside a Step Functions task with a 30-second timeout, inside an execution that is bounded at five minutes, fails fast and tells you which layer was slow. Without the inner limits, the outermost timeout is the only signal and it tells you nothing about the cause.

    Resource boundaries with IAM

    An agent should hold the permissions of its tools, not the permissions of its developer. Give each tool its own role, scoped to the exact resources it needs. A read-only lookup tool gets read-only access to one table, so even a successful prompt injection cannot make the agent delete data.

    "Ensure the agent can never delete records, even if a user tricks it" is answered with IAM (or Gateway policy) that does not grant delete, not with an instruction in the prompt and not with a Guardrails topic filter. Guardrails shape what the model says. IAM limits what the system can do. The exam places the requirement at the layer that can actually enforce it.

    A circuit breaker for a tool

    When a tool fails repeatedly, calling it again helps no one. A circuit breaker counts consecutive failures per tool. After a threshold it opens, and for a cooldown period calls fail instantly without touching the dependency. After the cooldown one trial call goes through (half-open). If it succeeds the breaker closes, otherwise it opens again.

    import time
import boto3

table = boto3.resource("dynamodb").Table("ToolBreaker")
THRESHOLD, COOLDOWN_S = 3, 60


def is_open(tool: str) -> bool:
    """Return True while the breaker for this tool is open and cooling down."""
    item = table.get_item(Key={"tool": tool}).get("Item", {})
    return item.get("failures", 0) >= THRESHOLD and time.time() - float(item.get("opened_at", 0)) < COOLDOWN_S


def record(tool: str, ok: bool) -> None:
    """Reset the counter on success. Count a failure and stamp the time on failure."""
    if ok:
        table.put_item(Item={"tool": tool, "failures": 0, "opened_at": 0})
        return
    table.update_item(
        Key={"tool": tool},
        UpdateExpression="ADD failures :one SET opened_at = :now",
        ExpressionAttributeValues={":one": 1, ":now": int(time.time())},
    )


def call_tool_safely(tool: str, fn, **kwargs):
    """Fail fast with a result the model can read when the breaker is open."""
    if is_open(tool):
        return {"ok": False, "error_type": "tool_unavailable", "retryable": False,
                "hint": "This tool is temporarily down. Tell the user or use another approach."}
    try:
        out = fn(**kwargs)
        record(tool, True)
        return out
    except Exception:
        record(tool, False)
        return {"ok": False, "error_type": "tool_error", "retryable": False}

    The fast-fail result matters as much as the counter. The model reads tool_unavailable and can choose to apologize, use another tool, or escalate, instead of looping. The breaker state lives in DynamoDB because Lambda containers do not share memory. Domain 1 showed the same pattern for model calls.

    Watch out

    Circuit breakers and retries pull in opposite directions. A retry gives a flaky call another chance, a breaker stops calls to a broken one. Put retries with backoff inside a single call, and count a call as one failure only after its retries are used up. Otherwise three quick retries open the breaker on a single bad moment.

    Model coordination (2.1.4)

    No single model is best at everything. A small, fast model can classify intent in a fraction of a second at a fraction of the price. A large model is better at multi-step reasoning. A multimodal model reads the screenshot. An embedding model handles retrieval. Coordination means giving each part of the workflow to the model that fits it.

    Ensembles

    An ensemble asks several models the same question and combines the answers. It costs more tokens and adds latency, so use it where a wrong answer is expensive: a fraud flag, a medical code, a contract clause. In Step Functions, a Parallel or Map state fans out one call per model and an aggregation state combines the results. The aggregation logic is yours, and the choice depends on the output type.

    Free textA judge model picks or merges the best answer against a rubricThe judge is a model too, so test it. Prefer a different model family from the candidates.
     
    from collections import Counter
from concurrent.futures import ThreadPoolExecutor


def classify_with(model_id: str, text: str) -> str:
    """Ask one model for a single-word label."""
    resp = bedrock.converse(
        modelId=model_id,
        messages=[{"role": "user", "content": [{"text": f"Label as FRAUD or OK. One word.\n\n{text}"}]}],
        inferenceConfig={"maxTokens": 5, "temperature": 0},
    )
    return resp["output"]["message"]["content"][0]["text"].strip().upper()


def ensemble_label(text: str, model_ids: list[str]) -> dict:
    """Majority vote across models. Escalate when there is no majority."""
    with ThreadPoolExecutor(max_workers=len(model_ids)) as pool:
        votes = list(pool.map(lambda m: classify_with(m, text), model_ids))
    label, count = Counter(votes).most_common(1)[0]
    return {"label": label if count > len(votes) / 2 else "REVIEW", "votes": votes}

    Watch out

    An ensemble multiplies cost by the number of models and latency by the slowest one. Do not make every request an ensemble. Use the cheap model first and call the ensemble only when the first answer has low confidence or the stakes are high. Chapter 2 calls this model cascading.

    Exam tip

    "Optimize performance across multiple capabilities" usually means a different model per task: a small model for classification or extraction, a large one for reasoning, a multimodal one for images. The wrong answer is the single largest model for everything, because it ignores cost and latency.

    Human-in-the-loop collaboration (2.1.5)

    Some actions should never run unreviewed: a refund above a limit, an email to a customer's executive, a production change. Some outputs need a person's judgment before they go out. Human-in-the-loop (HITL) design decides where people join the workflow, what they see, and what happens if nobody answers.

    The approval gate with a task token

    Step Functions can pause a workflow until an outside system reports back. You use the .waitForTaskToken integration pattern. Step Functions generates a unique task token when the state starts, hands it to your integration (here an SQS message), and waits. The execution consumes no compute while paused. A standard workflow can wait up to the one-year service limit, so you set your own shorter TimeoutSeconds.

    1. The agent decides to issue a refund above the threshold. The state machine reaches AskHuman.
    2. Step Functions sends an SQS message that contains the task token and the refund details (order, amount, the agent's reason). The execution pauses.
    3. A reviewer opens an internal page that reads the queue. The page shows the details and an Approve and a Reject button.
    4. A button calls an API Gateway endpoint, which invokes a Lambda function. The function calls SendTaskSuccess (or SendTaskFailure) with the token and the decision.
    5. The execution resumes and a Choice state follows the decision. If no one answers before the timeout, a Catch sends the run to a safe default, normally "do not do it" and notify a person.

    Deciding what needs a human

    The AWS Well-Architected guidance for agents recommends a deterministic risk classifier and not an LLM: a rule such as "refund over a limit, or any delete, needs approval". Map operation types to approval tiers (run freely, one reviewer, two reviewers), and log every approval with the reviewer, time, decision, and context. If you let the model decide what needs approval, a prompt injection can talk it out of asking.

    In Strands, the same idea appears as a hook that runs before each tool call and pauses the agent for a human response, then resumes it. The interface for this has been changing between SDK releases, so check the current Strands documentation before you copy code. In Bedrock Agents (classic), you mark an action group function as requiring user confirmation, or use return of control so the application runs the action itself after the user agrees.

    Feedback that improves the system

    An API Gateway route such as POST /feedback, validated against a schema, writes {requestId, rating, correction} to DynamoDB. The request ID joins the feedback to the stored prompt, response, and trace. Corrections become test cases for prompt regression checks (Domain 1) and evaluation sets (Domain 5). Without the join key, feedback is a number with no context.

    Exam tip

    "Pause the workflow until a manager approves, then continue" is Step Functions waitForTaskToken. "Send the question back to the user's application so it can perform the action" is return of control. "Ask the user to confirm before this function runs" is user confirmation. A distractor proposes polling a DynamoDB table in a Lambda loop, which wastes compute and hits the 15-minute function limit.

    Knowledge check

    1. An agent calls a refund tool. Security requires that the agent can never issue a refund of more than a fixed amount, even if a customer's message tries to override its instructions. Where should this limit be enforced?

      Answer

      In the tool and in a deterministic control outside the model: validation inside the tool (reject amounts above the limit), plus an AgentCore Policy rule at the Gateway or an IAM boundary where that fits. A system prompt instruction or a Guardrails filter shapes what the model says, it does not enforce what the system does, and a prompt injection can defeat it.

    2. A team runs an agent loop inside one Lambda function. It sometimes runs for the full 15 minutes, produces no answer, and the team cannot tell which step was slow. What should they change?

      Answer

      Move the loop to a Step Functions Standard workflow: one task for the model call, one for tool execution, a Choice state with a turn ceiling, a timeout and retry policy on each task, and an execution history that shows each step. The single-function loop has no per-step visibility, no per-step retry, and a hard 15-minute limit.

    3. A workflow must pause until a manager approves a purchase order, which may take two days, then continue. Which mechanism fits, and what must the team do for the case where nobody responds?

      Answer

      A Step Functions Standard workflow with the .waitForTaskToken callback pattern. The state sends the task token to an approval channel and pauses without using compute. The team sets TimeoutSeconds on the task and a Catch for States.Timeout that routes to a safe default such as rejecting the order and notifying a person. Express workflows cannot be used because they do not support this pattern and run at most five minutes.

    4. You must host a tool server for an agent. Tool A looks up one record in DynamoDB. Tool B keeps a local database file and holds a session across calls. Where does each belong?

      Answer

      Tool A fits Lambda (stateless, light, scales to zero), either as an AgentCore Gateway Lambda target or a stateless MCP server. Tool B needs state that survives between calls, so it belongs on Amazon ECS (or AgentCore Runtime), because a Lambda execution environment loses in-memory and local state and cannot hold a long-lived session.

    5. A support system handles billing, technical, and sales questions. Each domain has its own tools and instructions. One agent with all tools picks the wrong tool often and its prompt is very large. Which design fixes this?

      Answer

      Split by domain and route. Use specialist agents with small tool sets, with an orchestrator or a classifier in front: agents-as-tools or a swarm in Strands, a supervisor with collaborators in Bedrock Agents, or Agent Squad's classifier for intent routing with shared conversation context. Each specialist keeps a short prompt and its own context window.

    Chapter recap

    • Every agent is a loop: model call, tool request (stopReason: tool_use), tool run, result appended, repeat. The design choice is who runs the loop and what bounds it.
    • Bedrock Agents (classic) is in maintenance mode. New agents use AgentCore (Harness for a managed loop, Runtime for your own) or Strands, with Step Functions when you need an explicit, auditable loop.
    • Short-term state is the message list (conversation manager, session manager). Long-term state is extracted facts and preferences (AgentCore Memory). Lambda memory is not state.
    • A tool is a validated, idempotent endpoint whose client is a model. Validate arguments in the tool, return errors as data, and mark them retryable or not.
    • MCP standardizes tool access. Stateless and light means Lambda. Stateful, heavy, or long-running means ECS or AgentCore Runtime. Gateway unifies many tools behind one endpoint.
    • Safeguards come in four layers: stopping conditions, timeouts, resource boundaries (IAM and Gateway policy), and circuit breakers. Prompts do not enforce any of them.
    • Give each task to the model that fits it, use ensembles sparingly, and write the selection rules as configuration.
    • Human approval is a Step Functions callback with a task token and a safe default on timeout. A deterministic rule, not the model, decides what needs approval.

    Problem statement

    The scenario

    A retailer's support team receives about 400 tickets a day. Most ask the same things: where is my order, can I get a refund, why was I charged twice. Agents spend minutes per ticket copying data between a customer system and an order system. Leadership wants an AI assistant that prepares the answer, with three conditions that come from a past incident in which a different bot refunded an order twice:

    • The assistant can read customer and order data. It must have no permission to change anything.
    • Any refund over a set amount needs a named human to approve it. If nobody responds within a day, the refund is declined and the ticket goes to a person.
    • The assistant must stop after a small number of steps. A stuck run must end with a clear message, not a surprise bill.

    Build a triage service that takes a ticket, produces a draft reply and, when needed, a proposed refund, and enforces the three conditions in infrastructure rather than in the prompt.

    The exam describes this scenario in many forms: "the agent must not be able to modify records", "high-value actions require approval", "the workflow must end if the agent cannot finish in a fixed number of steps". Each phrase points to one box in the architecture below.

    Build path

    Suggested folder name: support-triage-agent, laid out as in the repository's project template (src/, tests/, infra/, Dockerfile if you package the agent as a container). Each step leaves something that runs.

    1. Design note and test ticketsOne page: the refund limit, the turn ceiling, the approval timeout, and what "stopped" means for the support team.     2. Tools firstWrite get_customer and get_orders as plain Python functions with Pydantic validation and structured error results. Unit-test them with bad arguments before any model is involved. Seed DynamoDB with sample data.
    3. Local agentBuild the Strands agent with the two tools, running on your machine. Add a turn counter that raises after the ceiling. Run all 20 test tickets and record how often the draft is correct, how many turns each took, and whether any run hit the ceiling.
    4. Move tools behind MCPDeploy the two tools as Lambda functions, create an AgentCore Gateway with a JWT authorizer, and add the Lambda targets. Replace the local tools with an MCPClient pointed at the gateway. Re-run the test tickets and confirm the results match.
    5. Lock down the rolesGive each tool Lambda a role limited to GetItem and Query on its table. Give the agent Lambda no DynamoDB write access. Prove it: try to make the agent change an order through a crafted ticket and confirm AWS denies it, not the prompt.
    6. State machine and approval gateWrap the agent in a Step Functions workflow: Triage, a Choice on the refund limit, AskHuman with a task token, ApplyDecision, and Refund. Build the approval endpoint with API Gateway and Lambda, with an authorizer and an audit record (who, when, decision). Set the real timeout and test the timeout path with a short one.
    7. Failure handlingAdd retries with backoff on the model call, a circuit breaker on each tool backed by DynamoDB, and a Catch that routes any error to "route to a person". Break a tool on purpose and confirm the agent tells the support team the lookup is unavailable and does not loop.
    8. Feedback and reviewAdd POST /feedback with schema validation that stores the rating and correction with the request ID. Write the infrastructure as code, deploy, and run the test tickets end to end. Review the execution history for one approved, one rejected, and one stopped run.

    Definition of done

    • The agent's role cannot write to any table. A test ticket that tries to make it change data fails with an AWS access error.
    • A refund above the limit never reaches the refund Lambda without an approval record that names the reviewer.
    • An unanswered approval ends in a decline and a route to a person after the timeout, and the ticket shows why.
    • With the ceiling set to a low number on a hard ticket, the run ends with a "stopped: iteration_limit" result and no further model calls.
    • With a tool forced to fail, the breaker opens after the configured number of failures and the agent reports the tool as unavailable.
    • You can open one execution in the Step Functions console and explain every step that ran and why.

    Implement Model Deployment Strategies

    With Bedrock on-demand, "deploying a model" means writing an API call. That is the right answer for most workloads, and the exam knows it. This chapter covers the cases where it is not: traffic that needs guaranteed capacity, models Bedrock does not host, and bills that shrink if you send easy questions to a cheaper model. You will learn to choose the hosting option from a scenario, to explain why LLMs are harder to host than a classic ML model, and to cut cost with model cascading.

    How this task is examined

    Scenario questions in this task give you three or four facts and ask for a hosting choice. The facts that matter are almost always the same: how steady the traffic is, whether the model is a Bedrock model or your own, how tolerant users are of latency, and what the team wants to operate.     Why LLMs are different to host (2.2.2)

    If you have deployed a scikit-learn or XGBoost model, you know the shape: a model file of a few megabytes, a CPU, one request in and one answer out in milliseconds. An LLM breaks every one of those assumptions. The exam asks you to name the differences, so learn them as a list.

    PropertyClassic ML modelLLMDeployment consequence
    Model sizeKilobytes to a few hundred megabytesGigabytes to hundreds of gigabytesThe weights may not fit on one GPU, so the model is split across GPUs. Loading takes minutes, not seconds.
    ComputeCPU is often enoughGPU or AI acceleratorInstance choice drives cost. Serverless options without GPU do not apply.
    Per-request workOne forward passOne pass per generated token, in a loopLatency grows with output length. You measure time to first token and tokens per second, not only total time.
    Memory during a requestFixedGrows with context length and number of concurrent requests (the KV cache)An instance that fits the weights can still run out of memory under load.
    Response deliveryOne response bodyOften streamed token by tokenEvery hop (API Gateway, Lambda, client) must support streaming, or the user waits for the whole answer.
    ScalingNew copy starts in secondsNew copy must load the weights onto GPUs firstAutoscaling reacts slowly to a spike, so you either keep warm capacity or speed up loading.

    A worked memory estimate

    The weights need roughly parameter count × bytes per parameter. A model stored in 16-bit precision uses 2 bytes per parameter.

    7 billion parameters  x 2 bytes (16-bit)  = about 14 GB
70 billion parameters x 2 bytes (16-bit)  = about 140 GB
70 billion parameters x 1 byte  (8-bit)   = about 70 GB
70 billion parameters x 0.5 byte (4-bit)  = about 35 GB

    Two things follow. First, the 70-billion-parameter model in 16-bit precision cannot sit on a single GPU, so it needs tensor parallelism, which splits each layer across several GPUs on one instance. Second, lowering the precision (quantization) shrinks the weights and lets you use fewer or smaller GPUs, at some cost in output quality. The numbers above cover weights only. The KV cache needs more memory on top, and it grows with every concurrent conversation, so leave headroom.

    Backend analogy

    Think of the weights as a database that must be fully loaded into RAM before the first query, and the KV cache as per-connection buffer memory. A database that fits in RAM can still crash when connections multiply. The same is true of an LLM host.

    Lambda as the on-demand front door (2.2.1)

    The exam's phrase "Lambda functions for on-demand invocation" confuses people who read it as "host the model in Lambda". Lambda does not host the model. It runs your code, which calls Bedrock. The model stays behind the Bedrock API, and you pay per token plus a little Lambda compute.

    import json
import os

import boto3
from botocore.config import Config

# Long generations can exceed the default 60 second read timeout, so raise it explicitly.
bedrock = boto3.client(
    "bedrock-runtime",
    config=Config(
        read_timeout=120,
        connect_timeout=10,
        retries={"max_attempts": 3, "mode": "standard"},
    ),
)
MODEL_ID = os.environ["MODEL_ID"]


def lambda_handler(event: dict, context) -> dict:
    body = json.loads(event["body"])
    resp = bedrock.converse(
        modelId=MODEL_ID,
        messages=[{"role": "user", "content": [{"text": body["prompt"]}]}],
        inferenceConfig={"maxTokens": 500},
    )
    text = resp["output"]["message"]["content"][0]["text"]
    return {"statusCode": 200, "body": json.dumps({"answer": text})}

    Put the model ID in an environment variable (or AppConfig, as in Domain 1's prompt management) so a model change is a configuration change, not a code deployment.

    Three limits decide whether Lambda alone is enough. Lambda runs for at most 15 minutes. When API Gateway sits in front of it with a REST API, the integration timeout defaults to 29 seconds, although Regional and private REST APIs can request an increase through Service Quotas (a higher timeout may lower your account-level throttle quota, so read the current notes). And the Lambda response is normally returned whole, so token streaming needs response streaming, which Chapter 4 covers.

    Exam tip

    When a scenario says users see timeouts on long generations behind API Gateway, the options usually include "increase the Lambda timeout" (necessary but not enough, because the 29 second gateway limit still applies), "stream the response", and "switch to an asynchronous pattern with SQS or Step Functions". Look at which limit the scenario actually hits.

    Bedrock Provisioned Throughput (2.2.1)

    On-demand shares capacity with other customers and is limited by your account quotas (see tokens and quotas). If your product must serve a steady, high volume without throttling, you can buy dedicated capacity instead. That is Provisioned Throughput.

    How it works

    1. You choose a model and a number of model units (MUs). One MU gives a fixed number of input tokens and output tokens per minute for that model. The capacity of an MU differs per model, and the documentation points you to your AWS account team for the figure.
    2. You choose a commitment: none (delete any time), one month, or six months. A longer commitment lowers the hourly price. You cannot delete a committed purchase before its term ends.
    3. Bedrock creates a provisioned model with its own ARN. You pass that ARN as the modelId in Converse or InvokeModel.
    4. You are billed every hour until you delete it, whether or not you send a request.
    import boto3

bedrock = boto3.client("bedrock")  # control plane, not bedrock-runtime

pt = bedrock.create_provisioned_model_throughput(
    provisionedModelName="support-bot-prod",
    modelId="<model ID that supports Provisioned Throughput>",
    modelUnits=1,
    # commitmentDuration="OneMonth",   # omit for no commitment
)
print(pt["provisionedModelArn"])

runtime = boto3.client("bedrock-runtime")
resp = runtime.converse(
    modelId=pt["provisionedModelArn"],
    messages=[{"role": "user", "content": [{"text": "Hello"}]}],
)

    Details to check before you buy

    Purchasing through the API requires the model ID variant that matches the context size, and only some base models support a no-commitment purchase. Both lists change. Read Supported Region and models for Provisioned Throughput in the current documentation, and do not copy IDs from a blog post.

    Two rules recur in exam scenarios:

    • A model you customized with Bedrock (fine-tuning or continued pre-training) can only be invoked through Provisioned Throughput. A model you imported with Custom Model Import is the exception and supports on-demand invocation.
    • Provisioned Throughput means "reserved capacity". It does not select a faster model. What changes is that your requests no longer compete with other customers' requests for capacity.

    Exam tip

    Look for the words "consistent", "predictable", and "sustained" for Provisioned Throughput, and "variable", "spiky", "seasonal", or "unknown" for on-demand. If the question asks for the lowest cost with an unpredictable load, the answer is not provisioned capacity, even if the throttling error is in the story. Cross-Region inference profiles or a retry-with-backoff pattern fix throttling without a commitment.

    Other ways to buy capacity

    • Cross-Region inference. An inference profile lets Bedrock route a request to another Region with capacity. The price per token matches the source Region. Routing adds a small latency, reported as double-digit milliseconds when the feature launched. Choose a geographic profile when data must stay inside a geography, and a global profile when only cost and capacity matter.
    • Reserved service tier. A token-per-minute reservation (1 or 3 month terms) with a minimum size, billed monthly, and it overflows to Standard when you exceed it. It suits teams that want reserved capacity sized in tokens rather than in model units. Arrange it with your account team.
    • Flex service tier. A discount for work that tolerates slower responses, such as evaluations and summarization backfills. Set service_tier per request.

    SageMaker AI endpoints (2.2.1)

    When Bedrock does not offer the model you need, or you need control over the serving stack, you host the model yourself. Amazon SageMaker AI gives you managed endpoints that run a container on instances you choose. SageMaker offers four ways to run inference. For LLMs, one of them is ruled out immediately.

    Payload and timeout limits for each SageMaker option differ between documentation pages and change over time. Do not memorize numbers. Know the shape: serverless is small and short, real-time is interactive, asynchronous is large and slow, batch is offline.

    Hybrid designs

    The exam's word "hybrid" means two or more options behind one entry point. Three patterns come up.

    • Provisioned base, on-demand burst. A router sends traffic to Provisioned Throughput until it returns a throttling error, then falls back to on-demand.
    • Bedrock plus a specialist on SageMaker. General questions go to a Bedrock model, while a domain-tuned open-weight model on a SageMaker endpoint handles one task, such as extracting fields from your claim forms.
    • Bedrock Marketplace. You deploy a supported model to a SageMaker endpoint from the Bedrock console, then call it through the Bedrock Converse API with the endpoint ARN as the modelId. Your application code keeps one interface, while the hosting is yours.

    Streaming and cost control on SageMaker

    • Use InvokeEndpointWithResponseStream to receive tokens as they are produced. The container must send chunked responses.
    • Scale to zero. An endpoint that hosts inference components can scale down to zero instances when idle. Set MinInstanceCount to 0 in the endpoint's managed scaling, register each inference component with Application Auto Scaling at minimum capacity 0, and add a step scaling policy tied to a CloudWatch alarm to scale back out. The first request after zero fails until an instance starts, which takes several minutes. Scale to zero saves money for development and rarely used models, but not for a customer-facing chat.
    • Inference components also let several models share one endpoint's instances, each with its own memory and accelerator share.

    Container patterns for LLMs (2.2.2)

    A SageMaker endpoint runs a container. For LLMs you rarely write the container yourself. You pick a Large Model Inference (LMI) container that AWS maintains and configure it with environment variables.

    • LMI containers use DJL Serving and bundle inference engines such as vLLM and TensorRT-LLM. The engine supplies tensor parallelism (split the model across GPUs), continuous batching (add new requests to a running batch instead of waiting for it to finish), and token streaming.
    • You set behavior with variables such as HF_MODEL_ID (which model to load), OPTION_TENSOR_PARALLEL_DEGREE (how many GPUs to split across), and options for batching. Names and defaults change between container versions, so read the LMI documentation for the version you deploy.
    • Hugging Face Text Generation Inference (TGI) is another widely used serving container with streaming.

    If you do build your own container (bring your own container), SageMaker requires it to answer GET /ping for health checks and POST /invocations for inference, and to read the model from /opt/ml/model. Everything else is up to you. That is a heavy commitment for an LLM, which is why AWS ships the LMI containers.

    What drives sizing

    1. Weights fit. Total GPU memory across the instance must hold the weights at your chosen precision, plus headroom for the KV cache.
    2. Parallel degree matches GPUs. A tensor parallel degree of 4 needs at least 4 GPUs on the instance.
    3. Token throughput. Measure tokens per second at your expected concurrency. Test with realistic prompt and answer lengths, because a benchmark with short prompts overstates throughput.
    4. Startup time. Give the container a long enough health-check timeout, because loading a large model can take many minutes.

    Other container hosts

    You can also run LLM containers on Amazon ECS or Amazon EKS with GPU instances. You gain flexibility and lose the managed endpoint features (autoscaling policies tuned for SageMaker, data capture, inference components). The exam rarely prefers this route for a pure "deploy an FM" question. It appears when a company already runs a Kubernetes platform and wants one operational model. Lambda container images (up to 10 GB) are for small helper models and application code, and not for GPU-hungry LLMs, because Lambda has no GPU.

    Model loading strategies (2.2.2)

    A 70-billion-parameter model is about 140 GB at 16-bit precision. Copying that from S3 to disk, reading it into CPU memory, splitting it across GPUs, and copying it to the GPUs can take many minutes. During a traffic spike, an autoscaling group that needs ten minutes to add capacity is no help. Four strategies reduce the delay.

    StrategyWhat it doesTrade-off
    Fast model loading (SageMaker Fast Model Loader)Pre-shards the model, then streams the weights from S3 straight to the GPUs, skipping the disk and CPU memory copies. AWS reports loading up to 15 times faster in its tests.One-time optimization step. Needs LMI and a supported setup, so check the current docs.
    QuantizationStores weights in fewer bits, so there is less to load and fewer GPUs are needed.Some quality loss. Evaluate on your own prompts.
    Ahead-of-time compilationCompiles the model for the target engine once, so each new instance skips the compile step.Ties the artifact to one engine version and instance family.

    Exam tip

    Match the symptom to the fix. "New instances take too long to serve traffic after scaling out" points to faster loading or warm capacity. "The model does not fit on one GPU" points to tensor parallelism on a multi-GPU instance, or quantization. "The endpoint is out of memory under load but fine when idle" points to the KV cache, so cut the maximum context or concurrency, or move to a larger instance. A distractor will offer a CPU-based serverless option for a multi-gigabyte model.

    Smaller models and model cascading (2.2.3)

    Most questions that reach an application are easy. "What are your opening hours?" does not need a frontier model. Sending every request to the largest model is like running every database query on your most expensive replica. Two techniques cut that cost.

    • Pick the smallest model that passes your quality bar for the task. Classification, extraction, and short rewrites are often handled well by a small model. A narrowly fine-tuned small model can beat a general large model on its one task, at a fraction of the cost and latency. Build a test set from real prompts and measure rather than guessing.
    • Cascade. Send each request to a small, cheap model first. If its answer passes a check, return it. If not, send the request to a larger model. The exam calls this API-based model cascading.
    flowchart LR
  R["Request"] --> S["Small model"]
  S --> G{"Answer passes the check?"}
  G -->|"Yes, most requests"| OUT["Return the answer"]
  G -->|"No"| L["Larger model"]
  L --> OUT

    The check is the design

    A cascade is only as good as its gate. Use signals that cost little and are reliable.

    • Structural checks. The answer is valid JSON, matches a schema, or contains required fields. Deterministic and nearly free.
    • Refusal or uncertainty markers. The small model says it cannot answer, or returns a low confidence value you asked for.
    • Rule-based routing before the call. Short prompts without keywords from a "hard topics" list go to the small model. Prompts that mention contracts or legal terms go straight to the large one.
    • A judge model. A second model rates the answer. It works, but it adds cost and latency to every request, so reserve it for cases where cheap checks fail.

LARGE_MODEL_ID = os.environ["LARGE_MODEL_ID"]

PROMPT = (
    'Answer the question. Reply only with JSON: {"category": "...", "answer": "..."}.\n'
    "Question: "
)


def ask(model_id: str, question: str) -> str:
    """Call one model with the Converse API and return its text."""
    resp = bedrock.converse(
        modelId=model_id,
        messages=[{"role": "user", "content": [{"text": PROMPT + question}]}],
        inferenceConfig={"maxTokens": 400, "temperature": 0},
    )
    return resp["output"]["message"]["content"][0]["text"]


def is_acceptable(answer: str) -> bool:
    """Deterministic gate: the answer must be a JSON object with both required keys."""
    try:
        data = json.loads(answer)
    except json.JSONDecodeError:
        return False
    return isinstance(data, dict) and {"category", "answer"} <= data.keys()


def cascade(question: str) -> dict:
    """Try the small model first and escalate to the large model only when the gate fails."""
    small_answer = ask(SMALL_MODEL_ID, question)
    if is_acceptable(small_answer):
        return {"tier": "small", "answer": small_answer}
    return {"tier": "large", "answer": ask(LARGE_MODEL_ID, question)}

    When a cascade pays off

    Every escalated request pays for both calls and waits for both. Expected cost per request is cost of small + escalation rate × cost of large. With made-up prices of $0.0004 per small call and $0.006 per large call, and 20% of requests escalating:

    cascade cost = 0.0004 + 0.20 x 0.006 = 0.0016 per request
large only   = 0.0060 per request
saving       = (0.006 - 0.0016) / 0.006 = about 73%

    If the escalation rate climbs to 90%, cost is 0.0004 + 0.9 × 0.006 = 0.0058, which is barely lower than the large model alone, and every user also waits longer. Track the escalation rate as a metric and treat a rising rate as a signal that the small model, the prompt, or the gate needs attention.

    Exam tip

    Cascading reduces cost and latency for routine queries and keeps quality for hard ones. If a scenario says "most queries are simple but a few need deep reasoning", cascade or route. If it says "every query is complex", cascading only adds a wasted call. Bedrock also offers prompt routing features that choose between models for you. Check the current documentation for which model families are supported before relying on them, and compare against a gate you control.

    Knowledge check

    1. A retailer's chatbot traffic is flat at a high volume all day, and the team sees occasional throttling on on-demand calls. Finance asks for predictable cost and no throttling. Which Bedrock option fits, and what must the team check before choosing it?

      Answer

      Provisioned Throughput (or the Reserved service tier arranged with the account team). Before buying, the team checks that the model supports Provisioned Throughput in their Region, sizes the number of model units from peak tokens per minute rather than the average, and compares the hourly cost times 730 hours with the on-demand bill. A longer commitment lowers the price and removes the option to delete early.

    2. A team fine-tuned a model with Bedrock model customization and now wants to call it from an application. What is required, and how does that differ from a model they trained in SageMaker and imported?

      Answer

      A model customized in Bedrock can only be invoked through a Provisioned Throughput purchase, so the team pays an hourly price even when idle and calls the provisioned model ARN. A model imported with Custom Model Import is called through InvokeModel on demand, with no purchase. The import route requires a supported architecture and file format.

    3. A company needs an open-weight model that Bedrock does not offer, traffic is sparse, and the model has 70 billion parameters. They propose a SageMaker serverless endpoint to avoid idle cost. Why does this fail, and what should they do?

      Answer

      Serverless inference has no GPU support and small payload and time limits, and a 70-billion-parameter model needs about 140 GB for its weights at 16-bit precision. They should use a real-time endpoint on a multi-GPU instance with an LMI container and tensor parallelism. To cut idle cost, host the model as an inference component and scale to zero, accepting that the first request after zero fails for several minutes. Asynchronous inference is another fit when users do not wait on the answer.

    4. After a traffic spike, new SageMaker instances take about ten minutes to start serving, and users see errors during that time. Name two changes that help.

      Answer

      Speed up loading (pre-shard the model and use fast model loading so weights stream from S3 to the GPUs, or quantize the model to reduce what must be loaded), and keep warm capacity (a higher minimum instance count, or scale on a leading metric such as concurrent requests instead of after the load arrives). Raising the instance's CPU count does not help, because the delay is moving weights onto the GPUs.

    5. Eighty percent of a support bot's questions are simple FAQs, and the rest need deep reasoning. The bill is high because every call uses the largest model. What design lowers cost without lowering quality on hard questions, and which metric tells you it is working?

      Answer

      A cascade or router. Send each request to a small model with a deterministic gate (valid structure, no refusal, or a rule-based pre-check), and escalate failures or known-hard topics to the large model. Track the escalation rate and the cost per request. If the rate is low, cost drops sharply. If it approaches 100%, the cascade adds cost and latency, so fix the small model, the prompt, or the gate.

    Chapter recap

    • Start with two questions: who runs the GPUs, and who pays when nobody is calling.
    • On-demand is the default and costs nothing at idle. Service tiers (Priority, Flex, Reserved) and cross-Region profiles adjust speed, price, and capacity without a model purchase.
    • Lambda is the code that calls Bedrock, not a host for the model. Watch its 15 minute limit and API Gateway's 29 second default integration timeout.
    • Provisioned Throughput reserves capacity in model units, bills hourly until deleted, and is required for models customized in Bedrock. Size it by peak load and compare it with the on-demand bill.
    • SageMaker AI is for models Bedrock does not host and for full control. Real-time for interactive, asynchronous for large and slow, batch for offline. Serverless has no GPU and does not suit LLMs.
    • LLMs differ from classic ML in size, GPU memory (weights plus KV cache), token-by-token generation, streaming, and slow startup. LMI containers handle tensor parallelism, batching, and streaming.
    • Loading strategies: fast model loading, quantization, ahead-of-time compilation, and warm capacity.
    • Use the smallest model that meets your quality bar, and cascade from small to large with a deterministic gate. Watch the escalation rate.

    Most real GenAI work is not a new app. It is a CRM, an ERP, a ticketing system or a mainframe that already runs the business, and someone asks you to add a model to it.     How this task is examined

    Task 2.3 questions describe a company, an existing system and a constraint, then ask for an architecture. The constraint decides the answer. Read each scenario with four questions in order.

    1. Does the caller have to wait for the model? If yes, you need a synchronous call and you must protect it from slowness. If no, an event or a queue is almost always the better answer.
    2. What happens when the other side is down? Anything that must survive an outage needs retries and a place for failed work to land (a dead-letter queue).
    3. Who is allowed to call the model, and as whom? People, applications and other accounts each have a different answer.
    4. Where may the data go? A residency rule can rule out a Regional service, a public network path, or a whole Region.

    What you need from Domain 1

    You should be comfortable with IAM roles and policies for Bedrock (IAM for Bedrock), the resilience tools of retries, timeouts and fallbacks (resilience), and prompt versions (Prompt Management). This chapter builds on all three.

    Three ways to connect a model to an existing system (2.3.1)

    Every integration in this task is one of three patterns, or a mix. Learn to name them from a scenario.

    Backend analogy

    Request-response is a synchronous REST call between two services. Event-driven is a message broker with routing rules, closer to a RabbitMQ topic exchange than to a function call. Data synchronization is a read replica or a search index fed by change events. The exam uses the same trade-offs you already know, with AWS service names attached.

    The adapter (anti-corruption layer)

    Legacy systems rarely speak your model's language. They send SOAP or fixed-width files, use field names like CUST_NM_1, and cannot sign AWS requests. Do not put the model call inside the legacy system. Put a small adapter between them: a Lambda function that translates the legacy format into a clean request, calls the model, and translates the result back. If you swap the model or the legacy system later, only the adapter changes. Domain-driven design calls this an anti-corruption layer, and the exam describes it as “loose coupling”.

    What the legacy side can do decides the pattern

    • It can make outbound HTTPS calls: expose a webhook receiver (API Gateway and Lambda) or an event ingestion endpoint. See the webhook handler later in this section.
    • It can only write files or database rows: poll or watch. S3 event notifications fire when a file lands. A scheduled EventBridge rule can run a Lambda that reads new rows.
    • It cannot be changed at all: wrap it. An adapter on a schedule or behind an event bus calls its existing API and publishes what it finds as events.

    4. When the retries run out, Lambda sends the failed event, with the error, to the on-failure queue you configured. No ticket is lost.
    5. When billing recovers, you replay the queued events (a small script, or SQS redrive back to the function). The drafts appear two hours late, and nobody retyped anything.

    Exam tip

    There are two dead-letter paths, and the exam likes to test the difference. EventBridge's per-target dead-letter queue catches events that EventBridge could not deliver to the target (a missing permission, a throttled target, a deleted function). Once Lambda has accepted the event, EventBridge considers it delivered. If your function then fails, the event goes through Lambda's own asynchronous retries and then to the function's dead-letter queue or on-failure destination. A scenario that says “the function failed, and the EventBridge DLQ is empty” is pointing at this gap.

    A Bedrock knowledge base does not watch its data source. When someone adds, edits or deletes a document, the vector index stays as it was until you start an ingestion job.     Lambda as a webhook handler

    A webhook is an HTTP call that another system makes to you when something happens. Webhook senders have short timeouts and retry aggressively, so the rule is: verify, store or publish, and answer fast. Do the model call somewhere else. The handler below checks an HMAC signature, publishes an event and returns 202 Accepted.

    import hashlib
import hmac
import json
import os

import boto3

events = boto3.client("events")
SECRET = os.environ["WEBHOOK_SECRET"].encode()  # in production, read it from Secrets Manager at cold start


def lambda_handler(event: dict, context) -> dict:
    """Verify the sender's signature, publish an event, and return 202 without calling the model."""
    body = event.get("body") or ""
    headers = {k.lower(): v for k, v in (event.get("headers") or {}).items()}  # header casing can differ by API type
    expected = hmac.new(SECRET, body.encode(), hashlib.sha256).hexdigest()
    if not hmac.compare_digest(headers.get("x-signature", ""), expected):  # constant-time compare
        return {"statusCode": 401, "body": "bad signature"}

    payload = json.loads(body)
    result = events.put_events(Entries=[{
        "Source": "crm.webhook",
        "DetailType": payload.get("type", "unknown"),
        "Detail": json.dumps(payload),
    }])
    if result["FailedEntryCount"]:  # put_events can return success with failed entries
        return {"statusCode": 503, "body": "could not publish"}
    return {"statusCode": 202, "body": "accepted"}

    Two details are worth remembering. First, return a 5xx when you could not publish, so the sender retries. Second, the sender may deliver the same webhook twice, so the consumer must tolerate duplicates (use an id from the payload as an idempotency key).

    EventBridge for event-driven integration (2.3.2)

    Amazon EventBridge is a serverless event bus. Producers put events on a bus. Rules match events by pattern and send them to targets such as Lambda, Step Functions, SQS or an HTTPS endpoint. The producer does not know who consumes its events, which is the loose coupling the exam asks about.

    A pattern and a publish call

    This rule matches only high-priority tickets from the CRM. Everything else is ignored by this rule, and other rules can still match the same event.

  "detail": { "priority": ["high", "urgent"] }
}

    Check the current docs

    The default retry values are documented differently for classic rule targets (24 hours and 185 attempts) and for newer subscriber types in the current docs. Set both numbers explicitly on every target instead of relying on defaults, and read the retry page for the bus type you are using.

    Secure access frameworks (2.3.3)

    When a GenAI feature leaks data or runs up a bill, the cause is usually a permission that was too wide. The exam breaks access into three questions: who is the caller (identity federation), what may that caller do (role-based access control), and how narrow is the permission (least privilege).

    Who is the caller

    CallerHow it gets AWS permissionsWhat to avoid

    An application running on AWSAn execution role (Lambda, ECS task role, EC2 instance profile). The credentials are temporary and rotate by themselves.Access keys in environment variables or code.

    Backend analogy

    Identity federation is single sign-on with short-lived tokens, the same idea as OAuth 2.0 and OIDC in your FastAPI services. The IdP is the authorization server. IAM roles are the scopes, and the temporary credentials are the access token.

    What may the caller do: role-based access control

    Define roles by job, not by person, and attach policies to roles. A typical set for a GenAI platform looks like this.

    RoleAllowedNot allowed
    App runtime (Lambda role)Invoke the approved models and inference profiles, with the required guardrailCreating guardrails, customization jobs, or Provisioned Throughput
    Data scientistInvoke models in a sandbox account, run evaluation jobsProduction data, deleting logs
    Platform adminManage guardrails, inference profiles, model accessReading customer conversations
    AuditorRead invocation logs and CloudTrailInvoking models

    Model access and data access are separate lists. The model list is a set of resource ARNs in an IAM policy. The data list depends on where the data lives: separate S3 prefixes, separate knowledge bases, separate databases. Knowledge bases need extra care. Because every synced document is retrievable by anyone with bedrock:Retrieve on that knowledge base, give each sensitivity level its own knowledge base, or have a trusted backend apply the access rule before it calls Retrieve. Do not let the client send the filter, because a client can send a different one.

    How narrow: least privilege for model access

    A least-privilege policy for an application role names the actions, the model resources, and a condition that forces a guardrail. Read it line by line.

    {
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "InvokeApprovedModelWithRequiredGuardrail",
      "Effect": "Allow",
      "Action": ["bedrock:InvokeModel", "bedrock:InvokeModelWithResponseStream"],
      "Resource": [
        "arn:aws:bedrock:*::foundation-model/MODEL_ID",
        "arn:aws:bedrock:REGION:111122223333:inference-profile/PROFILE_ID"
      ],
      "Condition": {
        "StringEquals": {
          "bedrock:GuardrailIdentifier": "arn:aws:bedrock:REGION:111122223333:guardrail/GUARDRAIL_ID:1"
        }
      }
    },
    {
      "Sid": "DenyAnyOtherGuardrailOrNone",
      "Effect": "Deny",
      "Action": ["bedrock:InvokeModel", "bedrock:InvokeModelWithResponseStream"],
      "Resource": "*",
      "Condition": {
        "StringNotEquals": {
          "bedrock:GuardrailIdentifier": "arn:aws:bedrock:REGION:111122223333:guardrail/GUARDRAIL_ID:1"
        }
      }
    }
  ]
}
    • Actions. The Converse API is authorized by bedrock:InvokeModel, and ConverseStream by bedrock:InvokeModelWithResponseStream. There is no separate bedrock:Converse action to grant.
    • Resources. The foundation model ARN has no account number and the Region is a wildcard. When you call through a cross-Region inference profile, Bedrock may run the request in any Region the profile lists, so the policy must allow the model in all of them, plus the inference profile ARN. Pinning the model ARN to one Region is a classic cause of AccessDeniedException on a profile call that worked in testing.
    • Condition. bedrock:GuardrailIdentifier rejects any call that does not name this exact guardrail and version. The Allow grants access only with it, and the Deny catches everything else, including calls with no guardrail at all (a negated condition is true when the key is missing).
    • The same key works in a service control policy (SCP). An SCP is an organization-level guardrail on what accounts may do. A Deny with "Null": {"bedrock:GuardrailIdentifier": "true"} requires some guardrail on every call in the organization, without fixing which one.

    Exam tip

    The correct answer is almost never bedrock:* on *, an IAM user with access keys, or one shared role for all applications. Prefer the answer that scopes actions and resources, uses temporary credentials, and enforces the guardrail with a condition key so that application code cannot skip it. A permission boundary caps what a role can ever be granted, and an SCP caps what an account can do. Both are useful when different teams create their own roles.

    Secure routing: keep the call on the private network

    An interface VPC endpoint (AWS PrivateLink) gives your VPC a private address for a service. For Bedrock inference, create one for com.amazonaws.<region>.bedrock-runtime. Traffic from private subnets then reaches Bedrock without a path through the internet. Three details matter.

    1. The default endpoint policy allows everything. Attach a custom endpoint policy that names the principals, actions and models you permit.
    2. An endpoint policy does not stop a call that bypasses the endpoint. To require the private path, add a Deny in the role's policy when aws:SourceVpce is not your endpoint ID, and test that a call from outside is refused.
    3. Agents, knowledge bases and other Bedrock features that call other services on your behalf use their own paths. Check each feature's network requirements instead of assuming one endpoint covers all.

    Two reference patterns

    • Hybrid. Orchestration runs in the Region, for example with Bedrock Agents, and a Lambda function calls a self-hosted model in a Local Zone or on an Outpost for the steps that touch regulated data. The prompt decides where the work runs.

    CI/CD pipelines for GenAI components (2.3.5)

    Picture this: someone edits a system prompt to make answers friendlier. Unit tests pass, because the code did not change. The change ships, and the refusal rate doubles for a customer segment. A GenAI release has more moving parts than a normal one: application code, prompt text, model ID, guardrail version, retrieval settings and tool definitions. Any of them can change behavior, and the output is not deterministic. A pipeline for these systems adds two stages a normal pipeline lacks: an evaluation gate and a security scan that includes prompt attacks.

    flowchart LR
  C["Commit, or new prompt version promoted"] --> B["CodeBuild: build and unit tests"]
  B --> E["CodeBuild: evaluation on a fixed dataset"]
  E --> S["CodeBuild: security scan and attack prompts"]
  S --> D["Deploy to staging"]
  D --> K["CodeDeploy: canary on a Lambda alias"]
  K -->|"alarm fires"| RB["Automatic rollback"]
  K -->|"healthy"| P["100 percent of traffic"]

    The stages

    1. Trigger. A commit to the main branch, or the promotion of a new prompt version in your prompt registry. Treat a prompt change like a code change.
    2. Build and unit tests. Test the deterministic parts: input parsing, tool functions, output validation, the legacy adapter. Mock the model.
    3. Evaluation. Run the new version against a versioned dataset of questions with known good answers, and score the outputs (rules, reference comparison, or a model acting as judge). Fail the build if the score falls below a threshold, so a quality regression cannot ship.
    4. Security scan. Static analysis of code, dependency vulnerability checks, secret scanning, and a set of adversarial prompts (prompt injection, attempts to extract the system prompt, attempts to make the model reveal personal data). Fail on findings above your threshold.
    5. Deploy to staging, then canary. Send a small share of production traffic to the new version, watch the alarms, then widen or roll back.

    CodePipeline and CodeBuild

    AWS CodePipeline is the orchestrator that moves a change through stages (source, build, test, deploy, approval). AWS CodeBuild is a managed build runner that executes commands from a buildspec.yml file and fails the stage when a command exits with a non-zero code. That exit code is the whole mechanism of a quality gate: write a small script that returns 1 when a check fails.

    version: 0.2
env:
  variables:
    EVAL_MIN_SCORE: "0.85"
phases:
  install:
    commands:
      - pip install -r requirements.txt
  build:
    commands:
      - pytest tests/unit -q                                   # deterministic code
      - python eval/run_eval.py --dataset eval/golden.jsonl --out eval/results.json
      - python eval/gate.py eval/results.json --min-score "$EVAL_MIN_SCORE"
      - bandit -r src -q                                       # static analysis (example tool)
      - pip-audit                                              # dependency check (example tool)
      - python eval/red_team.py --prompts eval/attacks.jsonl   # prompt-injection suite
artifacts:
  files:
    - '**/*'

    The tools named above are examples. Use the scanners your security team mandates. The gate script is the part that is specific to GenAI.

    import argparse
import json
import sys


def main() -> int:
    """Return 0 if the average score and every critical case pass, otherwise 1 (which fails the build)."""
    parser = argparse.ArgumentParser()
    parser.add_argument("results")
    parser.add_argument("--min-score", type=float, required=True)
    args = parser.parse_args()

    with open(args.results) as f:
        results = json.load(f)  # list of {"id": str, "score": float, "critical": bool}

    average = sum(r["score"] for r in results) / len(results)
    critical_failures = [r["id"] for r in results if r.get("critical") and r["score"] < 1.0]

    print(f"average score {average:.3f} (minimum {args.min_score}), critical failures: {critical_failures}")
    return 0 if average >= args.min_score and not critical_failures else 1


if __name__ == "__main__":
    sys.exit(main())

    An average alone can hide a disaster, because one broken safety case disappears in a mean of fifty good ones. That is why the gate also checks critical cases one by one.

    Rollback support

    Rollback means being able to return to the last good version in minutes, without a new build. For a Lambda-based application, AWS CodeDeploy shifts traffic between two published versions of a function through an alias. A deployment configuration sets the shape, such as 10 percent for five minutes and then the rest (canary), or 10 percent every minute (linear). You attach CloudWatch alarms to the deployment. If one enters the alarm state during the shift, CodeDeploy rolls back automatically. With the Serverless Application Model (SAM) it is a few lines.

    Resources:
  AdapterFunction:
    Type: AWS::Serverless::Function
    Properties:
      Handler: app.lambda_handler
      Runtime: python3.13
      AutoPublishAlias: live
      DeploymentPreference:
        Type: Canary10Percent5Minutes
        Alarms:
          - !Ref AdapterErrorsAlarm
          - !Ref GuardrailBlockRateAlarm

    What goes in the alarms decides whether rollback protects users. Lambda errors and latency are a start. For GenAI add custom metrics: the guardrail intervention rate, the share of responses that fail output validation, and a user signal such as thumbs-down. A prompt regression does not throw exceptions, so only a metric on quality-related behavior will catch it.

    Prompts have their own rollback. If prompts live in Bedrock Prompt Management (see Domain 1), each saved version is immutable, and the application points at a version number. Rolling back is changing that pointer back, which you can do without redeploying code.

    Exam tip

    If a scenario says tests pass but quality dropped after a release, the missing piece is an evaluation gate on a fixed dataset, not more unit tests. If it says “roll back automatically when errors rise”, the answer is CodeDeploy with alarms on an alias, not a manual redeploy. A distractor will propose a CodeBuild step that calls the model once and checks for a 200 status. That tests the network, not the quality.

    A minimal gateway handler

    This sketch shows the three jobs that matter most: take the caller's identity from the authorizer (never from the request body), enforce a per-team model allowlist, and emit one structured usage record per call. CloudWatch turns that record into metrics through the Embedded Metric Format (EMF), which is a JSON log line with a special _aws key.

    import json
import time

import boto3

bedrock = boto3.client("bedrock-runtime")

# In production this comes from a table or AppConfig, not a constant.
TEAM_POLICY = {
    "support": {"models": {"chat-small"}, "max_tokens": 500},
    "research": {"models": {"chat-small", "chat-large"}, "max_tokens": 2000},
}
MODEL_CATALOG = {"chat-small": "SMALL_MODEL_ID", "chat-large": "LARGE_MODEL_ID"}  # replace with real IDs


def emit_usage(team: str, alias: str, usage: dict, latency_ms: int) -> None:
    """Print one EMF log line so CloudWatch creates per-team token metrics."""
    print(json.dumps({
        "_aws": {
            "Timestamp": int(time.time() * 1000),
            "CloudWatchMetrics": [{
                "Namespace": "GenAIGateway",
                "Dimensions": [["Team", "Model"]],
                "Metrics": [
                    {"Name": "InputTokens", "Unit": "Count"},
                    {"Name": "OutputTokens", "Unit": "Count"},
                    {"Name": "LatencyMs", "Unit": "Milliseconds"},
                ],
            }],
        },
        "Team": team, "Model": alias,
        "InputTokens": usage["inputTokens"], "OutputTokens": usage["outputTokens"], "LatencyMs": latency_ms,
    }))


def lambda_handler(event: dict, context) -> dict:
    """Authorize by team policy, call the model through Converse, and record usage."""
    team = event["requestContext"]["authorizer"]["team"]  # set by the authorizer, never by the caller
    body = json.loads(event["body"])
    alias = body.get("model", "chat-small")

    policy = TEAM_POLICY.get(team)
    if policy is None or alias not in policy["models"]:
        return {"statusCode": 403, "body": json.dumps({"error": "model not allowed for this team"})}

    resp = bedrock.converse(
        modelId=MODEL_CATALOG[alias],
        messages=[{"role": "user", "content": [{"text": body["prompt"]}]}],
        inferenceConfig={"maxTokens": min(body.get("max_tokens", 300), policy["max_tokens"])},
    )
    emit_usage(team, alias, resp["usage"], resp["metrics"]["latencyMs"])
    text = resp["output"]["message"]["content"][0]["text"]
    return {"statusCode": 200, "body": json.dumps({"text": text})}

    Chapter 4 adds the parts this sketch leaves out: usage plans and rate limits at the API layer, retries, and fallbacks.

    Knowledge check

    1. A legacy ERP can only make outbound HTTPS calls. It sends bursts of 5,000 order notes in a few minutes, and the team wants a model-written summary stored for each. Bedrock throttles under that burst. What design absorbs it?

      Answer

      Receive the notes through API Gateway and a webhook Lambda that verifies the sender, publishes an event (or sends to an SQS queue), and returns 202 at once. A worker Lambda consumes the queue at a controlled concurrency so model calls stay under the quota, retries throttled calls with backoff, and sends repeated failures to a dead-letter queue. The ERP never waits for the model.

    2. An EventBridge rule invokes a Lambda adapter. The legacy system goes down, the function throws, and some events are lost. The rule's dead-letter queue is empty. Why, and what is the fix?

      Answer

      EventBridge delivered each event successfully, because Lambda accepted it for asynchronous processing. The failure happened inside the function, so the rule's DLQ never sees it. Configure the function's asynchronous invocation settings: retry attempts, a maximum event age, and a dead-letter queue or on-failure destination (SQS, for example). The EventBridge DLQ still protects against delivery failures such as a missing permission or a throttled target.

    3. A company wants every developer to use Bedrock from their laptop, with no long-lived keys, an audit trail per person, and access to only two approved models. What should they set up?

      Answer

      Federate the corporate IdP into AWS IAM Identity Center and create a permission set whose policy allows bedrock:InvokeModel and InvokeModelWithResponseStream on only the two models (and the inference profile ARNs they use). Assign it to a group synchronized from the IdP. Each person gets a temporary session, and CloudTrail records who called. IAM users with access keys, or one shared role, fail the requirements.

    4. A hospital must keep patient notes on premises, but another department only needs EU data residency and no public internet. What does each get?

      Answer

      The notes stay local with a fully local design: a self-hosted model and a local vector store on AWS Outposts in the hospital's data center, with nothing sent to the Region. The EU-only department uses Bedrock in an EU Region with a geographic cross-Region inference profile (not a global one), reached through a bedrock-runtime interface endpoint and, from on premises, Direct Connect or a Site-to-Site VPN, with a Deny on aws:SourceVpce to force the private path.

    5. A pipeline runs unit tests and deploys. A prompt change doubles the refusal rate in production, and no test failed. Name the missing pipeline stage, the missing alarm, and how to roll back.

      Answer

      The pipeline has no evaluation gate that runs the new prompt against a fixed dataset and fails below a threshold (and no check of critical cases). It has no alarm on a GenAI-specific metric such as the refusal or guardrail intervention rate. Rollback is a CodeDeploy traffic shift on a Lambda alias with alarms attached, which reverts automatically, or pointing the application back at the previous prompt version in Prompt Management.

    • Ask four questions: does the caller wait, what if the other side is down, who may call, and where may the data go.
    • Three patterns: request-response, event-driven and data sync. Put an adapter between a legacy system and the model so that either side can change.
    • API Gateway: AWS_PROXY for Lambda, AWS for direct service calls with mapping templates, HTTP_PROXY to front an existing REST service. Webhook handlers verify, publish and return 202.
    • EventBridge routes by pattern and has per-target retry policies and dead-letter queues. A function failure after delivery is handled by Lambda's own retries and on-failure destination, not by the EventBridge DLQ.
    • Knowledge bases do not update themselves. Trigger StartIngestionJob, and remember that anyone with bedrock:Retrieve can retrieve everything synced.
    • Access: federate people through Identity Center, give apps execution roles, never give end users model permissions. Scope actions and model resources, allow the model in every Region a cross-Region profile uses, and enforce guardrails with bedrock:GuardrailIdentifier.
    • Private path: a bedrock-runtime interface endpoint plus a Deny on aws:SourceVpce. Location rules need Outposts, Local Zones, or a geographic profile. Bedrock itself is Regional.
    • GenAI CI/CD adds an evaluation gate and an attack-prompt scan, and rolls back through CodeDeploy alarms on an alias or a prompt version pointer.

    The asynchronous pattern with SQS

    Amazon SQS is a managed queue. Producers put messages in, consumers take them out, and a message that is not deleted after processing becomes visible again after a timeout. That last property is what makes it safe for model calls: a worker that crashes does not lose the job.

    Walkthrough: 200 long documents arrive at once

    1. A client posts 200 summarization jobs. API Gateway puts each on the queue and answers 202 Accepted with a job ID in milliseconds. Nobody waits for Bedrock.
    2. Lambda's SQS integration polls the queue and invokes the worker with batches of messages. You set a maximum concurrency on the event source mapping, so at most a fixed number of workers run at once. That number is how you keep the model calls under your tokens-per-minute quota.
    3. Each worker calls Bedrock, writes the summary to a job table, and returns. Lambda deletes the messages it processed successfully.
    4. A call is throttled, so one message in a batch fails. The worker reports just that message as failed (a partial batch response), and the others are not re-run. The failed message reappears after the visibility timeout.
    5. After the queue's maximum receives value (say 3) the message moves to the dead-letter queue. An alarm on that queue's depth tells you something needs a person.
    6. The client polls GET /jobs/{id}, or you notify it with a webhook or a WebSocket message when the job is done.

    Three settings are classic exam material.

    • Visibility timeout: set it to at least six times the function timeout, plus the batching window. If it is shorter than the time a worker needs, SQS hands the same message to a second worker while the first is still running, and you pay for the model call twice.
    • Dead-letter queue and maximum receives: without them a poison message (one that always fails) returns to the queue forever.
    • Partial batch response: enable ReportBatchItemFailures on the event source mapping and return the IDs of failed messages. Without it, one failure makes Lambda retry the whole batch, including the messages that worked. If the function throws an exception instead of returning the list, the whole batch counts as failed.

    API Gateway request validation

    Every malformed request that reaches Lambda costs an invocation, and the one that reaches the model can cost real tokens. API Gateway can reject bad requests itself, before any backend runs. You attach a request validator to a method and describe the expected body with a model, which is a JSON Schema document. A request that does not match gets a 400 from API Gateway, and nothing downstream runs.

    {
  "$schema": "http://json-schema.org/draft-04/schema#",
  "title": "ChatRequest",
  "type": "object",
  "required": ["prompt"],
  "properties": {
    "prompt": { "type": "string", "minLength": 1, "maxLength": 8000 },
    "max_tokens": { "type": "integer", "minimum": 1, "maximum": 1000 },
    "tier": { "type": "string", "enum": ["fast", "deep"] }
  },
  "additionalProperties": false
}

    Read what this schema blocks: an empty prompt, a prompt over 8,000 characters, a max_tokens that would allow a huge, expensive answer, an unknown tier, and any extra field. The validator can also check that required query strings or headers are present (validateRequestParameters).

    Heads up

    A schema limits characters, not tokens. A prompt of 8,000 characters can be a few thousand tokens, and a prompt in another language can use more tokens per character. Edge validation is a cheap first filter. Token limits and context-window checks still belong in your code, which Chapter 5 covers.

    Exam tip

    “Reject malformed requests without invoking the backend” is a request validator with a model. The distractors are input validation inside the Lambda (which still costs an invocation), a Lambda authorizer (that handles identity, not shape), and AWS WAF (that matches patterns like SQL injection, not your schema).

    A model produces its answer one token at a time. A 500-token answer at a typical speed takes several seconds, and a non-streaming call hides all of it until the last token is ready. Streaming sends tokens as they are produced. The total time is unchanged. What changes is time to first token, which is the delay before anything appears and the number users feel.

        modelId=model_id,
        messages=[{"role": "user", "content": [{"text": prompt}]}],
        inferenceConfig={"maxTokens": 500},
    )
    for event in resp["stream"]:
        if "contentBlockDelta" in event:
            text = event["contentBlockDelta"]["delta"].get("text", "")
            if text and first_token_at is None:
                first_token_at = time.perf_counter() - start
            print(text, end="", flush=True)
        elif "metadata" in event:
            usage = event["metadata"]["usage"]
    return {"first_token_s": first_token_at, "total_s": time.perf_counter() - start, "usage": usage}

    Streaming lowers the chance of a read timeout on a long answer but does not remove it. The timeout still applies to each wait, including the wait for the first token, so a throttled or overloaded model can still time out before it emits anything.

    Note

    For InvokeModel the streaming operation is InvokeModelWithResponseStream, and the events carry a model-specific JSON payload. IAM treats ConverseStream and InvokeModelWithResponseStream as the same permission, bedrock:InvokeModelWithResponseStream, as Chapter 3 showed.

    A Python streaming endpoint

    The FastAPI handler below turns the Bedrock event stream into SSE events. It sends the text deltas as they arrive, then a final event with token usage. Because the response headers are already sent by the time the first token goes out, an error halfway through cannot change the status code. The handler therefore ends the stream with an error event that the client must handle.

    import json
import os
from collections.abc import Iterator

import boto3
from fastapi import FastAPI
from fastapi.responses import StreamingResponse
from pydantic import BaseModel, Field

app = FastAPI()
bedrock = boto3.client("bedrock-runtime")
MODEL_ID = os.environ["MODEL_ID"]


class ChatRequest(BaseModel):
    prompt: str = Field(min_length=1, max_length=8000)
    max_tokens: int = Field(default=300, ge=1, le=1000)


def sse(event: str, data: dict) -> str:
    """Format one server-sent event."""
    return f"event: {event}\ndata: {json.dumps(data)}\n\n"


def token_events(req: ChatRequest) -> Iterator[str]:
    """Yield SSE events for each text delta, then usage, or an error event if the stream breaks."""
    try:
        resp = bedrock.converse_stream(
            modelId=MODEL_ID,
            messages=[{"role": "user", "content": [{"text": req.prompt}]}],
            inferenceConfig={"maxTokens": req.max_tokens},
        )
        for event in resp["stream"]:
            if "contentBlockDelta" in event:
                text = event["contentBlockDelta"]["delta"].get("text", "")
                if text:
                    yield sse("token", {"t": text})
            elif "metadata" in event:
                yield sse("usage", event["metadata"]["usage"])
        yield sse("done", {})
    except Exception as exc:  # headers are already sent, so report the failure inside the stream
        yield sse("error", {"message": type(exc).__name__})


@app.post("/chat")
def chat(req: ChatRequest) -> StreamingResponse:
    """Stream the model's reply as server-sent events."""
    return StreamingResponse(token_events(req), media_type="text/event-stream")

    Two cost facts are easy to miss. First, a streaming Lambda keeps running if the client disconnects, so the model keeps generating and you pay for the full duration. Check for a closed connection in long-running handlers where you can. Second, test streaming from a real client such as curl --no-buffer. The Lambda console test always shows a buffered result, so it can make a working stream look broken.

    Exam tip

    Match the verb. “Show text as it is generated” is streaming. “Client sends follow-up messages while the reply continues” or “server pushes updates” is a WebSocket. “A stream that must outlive the 29-second REST timeout” is API Gateway response streaming (up to 15 minutes) or a Lambda function URL. A distractor offers response caching or a VTL response template, and neither works on a streamed response.

    Resilient FM systems (2.4.3)

    A busy GenAI application will see throttling, slow responses and occasional service errors. The goal is that users see a slower answer or a simpler answer, not an error page. Build resilience in layers, and put each concern at exactly one layer.

    1. Know which errors to retry

    ErrorMeaningDo this
    ThrottlingException (HTTP 429)You exceeded a quota for requests or tokens per minute.Retry with backoff and jitter. If it persists, slow down at the source, switch to a cross-Region profile, request a quota increase, or queue the work.
    ServiceUnavailableException (503)Temporary capacity shortage on the service side, not tied to your quota.Retry with backoff. Consider a cross-Region profile or a fallback model.
    ModelTimeoutExceptionThe model did not finish in time.Retry once or twice, then shorten the prompt or output limit, or stream.
    InternalServerExceptionA server-side error.Retry with backoff.
    ValidationException, AccessDeniedExceptionYour request or permissions are wrong.Do not retry. Fix the cause. Retrying only adds load.

    2. Retries with exponential backoff and jitter

    Exponential backoff waits longer after each failure (1 second, 2, 4, 8 and so on) so a struggling service gets room to recover. Jitter adds randomness to each wait. Without it, a thousand clients that failed together retry together, and the spike repeats. With it, the retries spread out.

    Made-up numbers, base delay 1 s, three retries:

Without jitter (1,000 clients all failed at t=0)
  retry 1 at 1 s   -> 1,000 requests at once
  retry 2 at 3 s   -> 1,000 requests at once
  retry 3 at 7 s   -> 1,000 requests at once

With jitter (each client waits a random time up to the limit)
  retry 1 between 0 and 1 s -> roughly 1,000 requests spread across the second
  retry 2 between 0 and 2 s -> spread across two seconds
  retry 3 between 0 and 4 s -> spread across four seconds

    The AWS SDKs do this for you. In Python, botocore has three retry modes: legacy, standard (the default now) and adaptive. Standard retries throttling and transient errors with exponential backoff and jitter, and it has a retry quota (a token bucket) that stops retries when a service has been failing for a while, so retries cannot pile onto an outage. Adaptive adds client-side rate limiting on top of standard: it slows the client down when it sees throttling.

    import boto3
from botocore.config import Config

bedrock = boto3.client(
    "bedrock-runtime",
    config=Config(
        retries={"max_attempts": 5, "mode": "standard"},  # in a Config object this counts retries, not the first try
        connect_timeout=5,
        read_timeout=60,
    ),
)

    Heads up

    The meaning of max_attempts depends on where you set it. In a Config object it excludes the first request (so 5 means up to 6 calls in total). In the AWS config file or the AWS_MAX_ATTEMPTS environment variable it includes the first request. The exam may not ask this, but a wrong number in production will surprise you.

    The main mistake is retrying at several layers at once. If the SDK retries 5 times, your application retries 3 times around it, and the client retries 3 times around that, one failure becomes 45 calls to an already struggling model. Pick the layer that owns the retry (usually the SDK), and let the layers above it fail fast or fall back.

    3. Rate limiting at the API layer

    Retries handle throttling after it happens. Rate limiting prevents one caller from causing it. In API Gateway you create a usage plan and attach API keys to it. Each plan has three numbers.

    SettingWhat it meansExample (made up)
    RateRequests per second that refill the bucket5 for the free tier, 50 for the paid tier
    BurstThe size of the token bucket: how many requests can arrive at once10 and 100
    QuotaTotal requests per day, week or month1,000 per day, 100,000 per month

    A client over its rate or burst gets 429 Too Many Requests from API Gateway, and your Lambda and Bedrock never see the request. API keys identify and meter clients for a plan. They are not a security mechanism on their own, so keep a real authorizer (Cognito, a Lambda authorizer or IAM) next to them.

    Heads up

    A request-per-second limit does not limit tokens. Ten requests per second with 5,000-token prompts can exhaust a tokens-per-minute quota that a hundred small requests would not. Pair rate limits with a maximum prompt length (the validator) and a max_tokens cap, and give each plan a daily quota sized in requests times an average token count.

    4. Fallbacks and graceful degradation

    When retries are used up, decide what the user gets. Work down a ladder and stop at the first rung that works.

    1. Same model through another route: a cross-Region inference profile, so capacity in another Region can serve the call.
    2. A different model: a cheaper or less loaded model that gives an acceptable answer.
    3. A cached answer: the response to a similar earlier question, if the use case permits.
    4. A reduced feature: a shorter answer, a retrieval-only result with no generation, or a canned response.
    5. A queued job: tell the user the answer will arrive by email or notification, and use the SQS pattern above.
    import boto3
from botocore.exceptions import ClientError

bedrock = boto3.client("bedrock-runtime")
RETRYABLE = {"ThrottlingException", "ServiceUnavailableException", "ModelTimeoutException", "InternalServerException"}


def ask(model_id: str, prompt: str) -> str:
    """Call one model once. The SDK has already retried transient errors inside this call."""
    resp = bedrock.converse(
        modelId=model_id,
        messages=[{"role": "user", "content": [{"text": prompt}]}],
        inferenceConfig={"maxTokens": 400},
    )
    return resp["output"]["message"]["content"][0]["text"]


def answer_with_fallback(prompt: str, chain: list[str]) -> dict:
    """Try each model in order. Return the answer and which rung produced it, or a degraded reply."""
    for rung, model_id in enumerate(chain):
        try:
            return {"text": ask(model_id, prompt), "rung": rung, "degraded": rung > 0}
        except ClientError as exc:
            if exc.response["Error"]["Code"] not in RETRYABLE:
                raise  # a bad request will fail on every model, so do not fall through
    return {"text": "We are very busy. Your request is saved and we will email the answer.", "rung": None, "degraded": True}

    Record which rung served each request. A dashboard that shows the share of degraded answers is how you notice, before your users tell you, that the primary model has been struggling for an hour.

    5. Observability across boundaries with X-Ray

    When a request crosses API Gateway, Lambda, SQS and Bedrock, the question “where did the time go?” has no answer in any single log. AWS X-Ray follows a request across services. It assigns a trace ID at the edge, passes it along in a header, and each service adds a segment (and code can add subsegments for the calls it makes). The console then shows a service map and a waterfall.

    • API Gateway: turn on active tracing on the stage. X-Ray supports tracing for REST APIs, not for HTTP APIs.
    • Lambda: set tracing to Active on the function. Lambda then records its own segment.
    • Calls to Bedrock: instrument the AWS SDK client so each call becomes a subsegment with its own duration. Annotate the trace with the model ID and, if you route, the route you chose, so you can filter by it later.

    With that in place, a slow request shows its split at a glance: 40 ms in API Gateway, 20 ms in cold start, 900 ms waiting for the first model token. The slow part is obvious, and the argument about who is to blame ends.

    Check the current docs

    Which library you use to instrument code (the X-Ray SDK, the AWS Distro for OpenTelemetry, or the Powertools for AWS Lambda tracer, which wraps the X-Ray SDK) has been shifting. Check what AWS currently recommends for your language. The concepts above do not change.

    Exam tip

    Match the symptom to the layer. “One customer's script causes throttling for everyone” is a usage plan. “Bursts cause occasional 429s from Bedrock” is SDK retries with jitter, and a cross-Region profile for capacity. “The service must still answer when the primary model is unavailable” is a fallback chain. “Find which service adds the latency” is X-Ray. A distractor says to increase the Lambda timeout. That hides the delay and does not fix the cause.

    Intelligent model routing (2.4.4)

    Chapter 2 showed a cascade: try the small model, escalate if a check fails. Routing is the other half of the idea: decide before the call which model should get the request. The aim is the same, the cheapest model that meets the quality bar for this request. The exam lists four ways to do it, from simplest to most dynamic.

    ApproachDecision is made byChanges whenUse it when
    Static routingA fixed table in application code or configuration: route name to model IDYou change the configurationFew request types, known in advance (for example, “summarize” always uses model A, “extract” always uses model B).
    Content-based routingA classifier looks at each request (rules, or a small model), then a Step Functions Choice state or code picks the branchThe request content changesMixed traffic: simple FAQs and hard reasoning, code questions and prose.
    Metric-based routingLive numbers: error rate, throttle rate, latency or cost of each modelThe system's health changesYou have two acceptable models and want traffic to move away from the one that is struggling.

    Static and content-based routing in code

    The router below combines a static table (the mapping from route to model, which you would load from configuration) with cheap rules to classify each request. Rules are fast, free and predictable. When rules are not enough, replace classify with a call to a small model that returns one of the route names, and validate that its answer is one of the allowed values.

    ROUTES = {
    "simple": "SMALL_MODEL_ID",
    "complex": "LARGE_MODEL_ID",
    "code": "CODE_MODEL_ID",
}
HARD_WORDS = ("compare", "analyze", "analyse", "step by step", "why does", "trade-off", "evaluate")


def classify(prompt: str) -> str:
    """Cheap, deterministic classification. Return one of the keys of ROUTES."""
    lowered = prompt.lower()
    if "```" in prompt or "traceback" in lowered or "def " in lowered:
        return "code"
    if len(prompt) < 200 and not any(word in lowered for word in HARD_WORDS):
        return "simple"
    return "complex"


def pick_model(prompt: str, override: str | None = None) -> tuple[str, str]:
    """Return (route, model_id). An explicit override from a trusted caller wins over classification."""
    route = override if override in ROUTES else classify(prompt)
    return route, ROUTES[route]

    Log the route with every request. Without that log you cannot tell whether the router sends 90 percent of traffic to the large model, which would mean it saves nothing.

    Content-based routing with Step Functions

    When routing involves several steps (classify, call, validate, maybe call again) it is easier to see and change as a state machine. The Choice state reads a field from the state's data and picks the next state. It is plain, deterministic logic, with no model deciding the branch.

    Read the failure path: if the small or code model fails after its retries, the Catch sends the same request to the large model, so routing doubles as a fallback. Step Functions also has an optimized integration that calls Bedrock directly, with no Lambda in between, which you can use for simple calls. Standard workflows are the right type here if you need execution history and long waits. Express workflows suit short, high-volume routing, and they cost less per request.

    Metric-based routing

    Here the router asks “is the primary model healthy right now?” and chooses accordingly. Bedrock publishes per-model CloudWatch metrics (in the AWS/Bedrock namespace, with a ModelId dimension), including invocations, throttles, errors and latency.

    import time
from datetime import datetime, timedelta, timezone

import boto3

cloudwatch = boto3.client("cloudwatch")
_cache: dict[str, tuple[float, float]] = {}  # model_id -> (checked_at, throttle_rate)


def _sum(model_id: str, metric: str, minutes: int) -> float:
    """Total of a Bedrock metric for one model over the last few minutes."""
    end = datetime.now(timezone.utc)
    points = cloudwatch.get_metric_statistics(
        Namespace="AWS/Bedrock", MetricName=metric,
        Dimensions=[{"Name": "ModelId", "Value": model_id}],
        StartTime=end - timedelta(minutes=minutes), EndTime=end,
        Period=minutes * 60, Statistics=["Sum"],
    )["Datapoints"]
    return sum(p["Sum"] for p in points)


def throttle_rate(model_id: str, minutes: int = 5, ttl: float = 60.0) -> float:
    """Share of recent calls that were throttled. Cached, because CloudWatch lags and costs a call."""
    checked_at, rate = _cache.get(model_id, (0.0, 0.0))
    if time.time() - checked_at < ttl:
        return rate
    calls = _sum(model_id, "Invocations", minutes)
    rate = _sum(model_id, "InvocationThrottles", minutes) / calls if calls else 0.0
    _cache[model_id] = (time.time(), rate)
    return rate


def choose(primary: str, secondary: str, max_throttle_rate: float = 0.05) -> str:
    """Use the primary model unless it is being throttled more than the allowed share of the time."""
    return secondary if throttle_rate(primary) > max_throttle_rate else primary

    Two cautions. CloudWatch metrics arrive with a delay of a minute or more, so metric-based routing reacts to trouble that started a little while ago, and the cache makes it slightly slower still. And the switch needs hysteresis: if the rule flips at 5 percent, a model hovering around 5 percent makes the router flap. Use a lower threshold to switch back than to switch away, or hold each decision for several minutes.

    Request transformation in API Gateway

    With a non-proxy integration (Chapter 3's AWS or HTTP types), API Gateway can rewrite the request before the backend sees it, using a mapping template written in Velocity Template Language (VTL). This one reads a header and a stage variable and sets the model field. No code changes are needed to move the “deep” tier to a different model, only the stage variable.

    #set($tier = $input.params('x-tier'))
{
  "model": "#if($tier == 'deep')$stageVariables.deepModel#{else}$stageVariables.fastModel#end",
  "body": $input.json('$')

    Remember the limits: a mapping template needs a non-proxy integration, and with response streaming switched on, API Gateway cannot apply a VTL response transformation. Request transformation is still available on the way in. Many teams keep routing in the Lambda (proxy integration) and use API Gateway only for the front door, which is simpler to test.

    Amazon Bedrock intelligent prompt routing

    Bedrock offers routing as a managed feature. You call a prompt router as if it were a model. For each request it predicts which of two models in the same family will answer well, and sends easy requests to the cheaper one and hard requests to the stronger one. One of the two is the fallback model. AWS provides default routers, and you can configure your own pair of models.

    • It routes between two models in the same model family, in the same Region.
    • It is tuned for English, chat-style prompts. For other languages or specialized domains, test it on your own prompts before you rely on it.
    • It does not learn from your application's own quality data, so it may not be the best choice for a narrow, domain-specific task.

    Check the current docs

    The list of supported models and Regions for prompt routing changes, so confirm it before you plan around it. When a scenario needs routing across different families, on custom criteria or across providers, build the router yourself with the approaches above.

def buffered(model_id: str) -> dict:
    """One blocking call. The user sees nothing until it returns."""
    start = time.perf_counter()

    Knowledge check

    1. An API Gateway REST API fronts a Lambda that calls Bedrock. Long answers fail at about 30 seconds even though the Lambda timeout is 5 minutes. Name two fixes and say when each fits.

      Answer

      Switch the user-facing call to streaming (API Gateway response streaming on a Lambda proxy integration, or a Lambda function URL with response streaming), so tokens flow within the time limit and the stream may run up to the streaming maximum. Or make the work asynchronous: return 202 with a job ID, put the job on SQS, and let a worker call Bedrock without a client waiting. Streaming fits interactive chat. Asynchronous fits batches, long documents and results nobody is watching. Raising only the Lambda timeout does not help, because the API's integration limit ends the request first.

    2. An SQS-triggered Lambda calls Bedrock. When one message in a batch of ten fails, all ten are processed again and the team pays for the model calls twice. What two settings fix it, and what must the function return?

      Answer

      Enable ReportBatchItemFailures on the event source mapping, and make the function catch errors per message and return {"batchItemFailures": [{"itemIdentifier": messageId}]} for only the failed ones. Also set the queue's visibility timeout to at least six times the function timeout plus the batching window, so a slow call is not handed to a second worker. A dead-letter queue with a maximum receive count stops a poison message from returning forever. If the function throws instead of returning the list, the whole batch counts as failed.

    3. A chat feature must show text as it is generated, and the user may also send a “stop” message while the reply is streaming. Which delivery option fits, and what limits should the team check?

      Answer

      A WebSocket API, because the client sends and receives on one persistent connection. SSE and response streaming are one-directional (the stop would need a separate request). The team should check the WebSocket limits: 128 KB message and 32 KB frame size, a 2 hour maximum connection, a 10 minute idle timeout, and the 29-second integration timeout (the sending Lambda can keep posting chunks to the connection ID). They must also store connection IDs and handle disconnects.

    4. At 9 a.m. each day Bedrock returns ThrottlingException for a few minutes. Developers have wrapped the call in three nested retry loops, and the throttling gets worse. Explain why and give the fix.

      Answer

      Nested retries multiply load. With the SDK retrying 5 times, an application loop 3 times and a client loop 3 times, one failure becomes dozens of calls, and without jitter they arrive in synchronized waves. Keep one retry layer (the SDK in standard or adaptive mode, with exponential backoff and jitter) and have the other layers fail fast or fall back. Reduce the cause too: usage plans to limit noisy callers, a queue to flatten the peak, a cross-Region inference profile for capacity, or a quota increase.

    5. A product has a free tier and a paid tier. The paid tier should use a stronger model, and the team wants to change which model each tier uses without redeploying code. Offer two designs.

      Answer

      First, an API Gateway non-proxy integration with a mapping template that reads a header or the usage plan's tier and sets the model from a stage variable, so changing the stage variable changes the model. Second, a route table in configuration (AppConfig or an environment variable) read by the Lambda, keyed by tier. A third option is a Step Functions Choice on the tier. Log the model used for each request so cost per tier is visible.

    Chapter recap

    • Decide whether the caller waits. Synchronous for interactive calls, asynchronous (SQS, a worker, a job table) for long, bursty or unattended work. A 29-second API Gateway integration limit is not fixed by a longer Lambda timeout.
    • SQS settings that matter: visibility timeout of at least six times the function timeout, a dead-letter queue with maximum receives, partial batch responses, and a concurrency limit that keeps you under the model quota.
    • API Gateway validators with a JSON Schema model reject bad requests before any backend runs. They limit characters, not tokens.
    • Streaming improves time to first token. Use ConverseStream and a streaming path all the way to the client: API Gateway response streaming, Lambda function URL streaming, or a WebSocket for two-way chat. Errors after the first byte must be sent inside the stream.
    • Retry only retryable errors (throttling, service unavailable, timeouts, server errors), once, at one layer, with exponential backoff and jitter. Usage plans prevent one caller from causing throttling for everyone.
    • Fallback ladder: another Region, another model, a cached answer, a reduced feature, a queued job. Log which rung served each request.
    • X-Ray follows a request across API Gateway, Lambda and the model call. API Gateway tracing works for REST APIs.
    • Routing: static table, content-based (code or Step Functions Choice), metric-based (with caching and hysteresis), API Gateway mapping templates, or Bedrock intelligent prompt routing between two models of one family.

    Problem statement

    The scenario

    A company is rolling out an internal assistant to three kinds of client: a web chat for employees, a team that sends nightly report requests from a script, and a partner integration that must be kept from using more than its share.     Build an API with these properties:

    • Chat shows the first words within a couple of seconds and the reply streams until it ends.
    • Report jobs are accepted at once, run in the background at a controlled pace, and can be fetched later. A bad job does not block the others.

    • Each client has its own rate and daily quota, and a malformed request never reaches a model.
    • When the primary model throttles or fails, the user gets an answer from the next rung of a fallback ladder or a clear “we saved your request” message.
    • A single trace shows where a slow request spent its time.

    FM API interfaces: limits, streaming and timeouts (2.5.1)

    Chapter 4 covered the API plumbing. Here the exam asks a narrower question: how do you keep one request inside the limits of the model and the gateway? Three limits apply, and each has its own control.

    LimitWhat breaksControl
    Context window (input plus output tokens the model accepts)The call fails with a validation error, or the oldest content is lostCount tokens before the call and trim history. CountTokens returns the count the model would be billed for, and the call is free.
    Output lengthThe answer stops mid-sentence and the response says stopReason: max_tokensSet inferenceConfig.maxTokens on purpose, and treat a max_tokens stop as a warning in your code.
    Quota (tokens per minute) and costThrottlingException, or a bill nobody expectedPer-caller budgets at the gateway (usage plans), a character cap in the request validator, and token counts in your logs.
    Gateway time limitA 504 or a timeout while the model is still writingStream the response, or hand the job to a queue (Chapter 4).

    Walkthrough: a long chat meets the limit

    1. A support chat has run for 40 turns. The client sends the whole history plus a new question.
    2. The API Gateway validator accepts it, because a validator checks characters and shapes, not tokens.
    3. The Lambda asks CountTokens for the size of the system prompt, history and question. Suppose the answer is 9,000 tokens and your budget for input is 6,000 (made-up numbers).
    4. The function drops the oldest question-and-answer pairs until the count fits, and keeps the system prompt and the latest question. Many teams also replace the dropped turns with a short summary written by a small model, so the user does not feel the model “forgot”.
    5. It calls the model with a deliberate maxTokens. If stopReason comes back as max_tokens, the answer was cut, and the function flags it (or asks the model to continue) instead of returning half a sentence as if it were complete.
    def count_input_tokens(client, model_id: str, system: list, messages: list) -> int:
    """Ask Bedrock how many input tokens this request would use. The call is free."""
    resp = client.count_tokens(
        modelId=model_id,
        input={"converse": {"messages": messages, "system": system}},
    )
    return resp["inputTokens"]


def fit_history(client, model_id: str, system: list, messages: list, max_input_tokens: int) -> list:
    """Drop the oldest user/assistant pairs until the request fits. Keeps the newest user message.

    Assumes messages alternate user, assistant, ... and end with a user message (an odd count),
    so removing two at a time keeps the list starting with a user turn.
    """
    trimmed = list(messages)
    while len(trimmed) > 1 and count_input_tokens(client, model_id, system, trimmed) > max_input_tokens:
        trimmed = trimmed[2:]
    return trimmed


def ask(client, model_id: str, system: list, messages: list, max_output: int = 500) -> dict:
    """Call Converse with an explicit output cap and report whether the answer was cut off."""
    resp = client.converse(
        modelId=model_id,
        system=system,
        messages=messages,
        inferenceConfig={"maxTokens": max_output},
    )
    text = resp["output"]["message"]["content"][0]["text"]
    return {
        "text": text,
        "truncated": resp["stopReason"] == "max_tokens",
        "usage": resp["usage"],
    }

    Counting every turn with a network call adds latency. For a hot path, many teams count once for the full request, and fall back to a rough local estimate (characters divided by four) inside the loop. Token counting is model-specific, so count with the model you will call. Some newer models may not support CountTokens on the standard runtime endpoint, so check the current docs for your model.

    Streaming and timeouts

    Streaming through API Gateway is the answer to “the user stares at a blank screen” and to the 29-second integration limit. Chapter 4 showed the options: REST API response streaming, a Lambda function URL, a WebSocket API. For 2.5.1 the new point is what to do when the model times out.

    FailureRetry?Strategy
    ThrottlingException, ServiceUnavailableExceptionYesSDK retries in standard mode with backoff and jitter, at one layer only. Then fall back (another model or Region profile).
    ModelTimeoutException or a client read timeoutOnce, changedRetrying the same huge request tends to time out again. Retry with a lower maxTokens, a shorter prompt, or by streaming, so the read timeout applies per chunk instead of to the whole answer.
    ValidationException (input too long, bad field)NoThe request itself is wrong. Trim or fix it. Retrying wastes quota.
    stopReason: max_tokensNot an errorRaise the cap, shorten the task, or continue the answer in a second call.

    Exam tip

    “Replies are cut off” is a maxTokens and stopReason problem, not a retry problem. “Requests fail because the conversation is too long” is a token-counting and trimming problem, and a larger Lambda timeout does nothing for it. An API Gateway request validator cannot count tokens, and it is a distractor in these questions. Streaming helps time to first token and the gateway timeout, but a model that cannot finish within its limits still needs a smaller task.

    Bedrock Flows: the no-code workflow builder

    The exam names this feature Bedrock Prompt Flows. The current AWS documentation calls it Amazon Bedrock Flows, so expect either name. A flow is a graph you draw on a canvas: nodes joined by connections, where the output of one node becomes the input of the next. Analysts can build and change it without writing code, and developers invoke it like any API.

    flowchart LR
  I["Flow input node"] --> P["Prompt node: classify the ticket"]
  P --> C{"Condition node"}
  C -->|"billing"| L["Lambda function node: look up the invoice"]
  C -->|"default"| K["Knowledge base node: search help articles"]

    Two ideas make flows safe to run in production. First, you prepare the working draft to test it, then publish a version, which is an immutable snapshot. Second, an alias points to a version, and the application calls InvokeFlow on the alias. To roll back, you point the alias at the earlier version. It is the same pattern as Prompt Management in Domain 1 and Lambda aliases in Chapter 3.

    A Lambda function node is the escape hatch. Flows sends your function an event that lists the node's inputs with their resolved values, and whatever your function returns becomes the node's output. An inline code node (Python only, in preview when this was written, and not available in asynchronous runs) does small transformations without a separate function. A flow can also include a guardrail, and can run asynchronously as a flow execution for long jobs.

    A flow is a small DAG runner with a UI, similar to a Zapier or n8n workflow that is hosted for you. Versions and aliases are releases and a moving latest tag. Step Functions is the heavier tool for production orchestration. Flows is the faster tool when the chain is mostly prompts.

    “Non-developers must build the workflow” is Flows. “No-code” plus “AWS services with retries and human approval” usually pushes the answer to Step Functions Workflow Studio.     Business system enhancement: CRM, documents and Data Automation (2.5.3)

    Most enterprises do not want a new chatbot. They want the system their staff already uses (a CRM, a ticket queue, a document inbox) to do more work on its own. The pattern is always the same: an event happens in the business system, a function adds some model-generated value, and the result goes back into the system of record where the staff already look.

    Lambda to enhance a CRM

    A CRM (customer relationship management system, such as Salesforce or Dynamics) stores customers and support cases. Suppose each new case should get a short summary, an urgency level and a product tag, filled in before an agent opens it.

    flowchart LR
  CRM["CRM: case created"] -->|"webhook or partner event"| EB["EventBridge bus"]
  EB -->|"rule: case.created"| L["Lambda: enrich"]
  L -->|"Converse, JSON only"| B["Amazon Bedrock"]
  L -->|"validated fields, idempotency key"| API["CRM API"]
  L -.->|"after retries"| Q[("DLQ for review")]
  API -.->|"update event"| EB

    Walkthrough: one new case

    1. A customer opens a case. The CRM publishes an event, which EventBridge routes to the enrichment Lambda (Chapter 3 showed this front door).
    2. The function builds a prompt from the case text (cut to a safe length) and asks for JSON only.
    3. It parses and validates the reply. Urgency must be one of three words, the summary must be a short string. A reply that fails the check is not written anywhere. It goes to a review queue.
    4. It writes to fields reserved for AI output, with an idempotency key made from the case ID and version, so a retried event cannot write twice.
    5. The write itself raises an “updated” event. The rule ignores events caused by the integration user, or the function would trigger itself forever.
    import json
import os

import boto3
from botocore.config import Config

bedrock = boto3.client("bedrock-runtime", config=Config(retries={"mode": "standard", "max_attempts": 3}))
MODEL_ID = os.environ["MODEL_ID"]
INTEGRATION_USER = "ai-integration"
ALLOWED_URGENCY = {"low", "normal", "high"}
PROMPT = (
    "Read the support case and reply with JSON only, using the keys "
    '"summary" (at most 40 words), "urgency" (low, normal or high) and "product".\n\n'
    "<case>{body}</case>"
)


def enrich(case: dict) -> dict | None:
    """Return validated CRM fields, or None when the model output cannot be trusted."""
    resp = bedrock.converse(
        modelId=MODEL_ID,
        messages=[{"role": "user", "content": [{"text": PROMPT.format(body=case["description"][:8000])}]}],
        inferenceConfig={"maxTokens": 300, "temperature": 0},
    )
    text = resp["output"]["message"]["content"][0]["text"]
    try:
        data = json.loads(text)
    except json.JSONDecodeError:
        return None
    if data.get("urgency") not in ALLOWED_URGENCY or not isinstance(data.get("summary"), str):
        return None
    return {
        "ai_summary": data["summary"][:300],
        "ai_urgency": data["urgency"],
        "ai_product": str(data.get("product", ""))[:80],
    }


def handler(event: dict, context) -> dict:
    """EventBridge target: enrich a new case and write the AI fields back."""
    case = event["detail"]
    if case.get("updated_by") == INTEGRATION_USER:
        return {"skipped": "our own update"}
    fields = enrich(case)
    if fields is None:
        return {"skipped": "invalid model output"}  # in production, send to a review queue
    update_crm(case["id"], fields, idempotency_key=f'{case["id"]}:{case["version"]}')
    return {"updated": case["id"]}

    update_crm stands for your CRM's own client. The model returns JSON here because the prompt asks for it, and some models wrap it in code fences. If yours does, use structured output with a tool schema, as covered in Domain 1, and keep the validation anyway.

    Watch out

    Never let model output overwrite a field a human owns. Write to separate AI fields, validate everything, and treat the integration as a second writer that can create event loops. Credentials for the CRM belong in Secrets Manager, and the Lambda role needs only bedrock:InvokeModel on the one model.

    Bedrock Data Automation: documents in, structured data out

    The second business case is paper. Invoices, claims and application forms arrive as PDFs and scans. Amazon Bedrock Data Automation (BDA) is a managed service that turns documents, images, audio and video into structured data through one API, without you choosing a model or writing extraction prompts.     import json
import os
import time

import boto3

bda = boto3.client("bedrock-data-automation-runtime")
sfn = boto3.client("stepfunctions")
table = boto3.resource("dynamodb").Table(os.environ["TOKEN_TABLE"])


def start_extraction(event: dict, context) -> None:
    """Step Functions task: park the token first, then start the job."""
    doc = f's3://{event["bucket"]}/{event["key"]}'
    # Store the token before starting. A fast job could finish before a later write.
    table.put_item(Item={"doc": doc, "token": event["taskToken"], "expires": int(time.time()) + 7200})
    bda.invoke_data_automation_async(
        inputConfiguration={"s3Uri": doc},
        outputConfiguration={"s3Uri": f's3://{os.environ["OUT_BUCKET"]}/results/'},
        dataAutomationConfiguration={"dataAutomationProjectArn": os.environ["BDA_PROJECT_ARN"], "stage": "LIVE"},
        dataAutomationProfileArn=os.environ["BDA_PROFILE_ARN"],
        notificationConfiguration={"eventBridgeConfiguration": {"eventBridgeEnabled": True}},
    )


def on_job_finished(event: dict, context) -> dict:
    """EventBridge target for the BDA job-finished events. Resumes the waiting execution."""
    d = event["detail"]
    doc = f's3://{d["input_s3_object"]["s3_bucket"]}/{d["input_s3_object"]["name"]}'
    item = table.get_item(Key={"doc": doc}).get("Item")
    if not item:
        return {"ignored": doc}
    if d["job_status"] == "SUCCESS":
        sfn.send_task_success(taskToken=item["token"], output=json.dumps({"output": d["output_s3_location"]}))
    else:
        sfn.send_task_failure(taskToken=item["token"], error=d["job_status"], cause=d.get("error_message", ""))
    table.delete_item(Key={"doc": doc})
    return {"resumed": doc}

    The code looks the token up by the document's S3 location because the event reliably carries it. For a small volume, a simpler workflow works too: a Wait state, a Lambda that calls GetDataAutomationStatus, and a Choice that loops until the status is Success. The callback version costs less and finishes sooner at scale. It also depends on a best-effort event, which is why the state has TimeoutSeconds and a Catch.

    What “testing an AI component” means

    A GenAI app has two kinds of parts, and they need different tests. Most of the code is deterministic: the router, the token trimmer, the output validator, the retry wrapper. Test those with ordinary unit tests and a fake Bedrock client. That is where an assistant that writes tests helps. The model's behaviour is not deterministic, so it gets an evaluation set with a pass mark, run in the pipeline.

    Advanced GenAI applications: chains, agents and orchestration (2.5.5)

    Chapter 1 built single agents and multi-agent systems. This skill asks you to choose the tool when the application has several steps. Start with the shape of the work, because it decides the tool.

    Prompt chaining

    Prompt chaining splits one large task into several smaller prompts, where each output feeds the next. Small prompts are easier to test, cheaper to retry, and can use different models. AWS's own Step Functions sample for Bedrock shows the shapes you should recognise.

    Bedrock Flows as a prompt chain

    The same chain can be drawn in Bedrock Flows: a Prompt node, then another Prompt node, with an Iterator and a Collector for loops. The trade is the one from the table earlier: Flows are faster to build and easier for non-developers to change. Step Functions gives you retries per state, long waits, human approval and the full set of AWS integrations.

    Strands and Agent Squad for code-first orchestration

    When the orchestration should live in your application code, use an agent framework. Strands Agents (open source, from AWS) can model a chain as a graph: you define the nodes and edges, so the order is fixed even though each node is an agent. AWS Agent Squad is the other framework the exam names: a classifier chooses which specialist agent handles each message, and the orchestrator keeps the conversation history. Chapter 1 explained both in depth (Strands, coordination patterns).

researcher = Agent(name="researcher", system_prompt="Collect the key facts about the topic. Be brief.")

builder.add_node(writer, "write")

    Troubleshooting GenAI applications (2.5.6)

    A normal web service fails with a stack trace. A GenAI service often fails quietly: the call succeeds, the status is 200, and the answer is wrong, late, cut off or expensive. To debug that you need three kinds of evidence, and each answers a different question.

    SignalWhere it livesIt answers
    Model invocation logsCloudWatch Logs and or S3, switched on in Bedrock settings (off by default)What was sent and returned, how many tokens, which role made the call, and any tags you attached
    Bedrock metricsCloudWatch namespace AWS/Bedrock, by model IDHow many calls, how slow (InvocationLatency, TimeToFirstToken), how many errors and throttles, tokens in and out
    Your application logsCloudWatch Logs, one JSON line per requestWhich route, prompt version, fallback rung, total latency and error class: the business context Bedrock cannot know
    X-Ray tracesX-Ray, from API Gateway through Lambda to the model callWhere one slow request spent its time

    Latency is a metric and a trace, not a field of the invocation log. When a question asks “which model is slowest” the answer is metrics, or your own logs. When it asks “what exactly did we send” the answer is the invocation log.

    Invocation logs and CloudWatch Logs Insights

    With invocation logging on, each Converse, ConverseStream, InvokeModel or InvokeModelWithResponseStream call on the bedrock-runtime endpoint produces one JSON record: time, request ID, operation, model ID, the caller's identity.arn, the input and output bodies (up to 100 KB, larger ones go to S3), and the input and output token counts. Logging is set per account and Region. CloudWatch Logs Insights is the query language for the log group. It filters, sorts and aggregates JSON fields without any setup.

    You can add your own tags to each call with requestMetadata. They appear in the log record, so you can group by feature, tenant or prompt version later.

    resp = bedrock.converse(
    modelId=MODEL_ID,
    messages=messages,
    requestMetadata={"feature": "ticket-summary", "prompt_version": "v7", "tenant": "acme"},
)

    These queries cover most of what the exam and a real incident ask for. Run the first four on the invocation log group.

    # 1. Which caller used the most tokens?
fields identity.arn as principal, input.inputTokenCount as inTokens, output.outputTokenCount as outTokens
| stats sum(inTokens) as totalInput, sum(outTokens) as totalOutput, count() as calls by principal
| sort totalInput desc

# 2. Which feature (your own tag) costs the most?
filter ispresent(requestMetadata.feature)
| stats sum(input.inputTokenCount) as inTokens, sum(output.outputTokenCount) as outTokens, count() as calls by requestMetadata.feature
| sort inTokens desc

# 3. The twenty largest prompts
fields @timestamp, requestId, modelId, input.inputTokenCount as inTokens, output.outputTokenCount as outTokens
| sort inTokens desc
| limit 20

# 4. Read the exact prompt and answer for one request
fields @timestamp, modelId, input.inputBodyJson, output.outputBodyJson
| filter requestId = "REQUEST_ID"

    Run these two on your application log group. They assume your code writes JSON lines with fields named latency_ms, route, level and error_code, which are your choices to make.

    # 5. Tail latency by route
filter ispresent(latency_ms)
| stats count() as calls, avg(latency_ms) as avg_ms, pct(latency_ms, 95) as p95_ms by route
| sort p95_ms desc

# 6. Errors by type, in 15-minute buckets
filter level = "ERROR"
| stats count() as errors by error_code, bin(15m)

    Watch out

    An invocation log is a copy of every prompt and answer, which means customer data and possibly personal data. Treat the log group like a database: encrypt it with a KMS key, limit who can read it, set a short retention, and consider masking sensitive values (CloudWatch Logs has data protection policies for this, so check the current docs). Do not turn on invocation logging in a shared account without telling the people who use it.

    X-Ray for foundation model calls

    AWS X-Ray follows one request across services and draws the time spent in each as a waterfall. Turn on tracing for the API Gateway stage (REST APIs) and active tracing for the Lambda function. To see the model call itself as a segment, instrument the SDK client (the X-Ray SDK patches boto3, and Powertools for AWS Lambda wraps it in a Tracer). Then add annotations, which are indexed and searchable, for the values you filter by, and metadata for details you only read.

    from aws_lambda_powertools import Tracer

tracer = Tracer()


@tracer.capture_method
def call_model(model_id: str, messages: list) -> dict:
    """The model call appears as its own subsegment in the trace."""
    tracer.put_annotation("model_id", model_id)      # searchable: filter traces by model
    resp = bedrock.converse(modelId=model_id, messages=messages)
    tracer.put_metadata("usage", resp["usage"])      # readable on the trace, not indexed
    return resp

    A slow request then shows, for example, 8.1 seconds in total, of which 7.8 are the model segment (made-up numbers). That tells you the code is fine and the fix lies in the prompt size, the output length, streaming or the model choice. A trace with a long gap before the model segment points to a cold start or a slow lookup instead.

    Knowledge check

    1. A support chat fails with a context-length error after about 30 turns. Separately, some answers stop in the middle of a sentence. Explain each problem and the fix.

      Answer

      The failure after many turns is the input exceeding the context window. Count the tokens before the call (CountTokens, which is free), and drop or summarize the oldest turns until the request fits, keeping the system prompt and the newest message. A validator at API Gateway cannot do this because it counts characters. The mid-sentence endings are the output cap: the response has stopReason: max_tokens. Set maxTokens deliberately, check the stop reason in code, and raise the cap, shorten the task or continue the answer. Neither is fixed by a longer Lambda timeout or by retrying.

    2. Analysts want to build and change a prompt chain themselves, with versions and a safe rollback. A different team needs a workflow that waits days for a manager’s approval and retries each step on failure. Which tool fits each?

      Answer

      Bedrock Flows (Prompt Flows in the exam text) for the analysts: a visual canvas, immutable versions, and an alias that the application calls, so rollback means pointing the alias at the earlier version. Step Functions for the approval workflow: waitForTaskToken pauses without cost, and each state has retry and catch settings. A Bedrock agent is the distractor for both, because the steps are known in advance and nobody wants the model to choose them.

    3. An invoice pipeline uses Bedrock Data Automation, and only low-confidence results should go to a person. A team member points out that the EventBridge “job succeeded” event is delivered on a best-effort basis. How do you design the wait so a lost event does not hang the workflow?

      Answer

      Use a callback task: the starter function stores the task token (keyed by the document location) before it starts the job, and the EventBridge-triggered function calls SendTaskSuccess or SendTaskFailure. Put TimeoutSeconds on the task and a Catch that goes to a recovery state, and have that state call GetDataAutomationStatus to see whether the job finished anyway. For low volume, a Wait and poll loop is simpler. Branch on the minimum confidence with a Choice state, and send doubtful documents to a review queue with a second task token.

    4. A Lambda enriches each new CRM case with an AI summary and writes it back. Within an hour the function runs thousands of times for the same cases and the bill rises. What happened and what are the fixes?

      Answer

      The write-back updates the case, and the update raises an “updated” event that matches the same rule, so the function triggers itself. Fix it by filtering out events caused by the integration user (in the EventBridge rule pattern or at the top of the handler), writing only to AI-owned fields, and using an idempotency key made from the case ID and version so a repeated event does nothing. Add a DLQ and an alarm on invocation count, and validate model output before writing it.

    5. Finance asks which application used the most tokens last week. Operations says one route has slow responses. Which evidence answers each question, and which common distractor does not?

      Answer

      Tokens by caller come from model invocation logs queried in CloudWatch Logs Insights, grouping by identity.arn or by a requestMetadata tag you added. Slowness comes from InvocationLatency and TimeToFirstToken metrics by model, your own application logs (p95 by route), and an X-Ray trace that shows which segment dominates. The invocation log has no latency field. CloudTrail is the distractor: it records the API call and the caller, not the prompt, the answer or the token counts.

    6. A team asks whether Amazon Q Developer can replace their prompt evaluation suite because it generates unit tests. What do you tell them?

      Answer

      It can help write unit tests for the deterministic code: the router, the validator, the token trimmer, the retry wrapper, using a stubbed Bedrock client. It does not judge whether answers are good. For that the pipeline needs an evaluation set with a pass mark, as in Chapter 3. Generated code and tests still need a human review, and suggestions about API parameters should be checked against the current API reference. Note also that AWS has announced end of support for the Q Developer IDE plugins in April 2027.

    Chapter recap

    • Three limits shape a request: context window, output cap and quota. Count tokens before the call, trim history, set maxTokens on purpose, and read stopReason. A validator counts characters, not tokens.
    • Retry only what can succeed. A model timeout is retried once with a smaller task or by streaming, a validation error is never retried.
    • Amplify AI kit gives front-end developers conversation and generation routes backed by AppSync, DynamoDB, Lambda and Bedrock, with declarative UI components. OpenAPI-first means the contract is imported into API Gateway, so validation and docs match the API. Bedrock Flows (Prompt Flows) is the no-code canvas, with versions and aliases for safe rollout.
    • Business systems get AI through events: EventBridge to Lambda for CRM enrichment (validate output, write to AI-owned fields, prevent event loops), and Bedrock Data Automation plus Step Functions for documents (blueprints, confidence scores, callback tasks, human review).
    • Q Developer speeds up developers: code, tests, API assistance and performance hints. It does not run your application's model, and it does not replace an evaluation set. Its IDE plugins have an announced end-of-support date.
    • Choose orchestration by who decides the next step. The designer decides: Step Functions, Flows, a Strands graph. The model decides: an agent. Many specialist agents behind one chat: Agent Squad.
    • Debug with four signals: invocation logs (what and who, with Logs Insights), AWS/Bedrock metrics (how slow and how often), your own structured logs (route, version, stop reason), and X-Ray (where the time went). Tag calls with requestMetadata. Protect the invocation log like a database.

    Problem statement

    The scenario

    An insurer registers claims in a twenty-year-old system. The system has no modern API. It can send an HTTP webhook with a signed header when a claim is registered, and it can accept updates through a small partner endpoint. Claimants attach PDFs of forms and receipts. Adjusters spend the first hour of each claim retyping fields and writing a first summary. Two other teams already want to use models too, and the security team has said that no application gets its own Bedrock permissions again.

    Build a system with these properties:

    • A registered claim triggers processing within a minute, and a replayed webhook never creates a second run.
    • Fields are extracted from the attached document. Only low-confidence extractions reach a person.
    • A short assessment summary and a draft claimant letter are produced by a chain of prompts, with a checker that can send a draft back once.
    • Results are written to AI-only fields of the claim, and the update never triggers another run.
    • Only the gateway’s role can invoke models, and it can only do so with the company guardrail. The workflow and the adapter are refused if they try.
    • A change to code or prompts is shipped only if it passes tests and an evaluation set, and it rolls back if an alarm fires.
    • For any claim, you can find what was sent to the model, what came back, how many tokens it used, and which team used them.

    The seven lines map to Tasks 2.3 and 2.5 in order. Use synthetic claims only. Invocation logs hold full prompts, so no real personal data belongs in this project.

    A fourth, separate project that joins the three. A support agent answers staff questions through a streaming chat API (P2). It calls tools through MCP with human approval for risky actions (P1). Customer documents arrive through an event-driven extraction pipeline and are reached only through a governed model gateway, with logging and a release pipeline (P3). The point is to see the same ideas working together, not to add new features.

    The repository's rule is that each project is independent and has its own dependencies and infrastructure. For the capstone, copy the few modules you need (the tool functions, the router, the gateway) into the new folder and keep them as local code. Do not import across project folders. If you copy the same module a third time, that is the point to consider a shared package, and not before.

    Build it in slices: the chat path with the router first, then the agent with one tool, then the approval step, then the document pipeline, and the gateway and pipeline last. Deploy to a sandbox account, delete it when you finish, and keep the cost notes from each workshop in view.

    Exam tip

    After each project, write a three-line summary of the decisions you made and the reason for each, for example "put the approval step in Step Functions because the wait can last days and Lambda cannot hold it". Exam scenarios reward constraint-driven reasoning, and your own build history gives you real examples to recall under pressure.
