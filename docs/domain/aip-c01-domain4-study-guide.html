    Chapter 1 · Task 4.1

    Implement Cost Optimization and Resource Efficiency Strategies

    A GenAI feature that works in a demo can still fail in production because it costs too much per request. Unlike a classic web service, the dominant cost is not servers but tokens, and every design choice (prompt size, model, caching, capacity mode) moves the bill directly. This chapter shows where the money goes, how to measure it, and the four levers the exam tests: token efficiency, model selection, throughput and capacity, and caching.

    Exam skills covered

    • 4.1.1 Token efficiency: estimation and tracking, context window optimization, response size controls, prompt compression, context pruning
    • 4.1.2 Cost-effective model selection: cost-capability trade-offs, tiered FM usage by query complexity, price-to-performance measurement
    • 4.1.3 High-performance FM systems: batching, capacity planning, utilization monitoring, auto-scaling, provisioned throughput
    • 4.1.4 Intelligent caching: semantic caching, result fingerprinting, edge caching, deterministic request hashing, prompt caching

    Where the money goes in a GenAI application

    Picture a Monday-morning finance message: the support assistant that cost 200 dollars a week during the pilot cost 9,000 dollars last week. Nothing was hacked. Traffic grew 10 times, but each request also grew, because someone added the full policy manual to the system prompt and the chat history was never trimmed. Cost per request is the product of two things: how many tokens go in and out, and the price per token of the model that processes them. Everything in this chapter attacks one of those two factors, or avoids the call entirely.

    You already know tokens, on-demand billing, and quotas from the Domain 1 orientation on billing modes and tokens and quotas. Two facts from there matter most here. Bedrock on-demand charges separately for input tokens and output tokens, and output tokens cost a multiple of input tokens (check the Amazon Bedrock pricing page for the current ratio on your model). And the price per token differs by an order of magnitude between a small model and a frontier model. That gives a simple formula to keep in mind:

    cost_per_request = (input_tokens  * input_price)
                 + (output_tokens * output_price)
                 + (cache_write_tokens * cache_write_price)
                 + (cache_read_tokens  * cache_read_price)

monthly_cost = cost_per_request * requests_per_month   (on-demand)
             = model_units * hourly_rate * hours        (provisioned throughput)

    Each term maps to a lever. Prompt compression and context pruning reduce input_tokens. Response limits reduce output_tokens. Model tiering reduces the price terms. Caching converts expensive input tokens into cheap cache reads, or removes the request altogether. Capacity choices (on-demand, batch, provisioned) change the shape of the formula itself.

The sections below follow that order of leverage, but we start with measurement, because you cannot trim what you cannot see.

    Exam tip

    Cost questions usually give a symptom (high bill, throttling, repeated identical questions, a huge static prompt) and ask for the single change with the best cost reduction and the least quality risk. Match the symptom to the lever: repeated static prefix means prompt caching, repeated similar questions means semantic caching, simple questions on an expensive model means tiered routing, nightly bulk work means batch inference, steady high volume means provisioned throughput.

    Token efficiency (Skill 4.1.1)

    Token efficiency means spending tokens only on content that changes the answer. It has four parts: estimating tokens before the call, tracking them after, shrinking what you send, and bounding what comes back.

    Estimating and tracking tokens

    There are three places to learn a token count, each useful at a different time.

    • Before the call, locally. A rough rule for English prose is about four characters per token, but the real tokenizer differs by model and by language, and code or non-English text can use noticeably more tokens. A local estimate is fine for guarding obviously oversized inputs. Do not use it for billing numbers.
    • Before the call, from AWS. Bedrock offers a token-counting operation (CountTokens in the bedrock-runtime client, available as count_tokens in recent Boto3 versions for supported models). It returns the input token count that the model would be charged for, without running inference. Check that your model and Boto3 version support it, and fall back to the local estimate if not.
    • After the call, exact. Every Converse response includes a usage object with inputTokens, outputTokens, and totalTokens, plus cacheReadInputTokens and cacheWriteInputTokens when caching is in play. This is the source of truth for per-request cost.

    A small helper turns the usage object into a dollar figure and a CloudWatch custom metric. Prices are passed in as configuration, because rates change and differ per model. The numbers in the example are placeholders. Look up current rates on the Bedrock pricing page.

    import time
import boto3

bedrock = boto3.client("bedrock-runtime")
cloudwatch = boto3.client("cloudwatch")

# Example placeholder rates in USD per 1,000 tokens. Replace from the pricing page.
PRICES = {
    "small":  {"in": 0.0002, "out": 0.0010, "cache_read": 0.00002, "cache_write": 0.00025},
    "large":  {"in": 0.0030, "out": 0.0150, "cache_read": 0.00030, "cache_write": 0.00375},
}

def call_and_track(tier: str, model_id: str, system: str, user: str, max_tokens: int = 400):
    started = time.time()
    resp = bedrock.converse(
        modelId=model_id,
        system=[{"text": system}],
        messages=[{"role": "user", "content": [{"text": user}]}],
        inferenceConfig={"maxTokens": max_tokens, "temperature": 0.2},
    )
    u = resp["usage"]
    p = PRICES[tier]
    cost = (
        u["inputTokens"] * p["in"]
        + u["outputTokens"] * p["out"]
        + u.get("cacheReadInputTokens", 0) * p["cache_read"]
        + u.get("cacheWriteInputTokens", 0) * p["cache_write"]
    ) / 1000

    cloudwatch.put_metric_data(
        Namespace="GenAIApp/Cost",
        MetricData=[
            {"MetricName": "RequestCostUSD", "Value": cost, "Unit": "None",
             "Dimensions": [{"Name": "Tier", "Value": tier}]},
            {"MetricName": "OutputTokens", "Value": u["outputTokens"], "Unit": "Count",
             "Dimensions": [{"Name": "Tier", "Value": tier}]},
        ],
    )
    return resp["output"]["message"]["content"][0]["text"], cost, time.time() - started

    Publishing the cost as a custom metric means you can graph cost per request, set an alarm on it, and slice it by tier or feature using ordinary CloudWatch tools. Chapter 3 returns to this idea in depth (custom metrics and dashboards).

    Context window optimization and context pruning

    The context window is the maximum number of tokens (input plus output) a model accepts. A bigger window is a capability, not a target. Every token you place in it is billed on every call, and long contexts also slow the response. Several patterns keep the window lean.

    • Sliding window with summary. Keep the last N turns verbatim and replace older turns with a short running summary produced by a small, cheap model. The summary costs a few hundred tokens once instead of thousands of tokens on every later turn.
    • Retrieve less, retrieve better. In RAG, passing ten chunks of 1,000 tokens "just in case" means 10,000 input tokens per question. Reducing numberOfResults, adding a reranker to keep only the top few (see hybrid search and reranking), and using smaller chunks all cut input tokens while often improving answer quality.
    • Context pruning. Drop content that cannot affect the answer: boilerplate email footers, repeated headers, tool results fields the model never uses, whitespace. For tool-heavy agents, return only the fields the model needs from a tool instead of the entire JSON document.
    • Pass references, not payloads. If a step only needs to know that a document exists, pass its ID and fetch details on demand with a tool call.

    Prompt compression

    Prompt compression rewrites instructions and examples into fewer tokens with the same meaning. Practical techniques: remove politeness and repetition from system prompts, replace five few-shot examples with two representative ones (measure the quality change), use compact structured formats (a short schema description instead of prose), and abbreviate repeated field names in data you inject. More automated approaches use a small model to summarize or extract the relevant sentences from a long document before it reaches the expensive model. This is a trade: you pay for the small-model call and risk losing a detail, so evaluate on a golden set before adopting it.

    Response size controls

    Output tokens are the more expensive direction, and a model left alone will often write more than needed. You have four controls:

    • inferenceConfig.maxTokens hard-caps output. The cap truncates mid-sentence, so set it from observed data, such as the 99th percentile of OutputTokenCount plus margin, not from a guess.
    • Instruct the format: "Answer in at most three sentences", "Return JSON with only these keys". This shortens answers without truncation.
    • stopSequences ends generation when a delimiter appears, useful for structured extraction.
    • Prefer structured output over prose when downstream code consumes it. A JSON object with four fields is shorter than an explanation paragraph.

    Watch out

    maxTokens also affects throttling. Bedrock reserves quota at the start of a request using input tokens plus maxTokens. If you leave maxTokens unset, the reservation can be the model's maximum output length (tens of thousands of tokens), so a few concurrent requests consume your tokens-per-minute quota and you see ThrottlingException at modest traffic. Always set it explicitly. A smaller maxTokens is a cost control and a capacity control at once.

    Backend analogy

    Think of tokens as bytes over a metered network link and the context window as your response payload size. You would not return an entire database table from an API endpoint "just in case" and you would paginate or select columns. Pruning and response limits are the same discipline, applied to the model's input and output.

    A token budget enforced in code

    A budget guard sits in front of the call and decides what to do when the request is too big: trim history, reduce retrieved chunks, or reject. The example shows a simple version using a conservative character-based estimate.

    def estimate_tokens(text: str) -> int:
    # Rough guard only. Use usage from the response for real accounting.
    return max(1, len(text) // 4)

def fit_to_budget(system: str, history: list[dict], chunks: list[str],
                  question: str, input_budget: int = 6000) -> tuple[list[dict], list[str]]:
    fixed = estimate_tokens(system) + estimate_tokens(question)
    # 1) Drop retrieved chunks from the tail (lowest ranked) first.
    kept_chunks = list(chunks)
    while kept_chunks and fixed + sum(map(estimate_tokens, kept_chunks)) > input_budget:
        kept_chunks.pop()
    # 2) Then drop the oldest history turns.
    kept_history = list(history)
    def total():
        return (fixed + sum(map(estimate_tokens, kept_chunks))
                + sum(estimate_tokens(m["content"][0]["text"]) for m in kept_history))
    while kept_history and total() > input_budget:
        kept_history.pop(0)
    return kept_history, kept_chunks

    Cost-effective model selection (Skill 4.1.2)

    Model choice is the biggest single price lever. Within one provider family, the large model can cost ten times or more per token than the small one. Yet most real traffic is easy: classify this ticket, extract these fields, answer a question whose answer is in the retrieved text. Sending all of it to your most capable model is like running every cron job on the biggest instance in the fleet. The goal is the cheapest model that meets your quality bar for each class of request, which you establish by measurement, not intuition.

    Measuring price-to-performance

    Build a golden set (30 to 200 representative inputs with reference answers or a scoring rubric), run each candidate model on it, and record quality score, average input and output tokens, latency, and cost per request. The useful number is cost per acceptable answer: cost per request divided by the fraction of answers that pass your quality bar. A cheap model with a 60% pass rate and a retry on failure can cost more than a mid-priced model that passes 95%. Bedrock Evaluations and LLM-as-a-judge (covered in Domain 5) automate the scoring, but a simple script with a rubric and a judge prompt is enough to start. Record the comparison in a table that you can show an architect:

    Tiered model usage by query complexity

    A tiered design sends each request to the cheapest tier likely to answer it, and escalates only when needed. There are three common ways to decide.

    • Rule-based routing. Use known attributes: request type, input length, customer plan, whether the user clicked "deep analysis". It is cheap, deterministic, and easy to test. Start here.
    • Classifier routing. A small, cheap model (or a fine-tuned classifier) labels the query as simple, standard, or complex, and the label picks the tier. You pay a small classification cost on every request, so the saving must exceed it.
    • Cascade with confidence check. Try the small model first and escalate to a bigger model if a validator fails: the answer is not valid JSON, a grounding check fails, the model says it is unsure, or a score from a judge falls below a threshold. Cascades cost more on hard queries (you paid for both calls), so they work when most queries succeed at the first tier.

    A minimal router with escalation looks like this. The model IDs come from configuration (see switching models without code changes), and the validator is whatever cheap check suits your output.

    import json, boto3

bedrock = boto3.client("bedrock-runtime")

TIERS = ["small", "mid", "large"]            # ordered cheapest to most capable
MODEL_FOR = {                                 # load from AppConfig or env in real code
    "small": "us.example.small-model-v1:0",   # example values, look up real IDs in your Region
    "mid":   "us.example.mid-model-v1:0",
    "large": "us.example.large-model-v1:0",
}

def choose_start_tier(question: str, doc_tokens: int) -> str:
    if doc_tokens > 20000 or "compare" in question.lower() or "why" in question.lower():
        return "mid"
    return "small"

def is_valid(text: str) -> bool:
    try:
        data = json.loads(text)
        return "answer" in data and "confidence" in data and data["confidence"] >= 0.6
    except (ValueError, TypeError):
        return False

def answer(question: str, context: str, doc_tokens: int) -> dict:
    start = TIERS.index(choose_start_tier(question, doc_tokens))
    for tier in TIERS[start:]:
        resp = bedrock.converse(
            modelId=MODEL_FOR[tier],
            system=[{"text": "Reply as JSON: {\"answer\": str, \"confidence\": 0..1}."}],
            messages=[{"role": "user", "content": [{"text": f"Context:\n{context}\n\nQ: {question}"}]}],
            inferenceConfig={"maxTokens": 300, "temperature": 0},
        )
        text = resp["output"]["message"]["content"][0]["text"]
        if is_valid(text) or tier == TIERS[-1]:
            return {"tier": tier, "result": text, "usage": resp["usage"]}

    Managed routing and cheaper modes of the same model

    Bedrock also offers Intelligent Prompt Routing, a managed feature that routes each request between two models of the same family (for example a larger and a smaller one) based on predicted answer quality, using a default or configured prompt router that you call by its ARN in place of a model ID. It saves you writing the router, but it only chooses within the supported families and you cannot inspect its rules, so confirm the supported models and Regions in the documentation and measure the result on your golden set.

    Two other price levers apply to the same model and are exam favorites:

    • Batch inference. For work that does not need an immediate answer (nightly summarization, back-filling classifications), you submit a file of requests as a batch job and receive results later, at a discounted price compared with on-demand. Check the pricing page for the current discount and the supported models.
    • Service tiers. On supported models, the on-demand service tier can be chosen per request: Priority (faster, premium price), Standard (default), and Flex (discounted, may queue at peak). Flex fits background and evaluation workloads. Priority fits latency-critical user flows. Availability varies by model and Region, so verify before designing around it.

    A third lever, model distillation and fine-tuning, trains a small model to imitate a larger one on your task so you can serve the small one. It pays back only at high, stable volume and needs a data pipeline and evaluation, so treat it as a later optimization, and see customization in Chapter 1.2 of Domain 1 for the mechanics.

    Exam tip

    "Reduce cost without a noticeable drop in quality for a mix of simple and complex questions" points to tiered routing or Intelligent Prompt Routing. "Process millions of documents overnight at the lowest cost" points to batch inference. "Cheaper, but the user still waits" points to a smaller model, not batch. Watch for distractors that propose provisioned throughput for spiky, low-volume traffic, which costs more.

    Throughput, capacity, and utilization (Skill 4.1.3)

    Once the per-request cost is under control, the next question is how to buy capacity. Bedrock gives you several ways, and the right one depends on how steady, bursty, and latency-sensitive your traffic is. The billing modes section introduced them. Here is how to choose with cost in mind.

    ModeYou payCapacity behaviorBest for

    Cross-Region inference profileOn-demand priceRequests spread across Regions for more burst headroomBursty traffic and throttling relief, with geographic profiles when residency matters

    When provisioned throughput pays off

    Provisioned Throughput bills by the hour whether you use it or not. It is therefore a utilization bet. Compute the break-even: take the hourly cost of the model units you would need and divide by the on-demand price per token to find the tokens per hour at which they are equal. If your sustained traffic is above that, provisioned is cheaper. If traffic is spiky and often idle, you pay for empty capacity. You would also need to call the model through the provisioned model ARN, and a model unit is tied to one model, so changing models means buying again.

    # Break-even sketch with EXAMPLE numbers. Use real rates from the pricing page.
units_hourly_cost = 40.0            # USD per hour for the model units you would need (example)
on_demand_in, on_demand_out = 0.003, 0.015   # USD per 1K tokens (example)
avg_in, avg_out = 1200, 300         # tokens per request, from your usage logs

cost_per_request = (avg_in * on_demand_in + avg_out * on_demand_out) / 1000
break_even_requests_per_hour = units_hourly_cost / cost_per_request
print(f"Provisioned wins above {break_even_requests_per_hour:,.0f} requests/hour sustained")
# Compare this with your p50 and p95 hourly request counts from CloudWatch.
# If p95 is above break-even but p50 is far below, consider on-demand plus cross-Region profiles instead.

    Batching strategies

    There are two different "batching" ideas, and the exam uses both words. Batch inference jobs (the Bedrock feature, create_model_invocation_job in the bedrock client) take a JSONL file of requests in S3 and write results back to S3, at a discounted price, with no latency guarantee. Application-level batching groups work yourself: combine several small classification items into one prompt that returns a JSON array, which saves the repeated cost of a long shared instruction, or embed 100 texts in a loop on a worker to smooth load. Batching items in one prompt trades per-item isolation for lower cost, so keep the group small enough that the model does not lose items, and validate that the output array length matches.

    Capacity planning and utilization monitoring

    Capacity planning for GenAI is token arithmetic, not CPU arithmetic. Estimate peak requests per minute, multiply by average input plus output tokens (using maxTokens for the reservation), and compare with your model's tokens-per-minute quota from Service Quotas. Quota consumption is more subtle than a simple sum: Bedrock reserves quota at request start from input tokens plus maxTokens and settles to actual use afterward, cache reads do not count against token quotas, and some models count output tokens with a burndown multiplier. Check the quota page for your model for the exact rule. Monitor utilization with the AWS/Bedrock CloudWatch metrics: Invocations, InputTokenCount, OutputTokenCount, InvocationThrottles, and InvocationLatency, dimensioned by ModelId. Alarm on InvocationThrottles greater than zero, and on token usage reaching, for example, 70% of quota, so you request increases (review takes days) before users feel it.

    The app tier needs scaling too. If your service runs on ECS on Fargate, use target tracking auto scaling on a metric that reflects load (CPU is a poor proxy when tasks mostly wait on model calls, so prefer requests per target or a custom metric such as in-flight model calls). For Lambda, use reserved concurrency to cap the number of simultaneous model calls so a traffic spike cannot exhaust your Bedrock quota. For asynchronous work, place an Amazon SQS queue between producers and workers and scale workers on queue depth, which smooths bursts and keeps token use within quota. Chapter 2 treats resource allocation and auto-scaling in more detail.

    Watch out

    Provisioned Throughput starts billing when it becomes active and continues until you delete it, and commitment terms cannot be cancelled early. A forgotten model unit left running after a lab is a classic surprise bill. Never create one in a learning account without a plan and a reminder to delete it, and check the pricing page for the minimum term before you click.

    Intelligent caching (Skill 4.1.4)

    The fastest and cheapest model call is the one that never happens. GenAI traffic has more repetition than it first appears: the same FAQ asked in slightly different words, the same long system prompt on every call, the same document summarized by many users. Caching exploits that repetition, but "cache" means different things at different layers, and the exam expects you to pick the right layer. There are five, ordered here from the edge of your system toward the model.

    Prompt caching in Bedrock

    With prompt caching, Bedrock stores the processed form of the beginning of your prompt, so later requests that start with the identical text skip reprocessing it. You still get a fresh answer each time. It is ideal when a large, stable prefix precedes a small variable part: a long system prompt, tool definitions, few-shot examples, or a reference document that many questions are asked against. You mark where the cacheable prefix ends by inserting a cachePoint content block after the content to cache.

    import boto3
bedrock = boto3.client("bedrock-runtime")

POLICY_MANUAL = open("policy_manual.txt").read()   # large, stable text, well above the model's minimum

def ask(question: str):
    resp = bedrock.converse(
        modelId="us.example.cache-capable-model-v1:0",   # example. Use a model that supports caching
        system=[
            {"text": "You answer questions using only the policy manual below."},
            {"text": POLICY_MANUAL},
            {"cachePoint": {"type": "default"}},          # everything above this line is cached
        ],
        messages=[{"role": "user", "content": [{"text": question}]}],   # variable part comes after
        inferenceConfig={"maxTokens": 400, "temperature": 0},
    )
    u = resp["usage"]
    print("write:", u.get("cacheWriteInputTokens", 0), "read:", u.get("cacheReadInputTokens", 0))
    return resp["output"]["message"]["content"][0]["text"]

ask("How many vacation days do new hires get?")   # first call: cacheWriteInputTokens > 0
ask("What is the expense approval limit?")        # second call within TTL: cacheReadInputTokens > 0

    The key facts, which the exam and real debugging both depend on:

    • Economics. A cache write costs more than a normal input token (about 25% more on models that document it) and a cache read costs far less (about 90% less). The first request in a window therefore costs more, so caching needs at least two requests inside the time to live (TTL) to break even, and savings grow with more reuse. Do not cache single-use content. Confirm the exact rates on the pricing page.
    • TTL. The default is 5 minutes, refreshed each time the cache is read. Some models also support a 1-hour TTL (add "ttl": "1h" to the cache point). When you mix TTLs, longer ones must come first. Check the model card for support.
    • Minimum size. The text before a cache point must exceed a model-specific minimum, roughly 1,000 to 4,000 tokens depending on the model. Below it, the cache point is silently ignored. Look up the minimum on the model's card.
    • Exact prefix match. A timestamp, request ID, reordered JSON key, or extra space before the cache point changes the prefix and produces a new write every time (cache fragmentation). Put anything dynamic after the cache point.
    • Quota benefit. Tokens read from the cache do not count toward the token quota, so caching also raises your effective throughput.
    • Where to verify. The usage object in the response (cacheWriteInputTokens, cacheReadInputTokens) and the matching AWS/Bedrock CloudWatch metrics. If both are zero, the model does not support caching or the prefix is below the minimum.

    Agents and Knowledge Bases can use prompt caching as well, for supported models, which is useful because agent prompts carry long tool schemas. Check the current feature page for the exact configuration on those services.

    Backend analogy

    Prompt caching is like a database prepared statement or a warmed JIT: the expensive parse of a repeated prefix is done once and reused, while the parameters (the user question) vary. A semantic cache is closer to a full response cache like Redis in front of an API, except the key is fuzzy.

    Deterministic request hashing (exact-match cache)

    If the same request, with the same model and prompt version, always has an acceptable answer, store it. Build a key from everything that influences the output: model ID, prompt template version, normalized user input, retrieved document IDs, and inference parameters. Hash it (SHA-256), look it up in Amazon DynamoDB (with a TTL attribute for automatic expiry) or Amazon ElastiCache, and call the model only on a miss. Normalization (lowercase, collapse whitespace, strip punctuation where it does not change meaning) raises the hit rate. This only makes sense when the output is stable enough to reuse, so it works best with temperature 0 and questions that do not depend on live data.

    import hashlib, json, time
import boto3

table = boto3.resource("dynamodb").Table("genai-response-cache")   # partition key: cache_key (S), TTL attribute: expires_at

def request_key(model_id: str, prompt_version: str, question: str, doc_ids: list[str], params: dict) -> str:
    normalized = " ".join(question.lower().split())
    payload = json.dumps(
        {"m": model_id, "p": prompt_version, "q": normalized, "d": sorted(doc_ids), "i": params},
        sort_keys=True, separators=(",", ":"),
    )
    return hashlib.sha256(payload.encode()).hexdigest()

def cached_answer(key: str, compute, ttl_seconds: int = 3600):
    item = table.get_item(Key={"cache_key": key}).get("Item")
    if item and item["expires_at"] > time.time():
        return item["answer"], True
    answer = compute()
    table.put_item(Item={"cache_key": key, "answer": answer, "expires_at": int(time.time()) + ttl_seconds})
    return answer, False

    The key must also include anything that makes the answer user-specific. If two users have different permissions on documents, a shared cache key that ignores identity can return one user's data to another, which is a security incident, not a cost saving. Include the tenant or the permission group in the key, or cache only the retrieval-independent parts.

    Semantic caching

    An exact-match cache misses "How do I reset my password?" versus "I forgot my password, how to reset it". A semantic cache embeds the incoming question (see embeddings), searches a vector index of previously answered questions, and returns the stored answer if the nearest neighbor's similarity exceeds a threshold. The embedding call is far cheaper than a generation call, and the vector search is fast, so a hit saves most of the cost and latency.

    You can build the index on Amazon OpenSearch Service or Aurora PostgreSQL with pgvector (both covered in vector search), or use an in-memory store with vector search support, such as Amazon MemoryDB or ElastiCache (check the current engine and version support), for lower lookup latency. Choose by latency need and what you already operate. The important tuning is the threshold. Too low and you return the answer to a different question ("cancel my order" versus "cancel my subscription"), too high and the hit rate collapses. Pick it by labeling a sample of near-duplicate and near-miss question pairs, then measure false-hit rate, not just hit rate. Partition the cache by tenant, language, and prompt version, expire entries with a TTL, and exclude personalized or time-sensitive questions entirely.

    Result fingerprinting

    Fingerprinting avoids repeating expensive work on unchanged inputs. Hash the content of a document (or its S3 ETag or version ID) together with the prompt version and model ID, and store the result (a summary, extracted fields, an embedding) under that fingerprint. When a pipeline sees the same document again, it skips the model call. When either the document or the prompt version changes, the fingerprint changes and the work reruns. This is the same idea as build caching keyed on file content, and it makes re-ingestion jobs and retries nearly free.

    Edge caching

    When responses are identical for many users (a public product FAQ answer, a static summary), cache at the edge so requests never reach your compute. Amazon CloudFront can cache API responses by path and query string, and API Gateway REST APIs have an optional stage-level cache with a configurable TTL. For authenticated or personalized endpoints, make sure the cache key includes what makes responses differ, or do not cache at the edge. Edge caching removes both model cost and your own compute cost, and cuts latency to a few milliseconds. It is the right choice only for responses that are truly shared.

    Invalidation and consistency

    Every cache needs an answer to "when is this wrong?". Use TTLs that match how fast the underlying facts change. Include a content or prompt version in the key so a prompt change or a document update naturally misses the old entries. For knowledge-base-backed answers, invalidate or version the cache when you re-ingest documents (see vector store maintenance). Log hit, miss, and false-hit counts as metrics so you can see whether the cache is helping.

    Exam tip

    Prompt caching reuses the input processing of a stable prefix but still generates a new answer. Semantic and exact-match caches reuse the answer and skip the model. If the scenario says "users ask the same question in different words", it is a semantic cache. If it says "the same long instructions precede every request", it is prompt caching. A cache write costs more than a normal input token, so one-off prompts should not use it.

    Chapter recap

    • Cost per request is tokens times price, so every optimization reduces tokens, lowers the price per token, or avoids the call.
    • Track tokens from the usage object in each Converse response, publish them as custom CloudWatch metrics, and treat local estimates as guards only.
    • Trim context with summaries, fewer and better retrieved chunks, and pruning. Always set maxTokens, which both caps output cost and avoids over-reserving quota.
    • Use the cheapest model that passes your quality bar: rule or classifier routing, cascades with validators, Intelligent Prompt Routing, batch inference, and service tiers.
    • On-demand suits spiky traffic, cross-Region profiles add burst headroom, batch suits offline work, and Provisioned Throughput pays off only at high sustained utilization.
    • Prompt caching needs a stable exact prefix above the model minimum and at least two hits per TTL. Exact-match and semantic caches reuse whole answers. Fingerprints and edge caches avoid repeated work earlier.
    • Use application inference profiles with cost allocation tags, Budgets, and Cost Anomaly Detection to attribute and govern spend.

    Knowledge check

    1. A document Q&A service prepends the same 8,000-token policy manual to every request. Questions vary. The monthly bill is high, and latency is noticeable. Which change gives the largest saving with the least risk to answer quality?

      Answer

      Enable prompt caching: put the manual before a cachePoint and the question after it. Cache reads are far cheaper and faster than reprocessing 8,000 tokens each time, and answers are still generated fresh. A semantic cache would risk returning the wrong stored answer, switching to a smaller model risks quality, and provisioned throughput does not lower per-token cost for a variable workload.

    2. Users rephrase the same few hundred support questions thousands of ways, and answers rarely change. Which caching approach fits best?

      Answer

      A semantic cache keyed on embeddings with a tuned similarity threshold and TTL. Exact-match hashing would almost never hit because the text differs, prompt caching still calls the model every time, and edge caching only works if the request URLs repeat and responses are shared.

    3. A team calls a model without setting maxTokens and sees ThrottlingException at modest traffic although token usage is far below quota. What is the most likely cause and fix?

      Answer

      Quota is reserved at request start from input tokens plus the maximum output tokens, and an unset maxTokens can default to a very large value, so few concurrent requests reserve the whole quota. Set maxTokens to a realistic value. Buying Provisioned Throughput or asking for a quota increase treats the symptom and costs more.

    4. A company must classify 5 million archived emails by next week. Results are not needed immediately, and cost should be minimal. What should they use?

      Answer

      Bedrock batch inference, submitting a JSONL file from S3 as a model invocation job at the discounted batch price. On-demand calls cost more, Provisioned Throughput bills hourly even when idle, and a semantic cache does not help unique emails.

    5. Eighty percent of queries are simple FAQ lookups and twenty percent need multi-step reasoning. All go to the largest model. How do you cut cost while protecting quality on hard queries?

      Answer

      Tier the models: route simple queries to a small model, and escalate to a larger one by a classifier or a validation failure, or use Intelligent Prompt Routing for a supported family. Validate the quality mix on a golden set. Using only the small model would hurt the hard queries, and caching alone would not help unique queries.

    6. Finance wants to know separately what the support bot and the search feature cost in Bedrock each month, with both calling the same model. What is the best approach?

      Answer

      Create an application inference profile for each feature, tag them (for example Project), activate the tags as cost allocation tags, and call each profile ARN as the model ID. Cost Explorer then groups spend by tag. IAM principal attribution only shows who called, not which feature, and invocation logs need custom analytics. Tags take about a day to appear after activation.

    Project 1: A cost-aware GenAI gateway

    Problem statement

    The scenario

    A retail bank runs a customer help assistant that answers questions about cards, fees, and transfers. It launched on one large model with a long system prompt, the full chat history on every turn, and no limit on answer length. Usage tripled in a quarter and the monthly Bedrock bill went from a rounding error to a line item that finance asked about. A review of one week of invocation logs found three patterns. About 60 percent of questions are simple lookups ("what is the overseas ATM fee?") that a small model answers equally well. About a third of all questions are near-duplicates of a short list of popular ones. Every request resends a 3,000-token system prompt and policy preamble, and long conversations carry the whole transcript. The bank wants the bill cut without a visible drop in answer quality. Requirements:

    • Every request has a token budget: the gateway estimates input tokens before the call, prunes history to fit, and sets maxTokens per route. Requests that cannot fit are rejected with a clear message and no model call.
    • A router classifies each request as simple, standard, or complex and sends it to a small, mid, or large model. The routing rules are data (a config file or AppConfig profile), not code.
    • The static part of the prompt is served from Bedrock prompt caching, and the gateway reports cache write and read tokens for every call.
    • Exact repeats (same normalized question, same model, same parameters) are answered from a response cache with a time to live. Near-duplicates are answered from a semantic cache with a similarity threshold, and a tenant or product scope so one customer's answer never reaches another.
    • Every request is tagged with a feature and tier so costs can be attributed, and a script produces a cost report: spend by tier, cache hit rates, tokens saved, and cost per 1,000 requests before and after.
    • A nightly job that summarizes the previous day's transcripts runs as a Bedrock batch inference job, not as live calls.
    • A replay test sends a fixed set of at least 200 historical questions through the baseline path and the optimized path, and compares cost and answer quality. The optimized path must cost at least 40 percent less (pick your own target) with a quality score no more than an agreed margin lower.

    Build the gateway that sits in front of Bedrock and enforces all of this in code and configuration, with metrics that prove the savings.

    The exam phrases this as "the company wants to reduce inference cost without changing the application", "most requests are repetitive", "a small percentage of queries need the most capable model", or "the same long system prompt is sent with every request". Each phrase points at one lever here. Prompt caching is the answer when a large static prefix repeats. A response or semantic cache is the answer when whole questions repeat. Tiered routing is the answer when difficulty varies. Batch inference is the answer when nobody waits for the result. The best answer under a cost constraint usually combines two of these, and it never trades away a stated quality or safety requirement.

    A request passes through four cheap decisions before it can spend a token. The budget step counts input tokens. Use the CountTokens operation of the Bedrock Runtime API where your model supports it, and fall back to a characters-divided-by-four estimate with a safety margin where it does not. Then it prunes: it keeps the system prompt, the latest turns, and a running summary in place of older turns, until the total fits the route's input budget. It also sets maxTokens to the route's answer limit. The exact cache normalizes the question (trim, lowercase, collapse whitespace), builds a key from the normalized text, the model ID, the system prompt version, and the inference parameters, hashes it with SHA-256, and looks it up in a key-value store with a time to live. Including the prompt version in the key is what keeps stale answers from surviving a prompt change. The semantic cache embeds the question with a Titan or Cohere embedding model on Bedrock, searches a small vector index for the nearest earlier question within the same scope, and returns the stored answer only when similarity is above a threshold you tuned on the replay set. The router only runs on a double miss.

    The router has two parts. A rules stage handles obvious cases without a model: a short question that matches a known intent goes to the small tier, and a message that contains an attachment or a request to compare options goes to the large tier. A classifier stage handles the rest with one cheap call to the smallest model that returns a single label, with maxTokens of a few tokens. The tier then chooses the model ID, the answer limit, and whether the call uses a cachePoint after the system prompt and policy preamble. On a cache write the first request pays a premium for the prefix, and every later request within the time to live reads it at a discounted rate, which the gateway sees in usage.cacheReadInputTokens and usage.cacheWriteInputTokens. Both caches are written after the model call, and a hit never calls the model. The cost report reads one usage record per request (tokens in and out, cache read and write tokens, tier, model, cache result) and multiplies by a price table you maintain in config, so the report works the same for on-demand and for test runs.

    What "slow" means for a GenAI application

    In a classic backend you measure one number per request: how long until the response arrives. A foundation model call splits that number into pieces that behave differently, and the fixes for each piece are different. Before you tune anything, learn the vocabulary the exam uses.

    • Time to first token (TTFT): the delay between sending the request and receiving the first generated token. It is dominated by network setup, queueing at the service, and processing of the input prompt (the "prefill" step). Longer prompts raise TTFT.
    • Output speed: tokens per second after the first token. Generation is sequential, so total generation time is roughly the number of output tokens divided by this rate.
    • Total latency: TTFT plus generation time. Bedrock reports it as metrics.latencyMs in a Converse response and as the InvocationLatency CloudWatch metric.
    • Perceived latency: what the user feels. With streaming, perceived latency is close to TTFT. Without it, perceived latency is total latency.

    Two consequences follow. First, output length is the biggest lever on total latency, because every output token is produced one after another. A 50-token classification label returns far faster than a 600-token essay from the same model. Second, in a RAG or agent workflow the model call is only one stage. Embedding the query, searching the vector store, reranking, calling tools, and running guardrails each add time, so the end-to-end number needs a per-stage budget.

    Backend analogy

    TTFT behaves like time to first byte on an HTTP response, and streaming is the same idea as chunked transfer encoding or server-sent events. A page that starts rendering at 300 ms feels faster than one that arrives complete at 3 s, even though the total work is identical.

    Responsive AI systems (4.2.1)

    The exam describes a scenario, such as a customer-facing chat feature that feels sluggish, and asks which change helps most. The techniques below are ordered roughly by how often they are the right answer.

    Stream the response

    Use ConverseStream (Boto3: converse_stream) instead of Converse for anything a human is watching. The model emits events as it generates: messageStart, then repeated contentBlockDelta events carrying text fragments, then contentBlockStop, messageStop (with the stop reason), and finally a metadata event with token usage and latency. Streaming does not make generation faster. It moves the first visible text from the end of generation to the beginning. The AWS CLI cannot call streaming operations, so this is an SDK-only feature.

    import boto3, time
from botocore.config import Config

client = boto3.client(
    "bedrock-runtime",
    config=Config(retries={"max_attempts": 5, "mode": "adaptive"}, read_timeout=120),
)

def stream_answer(prompt: str, model_id: str = "us.anthropic.claude-sonnet-4-6"):
    start = time.perf_counter()
    first_token_at = None
    resp = client.converse_stream(
        modelId=model_id,
        messages=[{"role": "user", "content": [{"text": prompt}]}],
        inferenceConfig={"maxTokens": 400, "temperature": 0.2},
    )
    for event in resp["stream"]:
        if "contentBlockDelta" in event:
            if first_token_at is None:
                first_token_at = time.perf_counter() - start   # TTFT
            yield event["contentBlockDelta"]["delta"].get("text", "")
        elif "metadata" in event:
            usage = event["metadata"]["usage"]
            total = time.perf_counter() - start
            print(f"\nTTFT={first_token_at:.2f}s total={total:.2f}s "
                  f"in={usage['inputTokens']} out={usage['outputTokens']}")

for piece in stream_answer("Explain eventual consistency in two sentences."):
    print(piece, end="", flush=True)

    In a FastAPI service you return this generator through a StreamingResponse with media type text/event-stream. Behind API Gateway REST APIs, response streaming needs to be explicitly supported and enabled for your integration, and Lambda needs response streaming enabled on the function URL or invoke mode. Check the current documentation for your chosen front door, because a buffering proxy silently removes the benefit. See the Domain 2 guide for the integration patterns.

    Watch out

    Streaming interacts with output controls. If a guardrail must inspect the full answer before the user sees it, streaming either waits for the check or runs the guardrail in an asynchronous mode where flagged content may already have been shown. Decide which behavior your safety requirements allow before you promise "instant" text.

    Choose a latency-optimized path

The priority tier gives preferential processing and lower latency for time-sensitive traffic at a higher price, and the flex tier is best effort for work that can wait. Support varies by model and Region, so confirm both in the Bedrock documentation or console before designing around either.

    Pre-compute what is predictable

    If a question will be asked often and its answer does not depend on the user, do the model work ahead of time. Examples: a nightly job that generates summaries for the top 500 product pages, an EventBridge Scheduler rule that refreshes a "daily briefing" at 06:00, or an S3 event that triggers summarization when a document lands. Store the result in DynamoDB or S3 and serve it with a key lookup. The user-facing latency becomes single-digit milliseconds, and the model cost is paid once per document instead of once per view. The trade-off is staleness and wasted work on content nobody reads, so pre-compute only what has a high hit rate. The same reasoning drives the exact-match and semantic caches in Chapter 1.

runtime = boto3.client("bedrock-runtime")

async def converse(prompt: str, model_id: str, max_tokens: int = 200) -> str:
    # boto3 is synchronous, so run each call in a worker thread
    def call():
        r = runtime.converse(
            modelId=model_id,
            messages=[{"role": "user", "content": [{"text": prompt}]}],
            inferenceConfig={"maxTokens": max_tokens, "temperature": 0},
        )
        return r["output"]["message"]["content"][0]["text"]
    return await asyncio.to_thread(call)

async def summarize_all(docs: list[str]) -> list[str]:
    sem = asyncio.Semaphore(8)          # cap concurrency, see the throughput section
    async def one(d):
        async with sem:
            return await converse(f"Summarize in 2 sentences:\n{d}",
                                  "us.amazon.nova-lite-v1:0")
    return await asyncio.gather(*(one(d) for d in docs))

    Parallel calls spend quota faster. Ten simultaneous requests consume ten requests' worth of tokens-per-minute budget at once, so parallelism trades throttling risk for latency. The semaphore above is the guard. In AWS-native orchestration, a Step Functions Parallel state or a Map state with MaxConcurrency expresses the same idea without custom code.

    Retrieval performance (4.2.2 and the vector side of 4.2.6)

    In a RAG application the retrieval stage often costs as much time as it is worth, and a bad retrieval stage wastes the model call that follows it by feeding it the wrong passages. Tuning retrieval means improving two numbers together: relevance (does the right passage come back) and speed (how long until it does). The chunking, embedding, and hybrid-search concepts are taught in the Domain 1 retrieval chapter. Here the focus is on the knobs that change latency and quality at runtime.

    Query preprocessing

    The user's raw question is rarely the best search string. Cheap preprocessing before the embedding call improves recall and can cut work:

    • Normalization: trim, collapse whitespace, strip boilerplate such as greetings, and fix obvious encoding noise. This also raises cache hit rates for exact-match caches.
    • Rewriting: turn a follow-up such as "and what about the premium plan?" into a standalone query using the conversation history. A small, fast model handles this well, but remember it adds a model call to the critical path. Run it only when the history makes the query ambiguous.
    • Expansion and decomposition: generate two or three paraphrases or split a compound question into sub-questions, then search in parallel and merge. This raises recall at the price of more search calls and more tokens to rerank.
    • Metadata filter extraction: pull out filters (department, date range, product) and pass them to the search call so the engine narrows the candidate set before scoring. Pre-filtering is usually the cheapest speedup available.

    Index and query settings that move latency

    The vector store you chose in Domain 1 exposes its own tuning surface. The exam does not ask for engine internals, but it does expect you to know which direction each setting pushes the trade-off.

    import boto3

agent_rt = boto3.client("bedrock-agent-runtime")

def search(kb_id: str, query: str, department: str):
    return agent_rt.retrieve(
        knowledgeBaseId=kb_id,
        retrievalQuery={"text": query},
        retrievalConfiguration={
            "vectorSearchConfiguration": {
                "numberOfResults": 20,               # wide candidate set
                "overrideSearchType": "HYBRID",      # keyword plus vector, only on stores that support it
                "filter": {"equals": {"key": "department", "value": department}},
            }
        },
    )["retrievalResults"]

def rerank(query: str, results: list[dict], model_arn: str, top_n: int = 5):
    r = agent_rt.rerank(
        queries=[{"type": "TEXT", "textQuery": {"text": query}}],
        sources=[{"type": "INLINE",
                  "inlineDocumentSource": {"type": "TEXT",
                      "textDocument": {"text": x["content"]["text"]}}} for x in results],
        rerankingConfiguration={"type": "BEDROCK_RERANKING_MODEL",
            "bedrockRerankingConfiguration": {
                "modelConfiguration": {"modelArn": model_arn},
                "numberOfResults": top_n}},
    )
    return [results[i["index"]] for i in r["results"]]

    The overrideSearchType value HYBRID is valid only for some self-managed vector stores (at the time of writing OpenSearch Serverless, Amazon RDS and Aurora PostgreSQL, and MongoDB Atlas with a filterable text field). Other stores accept only SEMANTIC, and managed knowledge bases do not expose the parameter at all. Check the knowledge base documentation for your store type. The reranker model ARN comes from the Bedrock model catalog for your Region.

    Hybrid search with custom scoring

    Hybrid search combines a keyword score (BM25, which rewards exact term matches such as product codes and error numbers) with a vector similarity score (which finds paraphrases). The two scores live on different scales, so engines combine them with normalization and weights, or with rank fusion such as reciprocal rank fusion. On OpenSearch you define a search pipeline with a normalization processor and weights, for example 0.3 for keyword and 0.7 for vector, and tune the weights against a labeled query set. Custom scoring goes further: boost recent documents with a date decay function, boost authoritative sources through a metadata field, or penalize superseded versions. The exam phrasing is "improve retrieval for queries that contain exact identifiers", and the answer is hybrid search, not a larger embedding model.

    Watch out

    Tune retrieval against a fixed evaluation set of real questions with known good passages, and track recall at k and mean reciprocal rank alongside latency. Changing k, chunk size, or the weights without a baseline makes it impossible to tell whether the change helped. The evaluation tooling is covered in Domain 5.

    Throughput optimization (4.2.3)

    Latency is about one request. Throughput is about how many requests, or how many tokens, the system completes per minute. GenAI throughput has an unusual limit: Bedrock enforces quotas in tokens per minute (TPM) and requests per minute (RPM) per model and Region, and the token budget is consumed by input and output together. Hitting either limit returns a ThrottlingException.

    Token processing

    Every token you do not send or generate is quota you keep. The tactics overlap with cost control: keep prompts tight, trim conversation history, cache stable prefixes, and, most importantly, always set maxTokens explicitly. When maxTokens is unset, the service reserves quota against the model's maximum output size for each request, which can throttle you at a fraction of your real usage. Setting it to the realistic maximum answer length frees that reservation. Right-size it by comparing OutputTokenCount in CloudWatch to the value you configured.

    Batch inference

    For work that no one is waiting on, Bedrock batch inference runs a large set of prompts asynchronously at a discount compared with on-demand pricing. You write the prompts as JSON Lines records, upload them to S3, create a job with CreateModelInvocationJob on the control-plane bedrock client, and read the results from an output S3 prefix when the job finishes. Each input record has a recordId and a modelInput in the model's native request format. Batch is supported for selected models and Regions, with its own quotas on concurrent jobs and records, so verify both before committing to a design.

    Concurrent invocation management

    Throughput is shaped by how you issue calls. Three controls matter.

    1. A concurrency cap. A semaphore in code, a worker-pool size, a Lambda reserved concurrency value, an SQS event source MaximumConcurrency setting, or a Step Functions Map MaxConcurrency. Pick a cap from your quota: if the model allows 400,000 tokens per minute and an average request uses 4,000 tokens, you can sustain about 100 requests per minute, not 1,000.
    2. Retries with backoff and jitter. Throttling is a signal to slow down. Boto3's adaptive retry mode adds client-side rate limiting that backs off when it sees throttle errors, and standard mode uses exponential backoff with jitter. Retry ThrottlingException, ModelTimeoutException, ServiceUnavailableException, and InternalServerException. Do not retry ValidationException or AccessDeniedException, because the second attempt fails the same way.
    3. Queue-based load leveling. Put requests that can wait into an Amazon SQS queue and let a consumer pull at a controlled rate. A burst of 5,000 summarization requests becomes a smooth stream that stays under quota, and a dead-letter queue catches the ones that keep failing.

    If bursts still exceed one Region's quota, a cross-Region inference profile (an ID with a us., eu., apac., or global. prefix) spreads requests across Regions. Geographic profiles keep traffic inside a boundary, while global profiles may route anywhere, so the prefix is also a data-residency choice. See Domain 1 resilience.

    Match the symptom to the control. Throttling at low real usage points to an unset maxTokens. Bursty traffic that can tolerate delay points to SQS load leveling.     Model parameters and A/B testing (4.2.4)

    Generation parameters control how the model picks each next token. Defaults are reasonable, but the best settings depend on the task, and the exam expects you to match them to requirements.

    ParameterWhat it doesLower valueHigher value
    temperatureScales how sharply the probability distribution over next tokens is peakedMore deterministic, repeatableMore varied, more creative, more risk of drift
    topP (nucleus sampling)Samples only from the smallest set of tokens whose cumulative probability reaches PNarrower, safer word choiceWider vocabulary
    topKSamples only from the K most likely tokensNarrowerWider
    maxTokensHard cap on output tokensFaster, cheaper, may truncateAllows long answers, reserves more quota
    stopSequencesEnds generation when a string appearsNot applicableNot applicable. Use to stop at a delimiter and save tokens

    Practical guidance: extraction, classification, and tool-argument generation want temperature at or near 0. Question answering over retrieved context wants low values, typically 0 to 0.3, so that answers stay close to the passages. Brainstorming and marketing copy tolerate 0.7 to 1.0. Change either temperature or topP, not both at once, because they act on the same distribution and it becomes hard to attribute the effect. Treat these ranges as starting points to test, not rules.

    The Converse API's inferenceConfig holds maxTokens, temperature, topP, and stopSequences. Parameters that exist for only some models, such as top_k for Anthropic models, go in additionalModelRequestFields using the provider's own field name. Supported ranges differ by model family, and some newer models restrict which sampling parameters you may set together, so read the model's parameter page. Invalid values return a ValidationException.

    modelId="us.anthropic.claude-sonnet-4-6",

    inferenceConfig={"maxTokens": 500, "temperature": 0.1, "stopSequences": ["###"]},

)

    A/B testing configurations

    A change that "feels better" in a demo is not evidence. An A/B test sends a controlled share of real or replayed traffic to variant B and compares outcomes with variant A. For GenAI the variants can be a model, a prompt version, a parameter set, a retrieval configuration, or a guardrail setting. Measure several outcomes together, because improving one often hurts another: quality score (human rating or an LLM-as-judge), latency (p50 and p95), cost per request, token usage, refusal rate, and a business metric such as resolution rate or thumbs-up rate.

    1. Assign deterministically. Hash the user or session ID to a bucket so a user sees one variant for the whole experiment. Random per-request assignment mixes variants inside a conversation.
    2. Keep config out of code. Store the variant definition (model ID, prompt version, parameters, traffic percentage) in AWS AppConfig or in Bedrock Prompt Management versions, and let the app read it. Shifting from 5% to 50% then needs no deployment. See dynamic model switching and the Prompt Management section.
    3. Tag every call. Pass the variant name in requestMetadata on the Converse call so model invocation logs can be filtered by variant, and emit the variant as a CloudWatch metric dimension.
    4. Compare with enough data. Decide the metric and the sample size before you start, and avoid stopping the moment variant B looks ahead. Run a canary first (1% to 5%) to catch errors, then widen.
    5. Evaluate offline first. Replay a saved set of production prompts through both variants with Bedrock Model Evaluation or your own harness before exposing users. Domain 5 covers evaluation jobs and LLM-as-a-judge in depth.

    Resource allocation and capacity planning (4.2.5)

    Capacity planning for a GenAI service has two layers that scale independently: the model layer, governed by Bedrock quotas or provisioned throughput, and the application layer, the containers or functions that call it. The app tier can scale in a minute. The model quota moves by request to AWS, which takes days, so the model layer is the one to plan ahead.

    Plan in tokens, not requests

    Estimate demand in tokens per minute. For each request type, take the average input tokens and average output tokens, multiply by requests per minute at peak, and add headroom (a 30 to 50 percent buffer is common, and bursts need more). Then compare with the model's TPM and RPM quotas shown in Service Quotas. A worked example:

    ItemValue
    Peak requests per minute300
    Average input tokens (prompt plus retrieved context)3,000
    Average output tokens400
    Peak tokens per minute300 x 3,400 = 1,020,000
    With 40% headroomabout 1,430,000
    DecisionCompare with the quota. If it is lower, request an increase, use a cross-Region inference profile, shrink prompts, or move to provisioned throughput

    Some models count output tokens at a burn rate greater than 1 against the token quota, so one output token consumes more than one unit of budget, and quota math must use the documented rates for your model. Check the quota page for the exact rules.

    On-demand, cross-Region, or provisioned

    On-demand shares capacity and bills per token. Cross-Region inference widens the pool. Provisioned throughput reserves model units for a fixed hourly price with a commitment term (none, one month, or six months), gives steady performance, and is required to serve a custom or fine-tuned model. A provisioned model is invoked by its ARN, not a model ID. Provisioned throughput pays off only when utilization is consistently high, because an idle model unit costs the same as a busy one. Compute the break-even point: the hourly price of the units divided by the on-demand price per token tells you how many tokens per hour you must sustain. The cost angle is in Chapter 1.

    Utilization monitoring

    The AWS/Bedrock CloudWatch namespace (dimension ModelId) publishes Invocations, InvocationLatency, InputTokenCount, OutputTokenCount, InvocationThrottles, and error counts. Build a dashboard with tokens per minute against the quota line, a throttle count, and p95 latency. Alarm on any sustained nonzero InvocationThrottles and on tokens per minute above about 80 percent of the quota. The monitoring chapter, Task 4.3, builds these in full. To track prompt and completion size patterns over time, enable model invocation logging and query it with CloudWatch Logs Insights.

    GenAI requests are long and uneven: one call can hold a connection for 20 seconds, and CPU stays low while the process waits on the model. CPU-based scaling therefore reacts too late or not at all. Choose a signal that reflects the real load.

    AWS LambdaConcurrency scales automatically, bounded by account and reserved concurrencySet reserved concurrency to protect the model quota. Remember the 15-minute maximum duration and use response streaming where supported
    Amazon ECS on FargateApplication Auto Scaling target tracking or step scaling on a serviceScale on in-flight requests per task or ALB RequestCountPerTarget (built-in) or a custom CloudWatch metric, not CPU alone

    Profiling and efficient communication (4.2.6)

    When "it is slow" has no obvious cause, profile before changing anything. The goal is a per-stage latency breakdown for a representative request.

    API call profiling for prompt and completion patterns

    • Log, for every model call: model ID, input tokens, output tokens, latencyMs, stop reason, cache read and write tokens if you use prompt caching, retry count, and a request ID. Model invocation logging gives you the token data in S3 or CloudWatch Logs without code changes.
    • Group by prompt template. A single template with 12,000 input tokens that is called on every request is the first thing to fix, either by trimming it or by caching its prefix.
    • Look at the stopReason distribution. Many max_tokens stops mean you are truncating answers and paying for output that is cut off, and many very short outputs under a large maxTokens mean the cap is looser than needed.
    • Add tracing spans around each stage (preprocess, embed, search, rerank, generate, post-process) so you can see where the milliseconds go. Tracing setup is in Task 4.3.

    LLM-specific latency techniques

    • Shrink the prompt. Prefill time grows with input length. Cut redundant instructions, limit retrieved passages, summarize old conversation turns.
    • Cache the prefix. Prompt caching (cachePoint blocks in Converse) lets Bedrock reuse the processing of a stable prefix such as a long system prompt or reference document. Cache reads reduce latency and cost, and the cache has a short time to live (about five minutes by default for supported models, with some models offering longer settings). Minimum cacheable token counts and supported models vary. See Chapter 1.
    • Cap and shape the output. Ask for terse formats, JSON with short keys, or labels in place of paragraphs. Use stopSequences to end at a delimiter.
    • Use a smaller model for easy steps. Route intent classification, query rewriting, and extraction to a small model, and keep the large model for synthesis.
    • Avoid unnecessary reasoning. Models with extended thinking spend tokens before the visible answer. Enable them for hard tasks only and set a reasoning budget where the model supports one.
    • Split long work. Break a 3,000-token document analysis into parallel section analyses and a short merge step.

    Efficient service communication

    • Reuse clients and connections. Create the Boto3 client once per process (outside the Lambda handler), so TLS handshakes and credential lookups are not repeated. Tune max_pool_connections in the botocore Config if you run many threads, and set read_timeout above your longest generation time, because the default read timeout of 60 seconds ends long responses early.
    • Co-locate. Put the app, the vector store, and the model in the same Region. Cross-Region hops add tens to hundreds of milliseconds per call. A cross-Region inference profile adds routing inside AWS, so measure it rather than assuming it is free.
    • Keep traffic on AWS's network. VPC interface endpoints for bedrock-runtime remove the trip through a NAT gateway and the internet, which helps security more than speed, but also avoids NAT bottlenecks and data-processing charges. See Domain 3 endpoints.
    • Batch embeddings. Embedding models take one text per call on some model families, so for many chunks use threads with a concurrency cap, or a batch job for large corpora, rather than one sequential loop.
    • Prefer direct service integrations. A Step Functions task can call Bedrock directly through an optimized service integration with no Lambda hop in the middle. Remove intermediate hops where they add no logic.
    • Cache lookups. Hold feature flags, prompt templates, and routing config in memory for a short TTL instead of reading AppConfig, Parameter Store, or DynamoDB on every request.

    CLI and Boto3 path

      import boto3, time, statistics, sys
from botocore.config import Config

rt = boto3.client("bedrock-runtime", config=Config(retries={"max_attempts": 5, "mode": "adaptive"}, read_timeout=120))
PROMPT = "Explain eventual consistency in about 100 words."

def run_stream(model):
    t0 = time.perf_counter(); ttft = None; out = 0
    r = rt.converse_stream(modelId=model,
        messages=[{"role": "user", "content": [{"text": PROMPT}]}],
        inferenceConfig={"maxTokens": 250, "temperature": 0})
    for e in r["stream"]:
        if "contentBlockDelta" in e and ttft is None:
            ttft = time.perf_counter() - t0
        if "metadata" in e:
            out = e["metadata"]["usage"]["outputTokens"]
    return ttft, time.perf_counter() - t0, out

def pct(xs, p): xs = sorted(xs); return xs[min(len(xs)-1, int(len(xs)*p))]

for model in sys.argv[1:]:
    rows = [run_stream(model) for _ in range(20)]
    ttfts = [r[0] for r in rows]; tots = [r[1] for r in rows]
    tps = statistics.mean(r[2] / max(r[1] - r[0], 0.001) for r in rows)
    print(f"{model}: TTFT p50={pct(ttfts,.5):.2f}s p95={pct(ttfts,.95):.2f}s "
          f"total p50={pct(tots,.5):.2f}s p95={pct(tots,.95):.2f}s ~{tps:.0f} tok/s")
    2. Find model and profile IDs available to you: aws bedrock list-inference-profiles --region us-east-1 --query "inferenceProfileSummaries[].inferenceProfileId" (use your own Region).
    3. Run python bench.py us.anthropic.claude-sonnet-4-6 us.amazon.nova-lite-v1:0, substituting IDs you have access to.
    4. Record the non-streaming total by running the same prompt with aws bedrock-runtime converse --model-id <id> --messages '[{"role":"user","content":[{"text":"Explain eventual consistency in about 100 words."}]}]' --inference-config '{"maxTokens":250}' and reading metrics.latencyMs in the JSON. The CLI cannot stream, so this shows the user-perceived delay without streaming.
    5. Query the metrics: aws cloudwatch get-metric-statistics --namespace AWS/Bedrock --metric-name InvocationLatency --dimensions Name=ModelId,Value=<id> --start-time $(date -u -d '-30 minutes' +%FT%TZ) --end-time $(date -u +%FT%TZ) --period 300 --statistics Average Maximum.

    Chapter recap

    • Split latency into TTFT, output speed, and total. Streaming improves perceived latency without changing total generation time, and output length is the biggest lever on total time.
    • Pre-compute predictable answers, run independent calls in parallel (bounded by quota), and use latency-optimized inference, the priority tier, or a smaller model where the requirement justifies it. Benchmark with percentiles.
    • Tune retrieval with query preprocessing, metadata pre-filters, a sensible k, ANN search settings, hybrid search with weights, and reranking of a wide candidate set down to a few passages.
    • Throughput is limited by tokens and requests per minute. Set maxTokens, cap concurrency, retry only retryable errors with adaptive backoff, level bursts with SQS, and use batch inference for offline work.
    • Tune temperature, topP, and topK to the task, change one thing at a time, and A/B test with deterministic assignment, config held in AppConfig or Prompt Management, and variant tags in logs and metrics.
    • Plan capacity in tokens per minute with headroom, choose among on-demand, cross-Region, and provisioned throughput, and scale the application tier on request count or queue depth, not CPU.
    • Profile per stage before optimizing, reuse clients, co-locate components, and set timeouts that match generation time.

    Knowledge check

    1. A support chat feature calls a large model with a 4,000-token answer limit. Users say it feels frozen for 8 seconds before text appears. The answer quality is fine and cost is acceptable. What change helps most?

      Answer

      Switch the call to ConverseStream and render tokens as they arrive. This cuts perceived latency to TTFT without altering quality or cost. A larger model is slower, not faster. Raising maxTokens only allows longer output. Provisioned throughput helps queueing under load, not an 8-second generation of a long answer.

    2. A batch of 3,000 independent product descriptions must be summarized nightly, and results are needed by morning. Which approach is the best fit under a cost constraint?

      Answer

      Bedrock batch inference: write JSONL to S3, create a model invocation job, and read results from the output prefix, at discounted pricing. Synchronous Converse in a loop costs more and risks throttling. Provisioned throughput is a poor fit for a job that runs once a night, because an hourly commitment sits idle the rest of the day. Streaming adds nothing for an unattended job.

    3. An application receives ThrottlingException at about 25 percent of its documented tokens-per-minute quota. Every call omits maxTokens. What is the most likely cause and fix?

      Answer

      Unset maxTokens makes the service reserve quota against the model's maximum output size on each request, so reserved quota is exhausted long before real usage is. Set maxTokens to the realistic maximum output. Raising the retry count only adds load, switching to a larger model uses more quota, and asking for a quota increase treats the symptom while wasting tokens.

    4. Search results for queries like "error ERR-40213 on invoice export" are poor with pure vector search because the identifier is rarely retrieved. Which improvement is best?

      Answer

      Hybrid search that combines keyword (BM25) and vector scores, with weights tuned on a labeled query set, optionally followed by reranking. A larger embedding model does not guarantee exact-token matching. A bigger k increases cost and prompt size without fixing the ranking. Fine-tuning the foundation model does not change what retrieval returns.

    5. You want to test whether temperature 0 improves factual accuracy of a question-answering service compared with 0.4, without redeploying code, and you want each user to see one behavior. What design fits?

      Answer

      Store the two parameter sets and traffic split in AWS AppConfig (or use Prompt Management versions), assign users by a hash of the user ID, tag calls with requestMetadata and a metric dimension, and compare accuracy, latency, and cost for each variant, starting with a small canary share. Random per-request assignment mixes variants inside a conversation. Editing constants in code requires a deployment. Comparing before and after a release confounds the change with time-based traffic differences.

    6. A Fargate service that calls Bedrock scales on CPU utilization at 60 percent. Under load, response times climb while CPU stays near 15 percent. What should replace the scaling signal?

      Answer

      Scale on a signal that reflects waiting work: ALB request count per target, a custom in-flight-requests metric, or queue depth for async work, and cap the maximum task count by the model's quota. CPU stays low because tasks are blocked on model responses. Adding a bigger CPU size does not help. A scheduled scale-out ignores real demand, and removing the cap lets extra tasks be throttled by Bedrock.

    Problem statement

    Scenario. A software company runs a support chat on its public help site. Agents and customers ask questions such as "How do I rotate an API key without downtime?" The answers come from about 3,000 help articles and release notes. The current prototype waits for the whole answer and then shows it. Median time to a visible answer is 9 seconds, and during a product launch the 95th percentile (p95) went past 30 seconds while the service returned throttling errors. Product wants the first words on screen in under 1.5 seconds, a p95 time to first token under 3 seconds at launch-day traffic, and a bill that does not triple.

    Requirements.

    • Answers stream to the browser as tokens are produced. Time to first token (TTFT) and total time are recorded for every request.
    • Retrieval and any other independent work (for example intent classification and a cache lookup) run in parallel, not one after another.
    • The 20 most common questions are pre-computed nightly and served without a model call.
    • Retrieval is tuned using a labelled set of at least 40 questions, and each change (query rewrite, filter, hybrid search, number of results) is kept only if the hit rate or latency improves.
    • A benchmark script reports p50, p95, and p99 for TTFT and total time, with a fixed set of prompts and a fixed concurrency.
    • Two parameter sets (for example a lower and a higher temperature, or two maxTokens limits) are compared on the same prompts. The result is judged on quality and latency, not on intuition.
    • The service limits concurrent model calls, retries with backoff when it is throttled, and scales out on a custom metric that reflects token load, not CPU.
    • Offline work, such as re-summarizing all articles, runs as a batch job and never competes with live chat for capacity.

    How the exam phrases it. Expect a stem such as "A company's chat application shows users a blank screen for 10 seconds while a foundation model generates a long answer. Which change improves perceived latency with the LEAST code change?" The answer is response streaming (ConverseStream or InvokeModelWithResponseStream). Distractors include a larger model (slower, not faster), Provisioned Throughput (it guarantees capacity, not lower per-token time), and a bigger Lambda memory setting (the wait is the model, not the function). Another common stem describes a service that is throttled during bursts. The best answer is usually a mix: request backoff, a queue or concurrency limit, cross-Region inference, or more quota, chosen by whether the traffic is interactive or batch.

    Solution architecture

    The service has an online path for interactive questions and an offline path for batch work. The online path is a streaming API in front of a short pipeline: normalize the question, then fan out to a cache lookup, retrieval, and a cheap classifier at the same time, then call the model with streaming on. The offline path pre-computes common answers and runs bulk jobs with Bedrock batch inference, so neither touches interactive capacity.

    Online path, step by step. A question arrives and the service first checks the pre-computed table with a normalized key. A hit returns in tens of milliseconds and costs no tokens. On a miss, it starts three calls at once with asyncio.gather: a cache lookup for a recent identical question, retrieval of the top passages, and a call to a small, fast model that classifies the intent (billing, how-to, outage). When they all finish, the service builds the prompt and calls ConverseStream. The first contentBlockDelta event is forwarded to the browser immediately, and the service records TTFT at that moment. When the stream ends, the final metadata event carries token usage, which the service publishes as metrics.

    Key decisions and trade-offs.

    • Measure first, then tune. Add timing to every stage before changing anything. Teams often spend a week on prompts when 40 percent of the delay is a sequential classifier call that could have run in parallel. The benchmark in milestone 2 is the baseline every later change is compared with.
    • Streaming does not make the model faster. Total time is the same, and it can be slightly worse because of per-event overhead. It lowers perceived latency because the user reads while the model writes. That makes TTFT the metric that matters for chat, and total time the metric that matters for batch and for agents that must read the whole answer.
    • Parallelize only independent work. Retrieval and classification do not depend on each other. Generation depends on both. If the classifier only picks a model tier, run it first and cheaply, because its result changes the next call. Draw the dependency graph before you write gather.
    • Latency optimization is a model and Region question as well. Smaller models generate faster. Some models offer a latency-optimized inference option in selected Regions, and cross-Region inference profiles add a routing hop but spread load. Check the current model and Region list before relying on either, and benchmark with the exact model ID you plan to ship.
    • Scale on tokens, not CPU. The service spends most of its time waiting on network streams, so CPU stays low while users queue. Publish a custom metric such as in-flight streams per task or tokens per minute, and scale on that. CPU-based scaling reacts too late or never.
    • Protect shared quota. Bedrock quotas are per account, per Region, per model, in requests and tokens per minute. A launch spike or a batch job can use all of it. Cap concurrency in the app, keep batch work on batch inference (its own capacity), and retry with backoff and jitter so throttled requests do not all return at the same instant.

    Definition of done

    • curl -N against the service prints tokens as they arrive, and the first token appears well before the last one.
    • The benchmark script prints p50, p95, and p99 for TTFT and total time for 40 questions at concurrency 1 and 10, and the results are saved in results/.
    • The final run shows TTFT p95 below the 3 second target (or the README explains, with measurements, which stage prevents it).
    • A trace or stage-timer log shows retrieval and classification starting at the same time, not one after the other.
    • The labelled retrieval set reports a hit rate for the baseline and for each kept change, and the retrieval table in the README shows which changes were rejected and why.
    • A question in the pre-computed set returns without a model invocation. You can show this from the absence of a matching model invocation log entry, or from a counter that did not change.
    • A load test above your concurrency limit produces 429 or queued responses, not unhandled exceptions, and the throttle count is lower with backoff on than off.
    • The A/B comparison table lists quality score, TTFT, total time, and output tokens for both variants, and one variant is chosen with a written reason.
    • CloudWatch shows the custom metrics, and a ramp test triggers a scale-out event (aws application-autoscaling describe-scaling-activities lists it).
    • A batch inference job completes and writes its output to S3, and the interactive benchmark run during the job stays within 20 percent of the earlier p95 TTFT.
    • The README holds the before and after table and a one-paragraph recommendation.

    Cost, Region, and account notes

    Watch out

    • Load tests spend real tokens. A benchmark of 40 questions at 10 concurrent users, repeated several times, can run to thousands of model calls. Use a small, low-cost model for the classifier and for most tuning runs. Cap maxTokens in every test. Do the final full benchmark once on the model you plan to ship.
    • Throttling can affect the whole account. Quotas are shared by every workload in the account and Region for that model. A load test above your quota can throttle other projects you run at the same time. Check your current quota in the Service Quotas console before a ramp test, and run tests when nothing else is using the model.
    • Always-on pieces bill while idle. A Fargate service, an Application Load Balancer, a NAT gateway if you add one for outbound access, an OpenSearch domain or collection, and an ElastiCache node all bill by the hour. Scale the service to zero tasks or delete the stack when you stop. OpenSearch Serverless has a minimum OCU charge that can exceed the rest of this project combined, so prefer a Bedrock knowledge base with a managed or low-cost store for the lab, and delete any OpenSearch collection the same day.
    • Batch inference is not instant. Jobs are queued and can take minutes to hours, and supported models and the discount vary by model and Region. Do not put a batch job on the interactive path. Check the model and Region list and current pricing before you plan on it.
    • Provisioned Throughput is not part of the default build. It is billed per model unit per hour with a commitment option, and it guarantees capacity, not lower latency per token. Do not buy it for a lab. Use the capacity estimate to learn when it would make sense.
    • Lambda streaming and load balancers have timeouts. An ALB idle timeout of 60 seconds can cut a long stream, and some proxies buffer SSE. Test the full path with a long answer, not just a local call.
    • Region: model availability, cross-Region inference profiles, latency-optimized options, batch inference support, and knowledge base features differ by Region. Check each in your assigned Region before you build, and keep resources in one Region so you do not add network latency between them.
    • Account limits: no account restrictions are documented for this repo. If a service above is unavailable on your plan, use the stated alternative (for example a Lambda-based service in place of Fargate).

    Expected spend for a lab run over a few days, with the compute stack deleted overnight, a small managed retrieval store, a small model for tuning runs, and a single full benchmark on the target model, is in the low tens of dollars. Most of it is model tokens from repeated benchmark runs and the hourly cost of the load balancer and service while they run.     What is different about monitoring a GenAI application

    You already run services with dashboards, alarms, and traces. The AWS tooling is the same: Amazon CloudWatch for metrics, logs, and alarms, and AWS X-Ray or OpenTelemetry for traces. What changes is what you measure and why the usual signals mislead you.

    • Cost is a runtime metric. A single bad prompt template or a runaway agent loop can multiply your bill within an hour. Tokens are the unit of spend, so token counts belong on the same dashboard as latency and errors.
    • Latency has two parts. Time to first token (TTFT) is what a streaming user feels. Total duration depends on how many output tokens the model writes. A p99 on total duration alone hides which part moved.
    • Correctness is not an error code. A hallucinated answer, a refused answer, and a good answer all return success. Quality has to be measured with extra work: LLM-as-a-judge scores, golden datasets, and user feedback.
    • The same input gives different output. Non-determinism means you watch distributions (average score, drift over a week), not single results.
    • The request fans out. One user question becomes a retrieval call, a model call, several tool calls, and maybe a second model call. Without tracing you cannot tell which step was slow or wrong.

Because EMF is just JSON on stdout, you need no library to start:

    import json, time

def emit_genai_metrics(feature: str, model_id: str, usage: dict,
                       latency_ms: float, cache_hit: bool,
                       grounding: float | None = None) -> None:
    """Write one EMF log line. CloudWatch turns it into metrics."""
    metrics = [
        {"Name": "TokensIn", "Unit": "Count"},
        {"Name": "TokensOut", "Unit": "Count"},
        {"Name": "LatencyMs", "Unit": "Milliseconds"},
        {"Name": "CacheHit", "Unit": "Count"},
    ]
    event = {
        "_aws": {
            "Timestamp": int(time.time() * 1000),
            "CloudWatchMetrics": [{
                "Namespace": "GenAIApp",
                "Dimensions": [["Feature", "ModelId"]],
                "Metrics": metrics,
            }],
        },
        "Feature": feature,
        "ModelId": model_id,
        "TokensIn": usage["inputTokens"],     # from the Converse response
        "TokensOut": usage["outputTokens"],
        "LatencyMs": latency_ms,
        "CacheHit": 1 if cache_hit else 0,
    }
    if grounding is not None:
        event["GroundingScore"] = grounding
        metrics.append({"Name": "GroundingScore", "Unit": "None"})
    print(json.dumps(event))

    The usage dictionary is the one every Converse response already returns (inputTokens, outputTokens, totalTokens, plus cache read and write counts when prompt caching is on), so token tracking costs you nothing extra. Keep dimension cardinality low: every distinct combination of dimension values is a separate billed metric. Put Feature and ModelId on a dimension, but never a user ID or request ID. Put those in the log line as plain properties instead, where they cost nothing and still search well.

    Backend analogy

    EMF is the CloudWatch version of structured logging feeding a Prometheus-style exporter: you log one JSON event and the platform derives counters and gauges from it. Dimensions behave like Prometheus labels, with the same cardinality bill if you put a user ID on one.

    Note

    CloudWatch also supports OpenTelemetry metrics queried with PromQL. If your team already instruments with OpenTelemetry, that is an alternative to EMF. For the exam, EMF and PutMetricData are the named mechanisms.

        with tracer.start_as_current_span("rag.retrieve") as span:
            chunks = retrieve(question)
            span.set_attribute("retrieval.count", len(chunks))
            span.set_attribute("retrieval.top_score",
                               max((c["score"] for c in chunks), default=0.0))

        with tracer.start_as_current_span("llm.converse") as span:
            t0 = time.perf_counter()
            resp = bedrock.converse(
                modelId=MODEL_ID,
                messages=[{"role": "user", "content": [{"text": question}]}],
                inferenceConfig={"maxTokens": 512, "temperature": 0.2},
            )
            span.set_attribute("gen_ai.request.model", MODEL_ID)
            span.set_attribute("gen_ai.usage.input_tokens", resp["usage"]["inputTokens"])
            span.set_attribute("gen_ai.usage.output_tokens", resp["usage"]["outputTokens"])
            span.set_attribute("gen_ai.response.stop_reason", resp["stopReason"])
            span.set_attribute("llm.latency_ms", resp["metrics"]["latencyMs"])
            span.set_attribute("app.wall_ms", (time.perf_counter() - t0) * 1000)
        return resp["output"]["message"]["content"][0]["text"]

    Two details matter. First, stopReason is a diagnostic gold mine: max_tokens means the answer was cut off, guardrail_intervened means a guardrail rewrote or blocked it, and tool_use means the model is asking for a tool. Second, do not put the full prompt or response in a span attribute by default. Spans are often retained and shared widely, and prompts contain user data. Log content to a protected, access-controlled destination (invocation logs) and keep the trace to metadata and identifiers. This follows the same privacy reasoning as Domain 3.

    Model invocation logs (4.3.2)

    Metrics say how much. Traces say where. Model invocation logging says what: when enabled, Bedrock records each request and response, with metadata such as timestamp, account, Region, model ID, input and output token counts, and the request metadata you attach. It is off by default. You choose destinations: a CloudWatch Logs log group, an S3 bucket, or both. Large payloads and binary data (images, for example) go to S3 even when text goes to CloudWatch Logs. The Domain 3 orientation has the setup walkthrough and the privacy discussion (invocation logging); this section is about using the logs for operations.

    Make logs searchable with requestMetadata

    Converse and InvokeModel accept requestMetadata, a small map of string key-value pairs that is copied into the invocation log record. Use it to tag each call with the feature, tenant tier, prompt version, and experiment arm. Do not put raw PII in it, because it lands in the log in clear text.

    resp = bedrock.converse(
    modelId=MODEL_ID,
    messages=[{"role": "user", "content": [{"text": question}]}],
    inferenceConfig={"maxTokens": 512},
    requestMetadata={
        "feature": "support-chat",
        "promptVersion": "v7",
        "tenantTier": "enterprise",
        "traceId": current_trace_id,   # join logs to traces
    },
)

    Querying the logs

    For logs delivered to CloudWatch Logs, use Logs Insights. Field names follow the log record schema (modelId, input.inputTokenCount, output.outputTokenCount, requestMetadata.*); run a sample query with fields @message | limit 5 first to confirm the exact names in your account before building dashboards on them.

    fields @timestamp, modelId, requestMetadata.feature as feature,
       input.inputTokenCount as tin, output.outputTokenCount as tout
| filter ispresent(requestMetadata.feature)
| stats count() as calls, sum(tin) as inTokens, sum(tout) as outTokens,
        pct(tout, 95) as p95Out
  by feature, bin(1h)
| sort inTokens desc

    For logs in S3, query with Amazon Athena (SQL over files in S3) after defining a table over the log prefix. That route suits long retention and large volumes, and it is cheaper per scanned gigabyte than keeping everything hot in CloudWatch Logs. A common pattern is CloudWatch Logs for 14 to 30 days of interactive debugging and S3 for months of audit history.

    Watch out

    Invocation logs contain complete prompts and responses. Guardrail PII masking applies to the response returned to the caller, not to what the invocation log stores, so the log can hold the unmasked text. Encrypt the log group and bucket with a customer managed KMS key (Domain 3, KMS), restrict read access tightly, set a retention period, and for the most sensitive workloads consider leaving content logging off and relying on metadata and traces. Logging also adds CloudWatch Logs ingestion and S3 storage cost proportional to your traffic.

    Exam tip

    “Detailed request and response analysis” or “what exactly was the prompt” points to model invocation logs. “Who called InvokeModel” points to CloudTrail. Neither replaces the other: CloudTrail records that a call happened and by which principal, while invocation logs capture the content and token usage.

    Proactive detection: bursts, drift, quality, and cost anomalies (4.3.2)

    Dashboards are for people who are looking. Alarms are for the 3 a.m. case. GenAI adds three things worth alarming on that classic services do not have: token bursts, response drift, and quality scores.

    Token burst alarms

    A token burst is a sudden rise in input or output tokens per minute. Causes include a prompt template that now inlines a whole document, a retry storm, an agent stuck in a loop, or abuse by one tenant. Two alarm styles fit:

    Alarm typeHow it decidesUse it for
    Static thresholdFires when a metric crosses a fixed number for N periodsHard ceilings: “more than 2 million output tokens in 5 minutes”, or usage above 80% of a known quota
    Anomaly detectionCloudWatch learns the metric’s normal pattern (including daily and weekly seasonality) and fires when it leaves a band of expected valuesTraffic that rises and falls on a schedule, where no single number is right all day

    An anomaly detection alarm uses the ANOMALY_DETECTION_BAND(metric, width) function as its threshold; a larger width gives a thicker band and fewer alarms. The model needs some history to learn from, and anomaly alarms cost more than standard alarms, so reserve them for the metrics where seasonality really exists. Here are both, as CLI and Boto3:

    Response drift

    Drift means the system’s outputs shift without anyone changing the code. Reasons: the provider updated a model behind an alias, your retrieval corpus changed, or the real traffic mix moved. You cannot watch “meaning” directly, so you watch proxies that you compute per response and emit as metrics:

    • Length: average output tokens per feature. A sudden drop often means more refusals or truncation, a rise often means verbosity or rambling.
    • Refusal and guardrail rate: the share of responses where stopReason is guardrail_intervened or the text matches a refusal pattern.
    • Format validity: the share of responses that parse as the JSON schema you asked for.
    • Embedding distance: embed each answer (or a sample), and track the average cosine distance to a centroid of known-good answers. A growing distance flags a semantic shift without a human reading anything.
    • Judge scores: the average of an LLM judge’s rating on a sample (next section).

    Alarm on these with anomaly detection or a moving-average comparison (this week against last week). The metric math expression language can compare a metric to its own value from a past period, which is enough for a first drift alarm.

    Quality metrics: hallucination rate and response quality

    CloudWatch cannot measure truthfulness by itself. You compute a score somewhere else and publish it as a metric, then use normal CloudWatch features on it. There are three common score sources, and the exam names them in different phrasings:

    Score sourceHow it worksCoverage and cost
    Guardrails contextual grounding checkFor RAG answers, ApplyGuardrail or an attached guardrail scores grounding (is the answer supported by the retrieved source) and relevance against a threshold. See Domain 3, hallucination controls.Every request if attached inline; guardrail charges apply
    LLM-as-a-judge on a sampleA second, usually cheaper or stronger model rates a sampled fraction of responses against a rubric (faithfulness, helpfulness, tone). You publish the average score.Sample 1 to 5% of traffic to bound cost
    Golden dataset replayA fixed set of questions with known-good answers is replayed on a schedule or at deploy time and scored (see troubleshooting).Small, fixed cost; catches regressions, not live-traffic issues
    User signalsThumbs up or down, edits, escalations, retries, abandonmentFree, noisy, and lagging, but real

    Publishing a judge score is just another EMF line. Notice how the sampling keeps cost bounded and how the judge call happens off the request path, so users do not wait for it:

    import random, json, boto3
bedrock = boto3.client("bedrock-runtime")
JUDGE_MODEL = "your-judge-model-id"   # a model enabled in your account

RUBRIC = ("Rate 1-5 how well the ANSWER is supported by the CONTEXT only. "
          "Reply with just the number.")

def maybe_judge(question, context, answer, feature, rate=0.03):
    if random.random() > rate:
        return
    prompt = f"{RUBRIC}\n\nCONTEXT:\n{context}\n\nQUESTION:\n{question}\n\nANSWER:\n{answer}"
    r = bedrock.converse(modelId=JUDGE_MODEL,
                         messages=[{"role": "user", "content": [{"text": prompt}]}],
                         inferenceConfig={"maxTokens": 5, "temperature": 0})
    score = float(r["output"]["message"]["content"][0]["text"].strip()[0])
    print(json.dumps({"_aws": {"Timestamp": int(__import__("time").time()*1000),
        "CloudWatchMetrics": [{"Namespace": "GenAIApp",
            "Dimensions": [["Feature"]], "Metrics": [{"Name": "JudgeFaithfulness", "Unit": "None"}]}]},
        "Feature": feature, "JudgeFaithfulness": score}))

    Run this in a separate worker (a queue consumer or a Lambda triggered from a stream) and not inline. Bedrock Evaluations can also run judge-style evaluation jobs against datasets; that service is the subject of the next domain, so here treat it as the managed version of the same idea.

    Cost anomaly detection

    Token alarms catch a spike within minutes. Spend still deserves a second net that works on the bill itself. AWS Cost Anomaly Detection (part of Billing and Cost Management) learns your normal spend by service, account, cost allocation tag, or cost category, and sends alerts through email or Amazon SNS when spend deviates. Create a monitor scoped to Amazon Bedrock (or to your Project tag, if you tag application inference profiles) and a subscription with an alert threshold. Its data arrives with the usual billing delay, so treat it as the slow safety net behind the fast CloudWatch alarms. AWS Budgets can add a fixed monthly or daily limit with alerts at set percentages of the budget.

    Exam tip

    Pick the detector by speed and shape. Minutes, per model: CloudWatch alarm on AWS/Bedrock token metrics. Seasonal traffic with no fixed number: CloudWatch anomaly detection alarm. Daily spend by service or tag: Cost Anomaly Detection. A fixed monthly cap: AWS Budgets. A distractor will offer Budgets for “detect a burst within minutes”, which it cannot do.

    Forensic traceability and audit logging

    When something goes wrong (a data leak, a complaint, a regulator’s question), you must be able to reconstruct one interaction end to end. The fields that make that possible are decided at design time, not during the incident:

    1. A request ID that follows the request everywhere. Generate it at the edge, put it in requestMetadata, in the trace as an attribute, and in your application logs.
    2. Immutable identity of what ran. Log the model ID or inference profile ARN, prompt version, guardrail ID and version, and retrieval index or knowledge base ID. A bare alias such as “latest” tells an auditor nothing a year later.
    3. Who asked. A pseudonymous user or session identifier (not raw PII) that you can resolve through a controlled lookup.
    4. Tamper resistance. Write audit records to an S3 bucket with Object Lock or to a log group with restricted write permissions, enable CloudTrail log file validation, and separate the permission to write logs from the permission to delete them.
    5. Control-plane history. AWS CloudTrail records management events such as changes to guardrails, logging configuration, IAM policies, and provisioned throughput, and (when you enable data events for the service) can record some runtime calls. Check the current CloudTrail documentation for which Bedrock runtime operations are logged as data events and how to enable them.

    The full governance angle (lineage, model cards, retention policy) is in Domain 3, audit logs. Here the point is operational: the same fields that support audit also make everyday debugging faster.

    User interaction and model behavior tracking

    Track what users do after the answer, because that is the closest thing to ground truth you get in production. Useful events: thumbs up or down, a copy of the answer, a follow-up that rephrases the same question (a sign the first answer failed), escalation to a human, and session abandonment. Log each as a structured event with the request ID, then join it to the invocation log and trace by that ID. For model behavior, keep a rolling view of output length, refusal rate, and topic distribution per prompt version, so that when a version changes you can see the effect on behavior without anyone having to guess.

    Backend analogy

    This is the same product analytics you would build around a search box: track the query, the result shown, and what the user did next, keyed by a session ID. The new part is that the “result” is generated text, so you also store which prompt version and model produced it.

    Note

    CloudWatch Contributor Insights and Logs Insights help answer “which tenants or users account for most tokens” without adding high-cardinality metric dimensions. Contributor Insights rules run on log groups and report top contributors by a chosen field.

    Monitoring tools, agents, and multi-agent coordination (4.3.4)

    Once the model can call tools, a new failure class appears: the model picks the wrong tool, calls the right tool with bad arguments, calls it ten times in a loop, or never calls it at all. The tool itself can be slow or failing and the model may paper over the failure with a plausible answer. You need telemetry on the tool layer separate from the model layer.

    import time, json
from opentelemetry import trace

    event = {"_aws": {"Timestamp": int(time.time()*1000),
             "CloudWatchMetrics": [{"Namespace": "GenAIApp/Tools",

def observed_tool(name):
    def deco(fn):
        def wrapper(**kwargs):
            with tracer.start_as_current_span(f"tool.{name}") as span:
                span.set_attribute("tool.name", name)
                span.set_attribute("tool.arg_keys", ",".join(sorted(kwargs)))
                t0 = time.perf_counter()
                try:
                    out = fn(**kwargs)
                    span.set_attribute("tool.result_chars", len(str(out)))
                    emit("ToolSuccess", 1, "Count", Tool=name)
                    return out
                except Exception as e:
                    span.record_exception(e)
                    emit("ToolError", 1, "Count", Tool=name)
                    raise
                finally:
                    emit("ToolLatencyMs", (time.perf_counter()-t0)*1000, "Milliseconds", Tool=name)
        return wrapper
    return deco

    Agents and multi-agent coordination

    For Bedrock Agents, enableTrace=True returns the orchestration trace: the model’s rationale, the chosen action group and parameters, the observation (tool result), and the final response. For agents on AgentCore, you instrument with ADOT and the platform reads agent input, output, tool calls, and per-step latency from the spans. In a multi-agent system, a supervisor delegates to sub-agents. The trace must carry context across those hops (OpenTelemetry context propagation, or a shared sessionId and parent span ID passed in the sub-agent call) so that the whole delegation tree appears as one trace and not as unrelated fragments. Without that, you will see a slow supervisor and an unrelated slow worker and never link them.

    Usage baselines for anomaly detection

    Once tool metrics exist, give each tool a baseline: the normal calls per request, error rate, and latency. Use CloudWatch anomaly detection on ToolLatencyMs and calls per hour per tool. A tool whose calls suddenly double after a prompt change, or a tool that drops to zero (the model stopped using it), is signal.     “Why did the agent choose this tool” is answered by the agent trace (rationale), not by CloudTrail or metrics. “Which tool is slow across all requests” is answered by per-tool latency metrics. “Detect an agent looping” is answered by counting tool or model calls per request or session and alarming on a ceiling, backed by a hard cap on iterations in the code.

    Automated index optimization

    Vector indexes degrade as data changes. Updates and deletes leave dead entries, segments multiply, and an approximate-nearest-neighbor (ANN) graph built on old data loses recall. Routine maintenance should be scheduled and measured, not done by hand:

    • OpenSearch: force-merge read-mostly indexes to reduce segment count, rotate or reindex when mapping parameters (such as the HNSW graph settings m and ef_construction) change, and check shard sizes against your search-latency target. Use Index State Management policies to automate rollover and delete.
    • pgvector: run VACUUM and ANALYZE after bulk change, and rebuild an IVFFlat index after large data shifts because its cluster centroids are chosen at build time. HNSW indexes cost more to build but tolerate growth better. Tune hnsw.ef_search or ivfflat.probes at query time for the recall and latency you need.
    • Measure recall, not just speed. Keep a small set of queries with known relevant chunks and compute recall at k (how many of the known-relevant chunks appear in the top k). Run it after each maintenance job, and alarm if it falls under your floor.

    Wire the schedule with Amazon EventBridge Scheduler invoking a Lambda function (or a Step Functions workflow for multi-step jobs) that runs the maintenance call, then the recall check, then publishes the result as a metric.

    import boto3, json, time
cw = boto3.client("cloudwatch")

def recall_at_k(search, probes, k=5):
    """probes: list of {'query': str, 'relevant_ids': set[str]}"""
    hits = total = 0
    for p in probes:
        got = {r["id"] for r in search(p["query"], k)}
        hits += len(got & p["relevant_ids"])
        total += len(p["relevant_ids"])
    return hits / total if total else 0.0

def handler(event, context):
    score = recall_at_k(search_fn, load_probes())
    cw.put_metric_data(Namespace="GenAIApp/Vector", MetricData=[
        {"MetricName": "RecallAt5", "Value": score, "Unit": "None",
         "Dimensions": [{"Name": "Index", "Value": "docs-v3"}]}])
    return {"recall": score}

    Data quality validation

    Stale or wrong data is the most common cause of a bad RAG answer, and no index setting fixes it. Add checks that run after each ingestion and on a schedule:

    • Freshness: the age of the newest and oldest chunk per source, from a last_updated metadata field. Alarm when a source has not updated within its expected window (this is the data maintenance loop made observable).
    • Completeness: document count in the source of truth against chunk-bearing document count in the index. Gaps mean failed ingestion.
    • Duplicates: repeated chunk hashes crowd out diverse results.
    • Schema and metadata: required fields (source URI, access tag, timestamp) are present. Missing access tags are a security defect, because metadata filters used for tenant isolation will fail open or closed depending on your query.
    • Embedding consistency: every vector has the dimension and model version you expect. Mixing embedding models in one index silently destroys similarity.

    AWS Glue Data Quality or a Lambda function can run these rules and publish pass/fail counts as metrics, using the same approach described for pipeline validation in Domain 1.

    Exam tip

    If a scenario says the cluster is healthy but answers are wrong or outdated, the problem is data quality or index drift, and the fix is validation and scheduled refresh, not a bigger instance. If search latency climbs as data grows, look at shard sizing, index parameters, memory for the graph, and the number of segments before adding nodes.

    Golden datasets

    A golden dataset is a curated set of inputs with expected outputs or expected properties, kept under version control. For a RAG app, each entry holds a question, the source passages that should be retrieved, and either a reference answer or a list of facts the answer must contain (and facts it must not). You replay it against the live pipeline and score each response. Because exact string matching fails on free text, score with a judge model, with fact checklist matching, or with embedding similarity to the reference.

    import json, boto3
bedrock = boto3.client("bedrock-runtime")

def check(question, answer, must_include, must_not_include):
    missing = [f for f in must_include if f.lower() not in answer.lower()]
    forbidden = [f for f in must_not_include if f.lower() in answer.lower()]
    return {"q": question, "missing": missing, "forbidden": forbidden,
            "pass": not missing and not forbidden}

def run_golden(path, ask):
    results = [check(g["q"], ask(g["q"]), g["must_include"], g.get("must_not_include", []))
               for g in map(json.loads, open(path))]
    rate = sum(r["pass"] for r in results) / len(results)
    return rate, [r for r in results if not r["pass"]]

    Run it on every prompt or model change in CI, and nightly against production, publishing the pass rate as a metric with an alarm. Seed it from real failures: each time a user reports a bad answer, add that question. Treat it as the regression suite for behavior.

    Output diffing and consistency analysis

    To measure consistency, send the same prompt N times (for example 5 at your production temperature) and compare the answers. For short factual answers compare normalized strings. For longer text compute pairwise embedding similarity, or ask a judge whether two answers contradict each other. A low average similarity, or any contradiction, flags an unstable prompt. Use the same technique across versions: run the golden set on the old and the new prompt and diff the outputs, so you see which questions changed rather than just a single average. High variance usually calls for lower temperature, a tighter prompt, a structured output schema, or better retrieval.

    Reasoning path tracing

    When the answer is wrong but the sources were right, inspect the steps in between. For agents, read the orchestration trace: what the model said it would do, which tool it called, what came back, and whether it used the result. For models that return reasoning content, the Converse response can include a reasoning block you can store with the trace (keep it in a restricted location, since it can include sensitive intermediate content). Look for characteristic faults: the model ignored the retrieved passage, called a tool with an argument copied from the wrong place, or stopped after a tool error and invented a result. Tag these in your trace data so that you can count them by type.

    Specialized observability pipelines

    The exam phrase “specialized observability pipelines” means a data path built for FM telemetry: invocation logs and traces flow into a store where you can sample, score, and analyze them offline. A common AWS design: invocation logs land in S3, an S3 event or a scheduled EventBridge rule triggers a Lambda or Step Functions workflow that samples records, calls a judge model, writes scores back (to S3 as Parquet and to CloudWatch as metrics), and an Athena or QuickSight view serves analysts. Low-score records are queued for human review, and reviewed items flow into the golden dataset. This closes the loop from production to test data.

    Watch out

    A judge model is another model with its own biases and cost. Calibrate it: have people rate a sample, compare with the judge, and re-check when you change the judge. Do not use the same model to both generate and judge the same answer if you can avoid it, because models tend to rate their own style higher.

    Chapter recap

    • GenAI monitoring adds token spend, split latency (first token and total), quality, drift, and the request fan-out to the classic metrics, logs, and traces.
    • Bedrock publishes AWS/Bedrock metrics by ModelId; you add business, quality, cache, and tool metrics yourself, with EMF as the low-overhead default and low-cardinality dimensions.
    • Traces (ADOT or X-Ray, Bedrock Agents enableTrace, AgentCore observability) show where time and errors sit. Record model, token usage, and stopReason as span attributes and keep prompt content out of spans.
    • Model invocation logs capture full requests and responses to CloudWatch Logs and S3. Use requestMetadata to make them searchable, treat them as sensitive data, and use CloudTrail for who-did-what on the control plane.
    • Alarm on token bursts with threshold or anomaly detection alarms, on drift with proxy metrics, on quality with grounding, judge, and golden-set scores, and on spend with Cost Anomaly Detection and Budgets.
    • Build separate dashboards for operations, business, compliance, and model behavior, and design audit fields (request ID, model and prompt versions, tamper-resistant storage) before you need them.
    • Wrap every tool for per-tool latency, errors, and call counts, propagate trace context across agents, and baseline tool use for anomalies.
    • Monitor the vector store at the cluster, index (recall, segments, rebuilds), and data (freshness, completeness, duplicates, embedding consistency) levels.
    • Troubleshoot with golden datasets, output diffing, reasoning path traces, and a sampling pipeline that feeds reviewed failures back into the test set.

    Knowledge check

    1. A support chatbot’s p99 latency doubled yesterday. Metrics show Bedrock InvocationLatency is flat. The chatbot calls a retrieval step, then Bedrock, then an order-status API. What is the fastest way to find the slow step?

      Answer

      Distributed tracing with spans around retrieval, the model call, and the tool call (ADOT or X-Ray), viewed for slow traces. Because model latency is flat, the time is elsewhere, and only per-step spans show where. Invocation logs show content and tokens, not step timing across your services. CloudTrail records API calls for audit, not latency. Raising Bedrock quotas does not help if the model is not the slow part.

    2. A finance team needs to know which product feature caused a 4x jump in output tokens last Tuesday, and the engineers want the full prompt for the worst offenders. Bedrock metrics show the jump by model only. What combination answers this?

      Answer

      Enable model invocation logging to CloudWatch Logs or S3, tag calls with requestMetadata (feature, prompt version), and query by feature in Logs Insights or Athena. The logs also hold the prompts. AWS/Bedrock metrics have no feature dimension. CloudTrail does not store prompt content or token counts. Cost Explorer by tag shows spend by tagged profile but not the prompt text and has a delay.

    3. Traffic to a GenAI summarization API peaks every weekday morning and is near zero overnight. The team wants an alert when token use is unusual for the time of day, without hand-tuning thresholds. Which alarm fits?

      Answer

      A CloudWatch anomaly detection alarm on the token metric, which learns daily and weekly patterns and alarms when the value leaves the expected band. A static threshold is either too high to catch overnight anomalies or too low and noisy at the morning peak. AWS Budgets works on spend limits with billing delay and cannot detect a burst within minutes. Cost Anomaly Detection also works on billing data with delay.

    4. A compliance reviewer asks for proof of which prompt version and guardrail produced a specific answer sent to a customer six months ago, and proof that the records were not altered. What should the design have recorded?

      Answer

      A request ID carried in requestMetadata, traces, and app logs; the concrete model ID or profile ARN, prompt version, and guardrail ID and version in the record; and storage with tamper resistance (S3 with Object Lock or restricted log groups, CloudTrail log file validation), retained for the required period. Metrics alone cannot reconstruct one interaction. An alias such as “latest” is not identifying six months later. Short log retention would have deleted the evidence.

    5. A RAG assistant’s OpenSearch cluster is green and fast, but users complain that answers cite last year’s policy. Which monitoring would have caught this, and what is the remedy?

      Answer

      Data freshness and completeness checks on the index (age of newest chunk per source, source-of-truth count versus indexed count, ingestion job failures) with alarms, plus a golden dataset that includes questions on recently changed policies. The remedy is to fix and schedule the ingestion or sync pipeline and re-index. Adding nodes or tuning HNSW parameters addresses speed or recall, not stale content. A larger model cannot know the policy changed.

    6. After a prompt edit, nobody saw errors, but a week later support says answers feel less accurate. How do you prevent this class of silent regression in future, and how do you detect it live?

      Answer

      Prevent with a golden dataset replayed in CI on every prompt or model change, comparing pass rate and diffing outputs against the previous version. Detect live with sampled LLM-as-a-judge or grounding scores published as CloudWatch metrics with a drift alarm, plus user feedback rates segmented by prompt version. HTTP error rate and latency would not move, so classic uptime monitoring cannot see it.

    Problem statement

    The scenario

    An online electronics retailer runs a support assistant. It answers product and policy questions from a Knowledge Base and calls three tools: get_order_status, check_stock, and start_return. It has been live for a month. On Monday the support lead reports that “the assistant feels worse” and that the Bedrock bill is up 40 percent. Nobody can say whether either claim is true, when it started, or which change caused it. The error-rate graph is flat, because every call returned HTTP 200.

    Build an observability stack with these properties:

    • One dashboard shows, per hour and per model: requests, input and output tokens, estimated cost, p50 and p95 latency, time to first token, throttles, and errors. A second panel shows business signals: answers rated helpful, handoffs to a human, and resolved-without-handoff rate.
    • Every request has a request_id and a trace that shows the retrieval call, each tool call, and each model call as timed segments, so a slow answer can be explained.
    • Bedrock model invocation logging is on, and three saved Logs Insights queries answer: which callers use the most tokens, which prompts have the longest outputs, and what happened for a given request_id.
    • An alarm fires within minutes when token usage bursts well above its normal pattern for the time of day, and another when the daily cost trend departs from normal.
    • Every tool call is logged with tool name, argument shape, latency, outcome, and the number of calls in the conversation. An alarm fires when a tool’s error rate or per-conversation call count leaves its baseline.
    • The vector store is monitored for query latency, errors, and document count, and a scheduled job checks that recently added documents are retrievable and that no chunk is empty or duplicated.
    • A golden dataset of 40 questions with accepted answers runs nightly and on every prompt or model change. The run reports a quality score, a consistency score between repeated runs, and a diff against the previous run, and publishes the scores as metrics.

    The exam phrases the same situation as “a company notices that costs and response quality have drifted and needs to detect this proactively with the least operational overhead”. The answers it rewards are managed signals first: CloudWatch metrics and anomaly detection alarms, model invocation logging queried with Logs Insights, X-Ray or OpenTelemetry traces, Cost Anomaly Detection, and a golden dataset for failure modes that ordinary metrics cannot see. Use synthetic orders and synthetic customers only. Invocation logs hold full prompts and answers, so no real personal data belongs in this project.

    Follow one question through the request path. The FastAPI service creates a request_id and opens a trace. It calls the Knowledge Base, then calls Converse with the tool definitions. When the model asks for a tool, the service runs the Python function, times it, and sends the result back, repeating until the model gives a final answer. Each step is a span inside the trace. Bedrock writes the full request and response to the invocation log on its own, because invocation logging is an account-level setting (see the three kinds of logs). Bedrock also publishes its own runtime metrics under the AWS/Bedrock namespace. The service adds what Bedrock cannot know: a structured log line in CloudWatch Embedded Metric Format (EMF), which CloudWatch turns into custom metrics for tokens per request, estimated cost, tool latency, retrieval latency, and the business signals. Dashboards and alarms read from the metrics. Logs Insights reads from the logs. The trace links the two through the request_id.

    The design has three key decisions. The first is to emit metrics as log lines (EMF) instead of calling put_metric_data on every request. One log line carries both the dimensions you can chart and the high-cardinality fields (request_id, user_id) you only search, so a metric and its evidence live together, and the service makes no extra API call on the request path. The trade-off is that EMF metrics appear after a short ingestion delay and each distinct dimension combination is a billed custom metric, so keep dimensions to model, tool, and environment. The second decision is to baseline before alarming. A fixed token threshold is wrong at 3 a.m. and wrong at noon, so token and cost alarms use anomaly detection, which learns the hourly and weekly shape. The third is to measure quality directly. A golden dataset run is the only signal here that notices “every call succeeded and the answers got worse”, so it publishes its score as a metric on the same dashboard.

Add requestMetadata with your request_id to every Converse call so records can be joined. Save three Logs Insights queries: top callers by tokens, longest outputs, and everything for one request_id.
    4. TracingAdd OpenTelemetry instrumentation with a span around retrieval, one around each model call, and one around each tool call. Put request_id, model ID, token counts, and tool name on the spans as attributes. Run the ADOT collector as a sidecar container, send traces to X-Ray, and confirm a slow request shows exactly where the time went on the service map and trace view.
    5. The dashboardBuild a dashboard from code with put_dashboard: an operations row (requests, tokens, cost, p50 and p95 latency, time to first token from your own EMF metric, throttles, errors, from AWS/Bedrock and your namespace) and a business row (helpful rate from /feedback, handoff rate, resolved-without-handoff rate). Generate synthetic traffic with a script that varies question type and rate, and check that every widget moves.
    6. Anomaly alarms and a cost guardCreate anomaly detection alarms on input tokens and estimated cost with a learned band, and static alarms on throttles and server errors. Create an AWS Cost Anomaly Detection monitor for the account, with an SNS subscription. Test by sending a burst of long prompts and confirming the token alarm moves to ALARM. Then add a daily budget in AWS Budgets as a backstop for the case where the anomaly model has not yet learned the pattern.
    7. Tool telemetry and baselinesWrite a decorator that wraps each tool and records latency, outcome (ok, error, timeout), argument shape without values, and the call index within the conversation, as an EMF line and a span. Add alarms on per-tool error rate and on the maximum calls per conversation.     9. The golden dataset, consistency, and diffsWrite 40 questions with accepted answers, including five that need a tool, five that are out of scope and should be declined, and five that are close paraphrases. Run each three times. Score each answer with a judge model against the accepted answer, score consistency as the average cosine similarity between the three embeddings, and write a diff of answers against the previous run to S3. Publish GoldenQuality and GoldenConsistency as metrics, schedule the run nightly with EventBridge Scheduler, and add an alarm on a drop below the band.

Swap in a cheaper model (cost should fall, quality should move, and the model dimension should change). Break the tool schema (tool error alarm and the trace should point at it). Delete a document from the Knowledge Base source (the canary or golden run should notice). For one bad answer, use the trace and invocation record together to explain the cause in writing.

    Definition of done

    • The dashboard shows tokens, estimated cost, p50 and p95 latency, time to first token, throttles, and errors per model, and the numbers match the sum of the usage fields in your own logs for a one-hour test window.
    • Given a request_id, one saved Logs Insights query returns the app log lines, and another returns the matching invocation record with the full prompt and completion.
    • A trace for a slow request shows separate timed segments for retrieval, each tool call, and each model call.
    • A synthetic burst of long prompts moves the token anomaly alarm to ALARM and sends an SNS message, while normal traffic at the same hour does not.
    • A forced check_stock failure triggers the tool error alarm, and the metric and trace both show the failing tool by name.
    • Removing the canary document’s source makes CanaryFound drop to 0 and the alarm fire within two check periods.
    • The golden run publishes GoldenQuality and GoldenConsistency, writes a diff to S3, and the quality alarm fires when you set max_tokens too low.
    • You can explain one wrong answer using the trace, the invocation log, and the golden diff, and write down which signal would have caught it first.
    • The log groups have a KMS key and a retention period, and a delete script removes every resource you created.

    Cost, Region, and account notes

    Watch out

    Use a sandbox account and your assigned Region, and confirm that your chosen models, the Knowledge Base, and X-Ray are available there. CloudWatch Logs bills per GB ingested, and invocation logging writes every full prompt and completion, so a chatty test script can produce a surprising bill. Set retention, keep prompts short, and delete the log groups at the end. Custom metrics are billed per metric per month, and every unique combination of dimension values is a separate metric, so putting request_id or user_id in a dimension creates one metric per request. Keep those fields in the log line and out of the dimensions. Anomaly detection alarms and dashboards also have per-item charges. X-Ray bills per trace recorded and retrieved, so sample if you run steady traffic. The golden run multiplies quickly: 40 questions times 3 repeats times a judge call is 240 model calls per run, so use a small, cheap model and run the full set nightly, not on every commit. Cost Anomaly Detection needs some days of spend history before it can learn, and AWS Billing data can lag, so do not expect an alert within minutes. Check current prices on each service’s pricing page.

    Invocation logs contain the original text of every prompt. Guardrail masking changes only the API response, not the log, so use synthetic data, a KMS key, and tight IAM on the log groups. Classic Bedrock Agents is closed to new customers, so if you add an agent, use AgentCore and its observability for traces.

    Expected spend for one pass through the build path is a few dollars of model and judge tokens if you keep the sets small, plus small amounts for logs, custom metrics, alarms, traces, and a Fargate task running a few hours. The largest risks are leaving a traffic generator running, adding high-cardinality dimensions to EMF, rerunning the golden set on a large model, and leaving invocation logging on in a busy account. Stop the service and the schedules between sessions, and delete the stack when you finish.

    Stretch ideas

    Toward Domain 5, turn the golden dataset into a full evaluation harness with Bedrock Evaluations and A/B comparisons of prompt or model changes. Toward earlier domains, add a cost guard that routes to a cheaper model when the budget alarm fires (Domain 4.1), and add a hallucination-rate metric from a grounding check (Domain 3). Add a composite alarm that combines quality, tool errors, and cost into a single page-worthy signal. Export invocation logs to S3 and query them with Amazon Athena for a monthly report, or try a managed GenAI observability view in CloudWatch and compare what it shows against your own dashboard.
