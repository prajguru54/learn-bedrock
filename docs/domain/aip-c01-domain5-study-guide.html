    Chapter 1 · Task 5.1

    Implement Evaluation Systems for GenAI

    A foundation model (FM) application can return HTTP 200 on every call and still be wrong, rude, or quietly worse than last week. This chapter builds the measurement layer: what to measure when the output is free text, how to score it with Bedrock evaluation jobs and your own LLM judges, how to gather user feedback, and how to turn all of it into regression tests, release gates, reports, and deployment checks.

    Why GenAI evaluation is a different problem

    In classic machine learning you have a label for every input and a metric that compares the prediction to the label: accuracy, F1, RMSE. The test set is fixed, the answer is a number or a class, and a single score tells you whether the model got better. A generative model breaks each of those assumptions. The output is open-ended text, many different outputs are equally correct, the same prompt can yield different answers on different calls, and "correct" often depends on context the model was handed at run time (retrieved chunks, tool results, a system prompt). You still need a number to gate a release, so the work of this chapter is building defensible numbers out of fuzzy outputs.

    You already know prompts, RAG, and agents from earlier chapters, so this chapter spends its words on the AWS layer: Amazon Bedrock Evaluations (managed evaluation jobs), the surrounding services you wire into an evaluation pipeline (Amazon S3, AWS Lambda, Amazon CloudWatch, AWS Step Functions, AWS CodePipeline, Amazon QuickSight), and the design patterns the exam expects you to recognise.

    Backend analogy

    Think of evaluation as the test suite plus the observability stack for a service whose function bodies are non-deterministic. Unit tests become a golden dataset with scored assertions, integration tests become end-to-end synthetic workflows, and the CI gate becomes a threshold on aggregate scores instead of a pass or fail on a single assertion.

    Four things that make GenAI evaluation hard

    • No single ground truth. "Summarise this ticket" has thousands of acceptable summaries. You compare against a reference loosely, or you score against criteria instead of an answer.
    • Non-determinism. With a temperature above zero, one prompt gives a distribution of outputs. A test that passes once proves little. You sample several times and look at the spread.
    • Many quality dimensions. An answer can be factually right and badly written, or fluent and invented. You track dimensions separately and decide which ones block a release.
    • Silent change. A provider updates a model version, you edit a prompt, an index is rebuilt: any of these shifts behaviour without a code error. Evaluation is how you notice.

    The evaluation loop

    Every system in this chapter is a variation of one loop. You hold a dataset of inputs (and ideally reference answers), run your candidate configuration over it, score the outputs, aggregate the scores, compare them with a baseline or a threshold, and act on the result.

    Metrics beyond accuracy (Skill 5.1.1)

    Skill 5.1.1 asks for an assessment framework, which in practice means a named list of quality dimensions, a definition of each, a way to score each, and a rule for how the scores combine. The exam names four: relevance, factual accuracy, consistency, and fluency. Real systems add several more.

    DimensionQuestion it answersTypical way to score it
    RelevanceDoes the answer address what the user asked?LLM judge with a rubric, or embedding similarity between question and answer
    Factual accuracy (correctness)Does the answer match known facts or the reference answer?Judge compared with a reference answer, exact or fuzzy match on extracted facts
    Faithfulness (groundedness)In RAG, is every claim supported by the retrieved context?Judge that checks each claim against the context. The main hallucination detector for RAG
    CompletenessDoes the answer cover everything the question needs?Judge against a reference or a checklist of required points

    Fluency and styleIs it readable, well formed, and in the right tone?Judge rubric. Rarely the blocking metric

    Three kinds of scorer

    Scorers differ in cost, determinism, and how well they handle open-ended text. A mature framework uses all three, cheapest first.

    1. Programmatic checks. Regex, JSON schema validation, length limits, required keywords, "answer must cite a source id". They are free, instant, and deterministic, so they run on every case and fail fast. Use them for anything you can express as code.
    2. Reference-based similarity metrics. Classic NLP scores such as ROUGE (n-gram overlap, used for summarisation), BLEU (translation), and BERTScore (embedding similarity of tokens) compare output to a reference. They are cheap and repeatable but reward wording overlap, so a correct paraphrase can score low. The Bedrock automatic evaluation metrics (accuracy, robustness, toxicity) belong to this family. Treat them as a coarse signal.
    3. Model-based scoring (LLM-as-a-judge). A second, usually stronger, model reads the question, the answer, and optionally a reference or context, and returns a score and an explanation against a rubric. It handles open-ended text well and scales to thousands of cases, at the price of token cost, some bias, and some noise. Covered in the judge section.

    Human review is the fourth scorer and the calibration anchor for the other three, covered in the feedback section.

    Exam tip

    When a question says the team needs to evaluate "beyond traditional ML metrics" for open-ended generation, the answer almost always combines several dimensions (relevance, factual accuracy, consistency, fluency) with a mix of automated scoring and human evaluation. A single accuracy number, or a single reference-overlap metric such as ROUGE on its own, is the distractor.

    Building the golden dataset

    The dataset is the most valuable artifact in the system, because every score is only as meaningful as the cases behind it. A workable recipe:

    • Start small and real. 50 to 200 cases drawn from real production questions (anonymised), support tickets, or subject-matter-expert (SME) written examples. A hundred good cases beat ten thousand synthetic ones for catching regressions.
    • Cover categories. Tag each case (category such as billing, refunds, edge-case, adversarial, out-of-scope). Aggregate scores per category so a regression in one slice is not hidden by an average.
    • Include reference answers where you can, and rubric notes where you cannot. For RAG, store the expected source document ids as well, which enables retrieval scoring.
    • Add negative cases. Questions the system should refuse or answer with "I don't know", prompt-injection attempts, empty inputs.
    • Grow it from failures. Every production bug becomes a case. Every low user rating is a candidate.
    • Version it. Keep the dataset in S3 with versioning on, and record the dataset version with every evaluation result, so two runs are comparable.

    Synthetic generation (asking a model to write questions from your documents) is a legitimate way to bootstrap coverage, especially for RAG, but have a human review a sample, because generated questions tend to be easier and more keyword-matching than real user questions.

    Measuring consistency

    Consistency is the dimension most often skipped. Two cheap tests cover it. First, repeat each prompt several times (say 5) at your production temperature and compute the average pairwise embedding similarity of the answers, or ask a judge whether the answers agree on the key facts. Second, paraphrase the question and check that the answers match. Low consistency means the prompt under-specifies the task, the temperature is too high, or retrieval is returning different chunks each time. A short Boto3 sketch of the first test:

    import itertools, json, boto3
import numpy as np

brt = boto3.client("bedrock-runtime")

def embed(text: str) -> np.ndarray:
    r = brt.invoke_model(
        modelId="amazon.titan-embed-text-v2:0",
        body=json.dumps({"inputText": text}),
    )
    return np.array(json.loads(r["body"].read())["embedding"])

def ask(model_id: str, prompt: str, temperature: float = 0.7) -> str:
    r = brt.converse(
        modelId=model_id,
        messages=[{"role": "user", "content": [{"text": prompt}]}],
        inferenceConfig={"maxTokens": 400, "temperature": temperature},
    )
    return r["output"]["message"]["content"][0]["text"]

def consistency(model_id: str, prompt: str, n: int = 5) -> float:
    answers = [ask(model_id, prompt) for _ in range(n)]
    vecs = [embed(a) for a in answers]
    sims = [
        float(a @ b / (np.linalg.norm(a) * np.linalg.norm(b)))
        for a, b in itertools.combinations(vecs, 2)
    ]
    return sum(sims) / len(sims)   # 1.0 means identical meaning

    Embedding similarity is blunt: two answers with opposite conclusions can score high because they share vocabulary. Use it to find unstable prompts, then confirm with a judge on the low-scoring ones.

    Amazon Bedrock Evaluations (Skills 5.1.2 and 5.1.5)

    Amazon Bedrock Evaluations is the managed way to score models and RAG systems without writing the harness yourself. You hand it a dataset in S3, a list of metrics, and the models or knowledge bases to test, and it runs inference, scores the outputs, and writes results back to S3 with a report in the console. There are two application types, set by the applicationType field of the API (ModelEvaluation or RagEvaluation), and three ways to score.

    Evaluation styleWho scoresUse it forTrade-off
    Automatic (programmatic)Built-in algorithmsQuick, cheap, repeatable checks on well-defined tasks: summarisation, question answering, classification, text generation. Metrics such as accuracy, robustness, and toxicityOverlap-style metrics miss meaning. Best as a coarse signal
    Model as a judgeAn evaluator FM you chooseOpen-ended quality: correctness, completeness, helpfulness, coherence, tone, harmfulness. Also RAG metrics such as faithfulness and context relevanceCosts tokens for both the generator and the judge. Judge bias and noise
    HumanYour own workforce (or an AWS-managed one) via a work teamSubjective quality, brand voice, domain correctness, calibration of the judgeSlowest and most expensive. Needs a work team and instructions

    Exam tip

    "Compare several FMs on our own prompts, with no custom evaluation code, and get quality scores plus a report" points to a Bedrock Model Evaluation job. "Measure whether a RAG answer is grounded in the retrieved documents" points to a Bedrock RAG evaluation (faithfulness, context relevance). "Capture subjective judgement from our domain experts" points to a human evaluation job.

    What the job needs

    All evaluation jobs run under an IAM service role you supply (roleArn) that Bedrock assumes. The role needs read access to the dataset bucket, write access to the output prefix, and permission to invoke the models involved (the models under test and, for judge jobs, the evaluator model). The trust policy must name bedrock.amazonaws.com, and AWS recommends confused-deputy conditions (aws:SourceAccount and aws:SourceArn) on it, as in the earlier domains. If the dataset bucket is browser-accessed from the console, it also needs a CORS configuration (the console tells you this at job creation). Check the current documentation for the exact policy statements, because they change as features are added.

    The dataset format

    Datasets are JSON Lines (.jsonl) files in S3, one record per line. For model evaluation, the common shape is a prompt, an optional reference response, and an optional category used to break results down:

    {"prompt": "Summarise the refund policy in two sentences.", "referenceResponse": "Refunds are issued within 30 days of purchase. Digital goods are not refundable once downloaded.", "category": "policy"}
{"prompt": "What is the capital of Australia?", "referenceResponse": "Canberra", "category": "geography"}

    RAG evaluation datasets use a conversation-turn shape (prompt content blocks, plus reference responses and, for some metrics, reference contexts). The field layout is more nested than the model case, and it differs again when you supply precomputed responses from your own pipeline instead of letting Bedrock run the knowledge base. Treat the layout in this guide as the general pattern and copy the exact schema from the current Bedrock evaluation documentation before you build the file. Do the same for the list of built-in metric names: the API accepts them as plain strings in metricNames, so a typo is a runtime error, not a compile error.

    Creating a job with Boto3

    The control-plane client is bedrock (not bedrock-runtime). The relevant operations are create_evaluation_job, get_evaluation_job, list_evaluation_jobs, stop_evaluation_job, and batch_delete_evaluation_job. The request has these required parts: jobName, roleArn, evaluationConfig, inferenceConfig, and outputDataConfig. The skeleton of an automatic model evaluation of one model over a custom dataset looks like this. The metric strings are examples of the built-in names, so confirm them in the console job wizard or the documentation for your Region:

    import boto3

bedrock = boto3.client("bedrock")

BUCKET = "my-eval-bucket"
ROLE_ARN = "arn:aws:iam::111122223333:role/BedrockEvalRole"
MODEL_ID = "us.amazon.nova-lite-v1:0"   # use a model you have access to

resp = bedrock.create_evaluation_job(
    jobName="qa-eval-nova-lite-001",
    jobDescription="Automatic eval on the support golden set",
    roleArn=ROLE_ARN,
    applicationType="ModelEvaluation",
    evaluationConfig={
        "automated": {
            "datasetMetricConfigs": [{
                "taskType": "QuestionAndAnswer",   # Summarization | Classification | QuestionAndAnswer | Generation | Custom
                "dataset": {
                    "name": "support-golden-v1",
                    "datasetLocation": {"s3Uri": f"s3://{BUCKET}/datasets/support-golden-v1.jsonl"},
                },
                "metricNames": ["Builtin.Accuracy", "Builtin.Robustness", "Builtin.Toxicity"],
            }]
        }
    },
    inferenceConfig={
        "models": [{
            "bedrockModel": {
                "modelIdentifier": MODEL_ID,
                "inferenceParams": '{"inferenceConfig":{"maxTokens":512,"temperature":0.2}}',
            }
        }]
    },
    outputDataConfig={"s3Uri": f"s3://{BUCKET}/eval-results/"},
)
job_arn = resp["jobArn"]

# Poll until finished (InProgress, Completed, Failed, Stopping, Stopped, Deleting)
status = bedrock.get_evaluation_job(jobIdentifier=job_arn)["status"]

    Notes on the pieces. taskType must be one of Summarization, Classification, QuestionAndAnswer, Generation, or Custom, and the allowed metrics depend on it. inferenceParams is a JSON string whose shape depends on the model family, so copy it from the console for your model. A job accepts a small number of models (the console shows the current limit), which is how multi-model comparison works. Alternatively, instead of bedrockModel you can supply precomputedInferenceSource, which lets you evaluate outputs produced elsewhere (a SageMaker endpoint, another provider, your own pipeline) by naming a source identifier that matches a field in the dataset. This "bring your own responses" mode is how you evaluate a model Bedrock cannot call.

    Watch out

    The taskType enum in the current Boto3 model lists Summarization, Classification, QuestionAndAnswer, Generation, and Custom. The judge example above shows a placeholder value for that field (Generation) because the right value for judge jobs is easy to get wrong and I could not confirm it against the current documentation. Build one job in the console, then read it back with get_evaluation_job and copy the exact request shape it shows. That read-back trick is the fastest way to learn any evaluation job configuration.

    Judge jobs support custom metrics through customMetricConfig. A custom metric is a name, an instruction prompt that tells the judge how to rate, and a rating scale. Use them for business-specific criteria such as "does the answer follow our refund policy wording" or "does the tone match the brand guide". Metric names must be unique within a Region.

    RAG evaluation

    A RAG evaluation job (applicationType="RagEvaluation") uses ragConfigs in the inferenceConfig instead of models. Each RAG source is either a Bedrock Knowledge Base that Bedrock calls for you or a precomputed source containing responses you already generated. There are two modes, and the difference matters for the exam:

    • Retrieve only. Bedrock calls the knowledge base Retrieve operation and scores the retrieved passages. Metrics are about retrieval quality: context relevance (are the retrieved chunks relevant to the question) and context coverage (do they contain what the reference answer needs, which requires reference answers in the dataset).
    • Retrieve and generate. Bedrock runs retrieval plus generation and scores the final answer as well: correctness, completeness, helpfulness, logical coherence, and the RAG-specific faithfulness (claims supported by the retrieved context), plus citation metrics (citation precision and citation coverage) when the source supplies citations. Responsible-AI metrics such as harmfulness, stereotyping, and refusal are also available.

    These names are what you should recognise on the exam. Verify the exact list for your Region before you build a job, since the set of built-in metrics grows over time.

    Backend analogy

    A Bedrock evaluation job is a managed batch job: input in S3, a role it assumes, a status you poll, output written to S3. It is much closer to an AWS Glue job or a Bedrock batch inference job than to a synchronous API call, which is why the exam expects you to think about the IAM role, the output location, and job status rather than a response body.

    Cost and limits to remember

    You pay for the inference the job performs (the model under test, and the judge for judge jobs) at normal Bedrock rates, plus S3 storage. Judge jobs multiply the token bill because every case produces one generator call and one judge call per metric. Human jobs add the labeling effort. Start with a 20-case dataset and one or two metrics, check the output, then scale up. Dataset size, number of metrics per job, and number of concurrent jobs are limited by quotas, so check Service Quotas rather than assuming a number.

    Custom LLM-as-a-judge in Boto3 (Skill 5.1.5)

    The managed judge covers common metrics. You still write your own judge when you need a rubric the managed metrics do not offer, when you want the evaluation inside your CI pipeline without creating a Bedrock job per run, or when you want per-case control over what the judge sees. The pattern is a structured prompt that returns JSON, called through the Converse API at low temperature:

    import json, boto3

brt = boto3.client("bedrock-runtime")
JUDGE_MODEL = "us.anthropic.claude-sonnet-4-6"

RUBRIC = """You are a strict evaluator. Score the ANSWER to the QUESTION.
Use the REFERENCE and CONTEXT only as evidence. Do not reward length.

Return JSON only:
{"relevance": 1-5, "correctness": 1-5, "faithfulness": 1-5,
 "reasoning": "one or two sentences naming the evidence"}

Scoring guide:
5 = fully correct and grounded, 3 = partly correct or partly unsupported,
1 = wrong, off-topic, or contradicts the context."""

def judge(question, answer, reference="", context=""):
    user = (f"QUESTION:\n{question}\n\nREFERENCE:\n{reference}\n\n"
            f"CONTEXT:\n{context}\n\nANSWER:\n{answer}")
    r = brt.converse(
        modelId=JUDGE_MODEL,
        system=[{"text": RUBRIC}],
        messages=[{"role": "user", "content": [{"text": user}]}],
        inferenceConfig={"maxTokens": 300, "temperature": 0.0},
    )
    text = r["output"]["message"]["content"][0]["text"]
    return json.loads(text[text.index("{"): text.rindex("}") + 1])

    Give the judge an explicit scale with anchors, ask for reasoning (it improves reliability and gives you something to debug), set temperature to 0, and parse defensively, because models sometimes wrap JSON in prose.

    Known judge biases and how to handle them

    • Verbosity bias. Judges prefer longer answers. Add "do not reward length" to the rubric and track answer length next to the score.
    • Position bias. In pairwise comparisons the first answer tends to win. Run each pair twice with the order swapped and count only consistent wins.
    • Self-preference. A model favours text written by itself or its family. Use a judge from a different model family than the generator when you can.
    • Drift of the judge. If the judge model version changes, scores shift. Pin the judge model id and record it with every result.

    Calibrating against humans

    Before trusting a judge, have humans label 30 to 100 cases, then measure agreement (the share of cases where the judge and humans land within one point, or a correlation). If agreement is poor, tighten the rubric, add few-shot scored examples, or move to a stronger judge. Recalibrate whenever the rubric or judge model changes. This is the reason the exam pairs LLM-as-a-judge with human feedback in Skill 5.1.5: the humans validate the judge, and the judge scales the humans.

    Exam tip

    If an option says "use the same model that generated the answer to grade it, to keep costs low", it is a trap: self-preference bias. Better answers use a different or stronger judge, a rubric with anchored scores, and human spot checks.

    Comparing models and configurations (Skill 5.1.2)

    "Which model, prompt, and parameter set is best?" is never answered by quality alone. The exam wants you to weigh quality against cost and latency, and to roll out the winner safely. The method has three parts: an offline comparison on the golden set, a cost-performance analysis, and an online test on real traffic.

    Offline multi-model evaluation

    Run the same dataset through every candidate (model by prompt by parameter set) and record, for each case: the output, the quality scores, input and output tokens, and latency. A Bedrock evaluation job can compare models in one job, and a custom harness gives you the extra columns. The Converse response carries what you need for the cost columns:

    import time, boto3
brt = boto3.client("bedrock-runtime")

def run_case(model_id, prompt, max_tokens=400, temperature=0.2):
    t0 = time.perf_counter()
    r = brt.converse(
        modelId=model_id,
        messages=[{"role": "user", "content": [{"text": prompt}]}],
        inferenceConfig={"maxTokens": max_tokens, "temperature": temperature},
    )
    return {
        "text": r["output"]["message"]["content"][0]["text"],
        "in_tokens": r["usage"]["inputTokens"],
        "out_tokens": r["usage"]["outputTokens"],
        "latency_ms": r["metrics"]["latencyMs"],          # model-side latency
        "wall_ms": int((time.perf_counter() - t0) * 1000),  # includes network
    }

    Cost-performance analysis

    Turn the raw numbers into comparable ratios. Prices vary by model and change, so read them from the Bedrock pricing page at the time you run the analysis and keep them in a config file.

    RatioFormulaWhat it tells you
    Cost per request(in_tokens x input price) + (out_tokens x output price)Unit economics at the current prompt size
    Quality per dollarmean quality score / cost per requestWhich model buys the most quality
    Token efficiencyquality score / output tokensWhether a model is wordy for the same quality
    Latency-to-qualityp95 latency / quality score, or quality at a latency budgetWhether the better model still meets the user-facing latency target
    Business outcomeTask success, resolution rate, conversion, escalation rateWhether a quality gain moves the metric the business cares about

    A frequent finding is that a mid-tier model reaches 95 percent of the top model's quality at a fraction of the cost, and that routing easy requests to the small model and hard ones to the large one beats either alone (the tiering technique from Domain 4). Report the whole table, not a single winner, so stakeholders can pick the trade-off.

    A/B and canary testing in production

    Offline sets never match live traffic exactly, so confirm the offline winner online. Two patterns:

    • A/B test. Split users (not requests, so one user sees a consistent variant) by a stable hash, for example 50/50 between the current and candidate configuration. Log the variant with each request and compare user ratings, task success, cost, and latency. Run long enough to get a usable sample, and watch guardrail metrics (error rate, safety flags) as stop conditions.
    • Canary. Send a small slice (1 to 5 percent) to the candidate, watch the metrics, and ramp up in steps if they hold, or roll back instantly if they do not. A canary is a safe-rollout tool, an A/B test is a measurement tool. They use the same plumbing.

    On AWS the split can live in several places: weighted routing in Amazon API Gateway canary releases or an Application Load Balancer weighted target group, a Lambda alias with weighted traffic shifting, an AWS AppConfig feature flag or configuration profile that selects the model id or prompt version, or simple application code. AppConfig is attractive because the model id and prompt version become configuration you change without a deploy, with gradual rollout and automatic rollback on a CloudWatch alarm. For prompt variants specifically, Bedrock Prompt Management versions give you immutable, referenceable prompt versions to put in each arm (see Domain 1 on switching models and prompts).

    A/B testing needs a random, sticky assignment and enough traffic to be meaningful. Canary testing is about limiting the blast radius of a bad release.     User-centered evaluation and feedback (Skill 5.1.3)

    Automated scores approximate quality. Users and domain experts are the ground truth for it. Skill 5.1.3 asks you to build the channels that capture their judgement and feed it back into improvement. There are three layers, from cheapest to richest.

    1. Implicit signals. Behaviour you log without asking: the user copies the answer, regenerates it, rephrases the same question, abandons the session, or escalates to a human. They are noisy but free and abundant.
    2. Explicit ratings. A thumbs up or down, or a 1 to 5 score, with an optional reason (wrong, outdated, unhelpful, unsafe, tone). Keep it one click. Store the rating with the request id so you can join it to the prompt, model, prompt version, retrieved chunks, and trace.
    3. Expert annotation. Reviewers label a sample against a rubric, correct answers, and mark failure causes. This is the layer that calibrates the judge and builds the golden set.

    A feedback pipeline on AWS

    flowchart LR
  UI["Chat UI: thumbs, rating, comment"] --> API["API Gateway + Lambda"]
  API --> DDB["DynamoDB: request_id, rating, reason"]
  DDB --> EXP["Scheduled export to S3"]
  EXP --> ATH["Athena and QuickSight"]
  DDB --> LOW{"Rating low?"}
  LOW -->|"yes"| Q["Review queue"]
  Q --> ANN["Annotators"]
  ANN --> GS["Golden dataset in S3"]

    A minimal feedback endpoint stores the rating together with the identifying context, and publishes a custom metric so a falling satisfaction rate can alarm:

    import json, time, boto3

ddb = boto3.resource("dynamodb").Table("genai-feedback")
cw = boto3.client("cloudwatch")

def handler(event, context):
    body = json.loads(event["body"])
    ddb.put_item(Item={
        "request_id": body["request_id"],        # partition key
        "ts": int(time.time()),
        "rating": body["rating"],                # 1 = down, 5 = up
        "reason": body.get("reason", ""),
        "model_id": body["model_id"],
        "prompt_version": body["prompt_version"],
    })
    cw.put_metric_data(
        Namespace="GenAI/Quality",
        MetricData=[{
            "MetricName": "ThumbsUp",
            "Dimensions": [{"Name": "PromptVersion", "Value": body["prompt_version"]}],
            "Value": 1.0 if body["rating"] >= 4 else 0.0,
            "Unit": "Count",
        }],
    )
    return {"statusCode": 204}

    Watch out

    Do not store prompts and answers in the feedback table without thinking about privacy. They may contain personal data. Store ids and join to the protected invocation logs when needed (see the logging controls in Domain 3), and apply retention rules.

    Annotation workflows

    For structured human review you have three AWS options, and the exam may ask you to choose between them:

    • Bedrock human evaluation jobs. Created through create_evaluation_job with evaluationConfig.human. They take a work team and a rating method you configure, and the API requires a humanWorkflowConfig with a flow definition ARN (an Amazon SageMaker AI Ground Truth style construct) and optional customMetrics. Best when the thing under review is model or RAG output against a fixed dataset and you want Bedrock to run inference and collect ratings in one job.
    • Amazon SageMaker Ground Truth (labeling jobs). A managed data labeling service with private workforces, vendor workforces, and the public Amazon Mechanical Turk workforce, plus built-in label review. Best for large annotation projects with custom task UIs. Check the current availability notes for the service before planning around it.
    • Amazon Augmented AI (A2I). Human review loops that you trigger from your application when a condition is met, for example a confidence below a threshold or a random sample. Best for inline human-in-the-loop approvals on production traffic. Check current service status and Region availability in the documentation before depending on it.
    • A custom review UI over the DynamoDB review queue, when the workflow is small and the reviewers are your own SMEs.

    Whichever you choose, give annotators a written rubric with scored examples, have two reviewers label a subset to measure inter-annotator agreement, and write the results back into the golden dataset with a version bump.

    Exam tip

    "Continuously improve based on user experience" is a loop question. The right answer captures feedback with the request context, aggregates it into metrics, routes low-rated cases to expert review, and feeds the corrected cases into the evaluation dataset and prompt or retrieval changes. A design that only collects thumbs and never closes the loop is the incomplete option.

    Quality assurance, regression tests, and gates (Skill 5.1.4)

    Evaluation that runs once is a benchmark. Evaluation that runs on every change is quality assurance (QA). Skill 5.1.4 is about wiring the scores into your delivery process so that a prompt edit, a model swap, a retrieval change, or a library upgrade cannot reach users without passing the same checks.

    What triggers a run

    • Code or prompt change (pull request): run a fast subset of the golden set.
    • Model or configuration change: run the full set plus consistency checks.
    • Schedule (nightly or weekly): catch silent drift, such as a provider updating a model behind an alias, or an index rebuilt with new documents.
    • Data change: a knowledge base re-ingestion should trigger retrieval and RAG evaluation.

    Regression testing for outputs

    A regression test for text outputs compares the candidate's scores to a stored baseline, not to a fixed expected string. The assertion is of the form "faithfulness mean must not fall by more than 0.03", and "no category may drop by more than 0.05". Store the baseline (scores per case and per category, the dataset version, the model id, the prompt version) as a JSON artifact in S3 from the last release that passed. A minimal comparison:

    import json, sys

THRESHOLDS = {            # hard floors and allowed regression
    "faithfulness":  {"min": 0.85, "max_drop": 0.03},
    "correctness":   {"min": 0.80, "max_drop": 0.03},
    "format_valid":  {"min": 0.99, "max_drop": 0.00},
}

def gate(baseline: dict, candidate: dict) -> list[str]:
    failures = []
    for metric, rule in THRESHOLDS.items():
        base, cand = baseline[metric], candidate[metric]
        if cand < rule["min"]:
            failures.append(f"{metric}: {cand:.3f} below floor {rule['min']}")
        if base - cand > rule["max_drop"]:
            failures.append(f"{metric}: dropped {base - cand:.3f} from baseline")
    return failures

if __name__ == "__main__":
    base = json.load(open("baseline.json"))
    cand = json.load(open("candidate.json"))
    problems = gate(base, cand)
    for p in problems:
        print("FAIL", p)
    sys.exit(1 if problems else 0)

    Because outputs are noisy, a single case dropping means little, and the mean across 100 cases moving by a few points can be noise as well. Guard against false alarms by running enough cases, fixing the temperature low for the test, using per-metric tolerances, and re-running a failing gate once before blocking.

    Automated quality gates in CI/CD

    A quality gate is a pipeline stage that runs the evaluation and fails the stage when thresholds are missed. On AWS the usual shape is AWS CodePipeline with an AWS CodeBuild stage that runs the evaluation script, or a Step Functions state machine called from the pipeline when the evaluation is long-running (a Bedrock evaluation job takes minutes to hours). The build stage fails with a non-zero exit code, and CodePipeline stops promotion. Add a manual approval action after the automated gate when a human sign-off is required.

    Backend analogy

    The baseline file is a snapshot test, except that it stores aggregate scores with tolerances instead of exact strings. The gate is the coverage-threshold check in your CI pipeline: it does not say the code is right, it says the change did not make known things worse.

    Retrieval quality testing (Skill 5.1.6)

    In a RAG system, many wrong answers are retrieval failures wearing a generation costume: the model never saw the right passage. Testing retrieval on its own, without the generator, isolates the cause and is far cheaper because no generation tokens are involved. Chapter 2 covers diagnosing a retrieval problem; this section covers measuring it.

    What you need: a labeled retrieval set

    For each test question, record which document or chunk ids are relevant (the "gold" sources). Ten minutes per question from an SME is enough to start, and a model can propose candidates for the SME to confirm.

    Metrics

    MetricMeaningUse it when
    Recall@kShare of the gold sources that appear in the top k resultsThe generator needs every relevant source. The headline retrieval metric
    Precision@kShare of the top k results that are relevantNoise in the context hurts the answer or wastes tokens
    Hit rate (success@k)Fraction of questions where at least one gold source is in the top kOne good passage is enough
    MRR (mean reciprocal rank)Average of 1 / rank of the first relevant resultOrder matters, for example when you pass only the top 1 or 2
    nDCGRank-aware gain with graded relevanceRelevance has levels, not just yes or no
    Context relevance and coverage (judge)A judge scores whether the retrieved text is relevant to the question and covers the reference answerNo gold ids available. Bedrock RAG evaluation offers these as managed metrics
    Retrieval latencyp50 and p95 time of the retrieve callAlways: it is part of the user-visible latency budget
     
    import time, boto3
agent_rt = boto3.client("bedrock-agent-runtime")
KB_ID = "ABCDEFGHIJ"   # your knowledge base id

def retrieve(question, k=5):
    t0 = time.perf_counter()
    r = agent_rt.retrieve(
        knowledgeBaseId=KB_ID,
        retrievalQuery={"text": question},
        retrievalConfiguration={"vectorSearchConfiguration": {"numberOfResults": k}},
    )
    ms = (time.perf_counter() - t0) * 1000
    # Source identifier: S3 URI of the originating document
    sources = [x["location"]["s3Location"]["uri"] for x in r["retrievalResults"]]
    return sources, ms

def evaluate(cases, k=5):
    hits = rr = recall = 0.0
    lat = []
    for c in cases:                       # c = {"q": ..., "gold": {s3 uris}}
        got, ms = retrieve(c["q"], k)
        lat.append(ms)
        rel = [i for i, s in enumerate(got) if s in c["gold"]]
        hits += 1 if rel else 0
        rr += 1 / (rel[0] + 1) if rel else 0
        recall += len({got[i] for i in rel}) / len(c["gold"])
    n = len(cases)
    lat.sort()
    return {"hit_rate": hits / n, "mrr": rr / n, "recall_at_k": recall / n,
            "p95_ms": lat[int(0.95 * (n - 1))]}

    Sweep the knobs that matter and compare: chunk size and overlap, the embedding model, the number of results, hybrid versus semantic search, metadata filters, and a reranking step (see chunking and hybrid search and reranking in Domain 1). Changing chunking means re-ingesting, so run this sweep on a small corpus first. Remember the cost angle: more results and a reranker raise latency and tokens, so report latency and context size next to recall.

    Exam tip

    If answers are wrong but the model is fine, the question is usually about retrieval. The scoring answer measures retrieval separately (relevance scoring, context matching, latency) before tuning the prompt or swapping the model. Tuning the generator to compensate for missing context is the distractor.

    Evaluating agents (Skill 5.1.7)

    An agent adds a new failure surface: it can reach the right answer through a wrong path, take twenty steps where three would do, call a tool with bad parameters, loop, or give up. Final-answer scoring alone misses all of that. An agent evaluation scores the outcome and the trajectory (the sequence of reasoning steps and tool calls).

    DimensionMeasure
    Task completionShare of test tasks where the goal state was reached (checked by code, such as "the ticket exists with status X", or by a judge)
    Tool selection accuracyDid the agent call the expected tool for the step?
    Tool parameter accuracyWere the arguments valid and correct?
    EfficiencySteps, tool calls, tokens, and wall time per task, against a reference trajectory
    Reasoning qualityA judge reads the trace and checks each step follows from the previous observation, with no unsupported leaps or loops
    RecoveryWhen a tool returns an error or an empty result, does the agent retry sensibly or report honestly?
    SafetyDoes it stay in scope, refuse disallowed actions, and avoid calling destructive tools without confirmation?

    How to collect the trajectory

    With classic Amazon Bedrock Agents, invoke_agent accepts enableTrace=True and streams trace events that include the orchestration steps, the rationale, the action group invocations with parameters, and the observations. Parse the trace into a list of steps and score it. Note that classic Bedrock Agents are in maintenance mode and closed to new customers, so greenfield work belongs on Amazon Bedrock AgentCore, but existing agents and the exam still refer to the classic service. For agents you build yourself, record each tool call (name, arguments, result, duration) in your own trace with OpenTelemetry or AWS X-Ray, as shown in Domain 4.

    import uuid, boto3
art = boto3.client("bedrock-agent-runtime")

def run_agent_case(agent_id, alias_id, task):
    steps, answer = [], ""
    resp = art.invoke_agent(
        agentId=agent_id, agentAliasId=alias_id,
        sessionId=str(uuid.uuid4()), inputText=task, enableTrace=True,
    )
    for event in resp["completion"]:
        if "chunk" in event:
            answer += event["chunk"]["bytes"].decode()
        if "trace" in event:
            steps.append(event["trace"]["trace"])      # orchestration trace parts
    return answer, steps

    For scoring, define each test as a task, the expected tool sequence (or the set of acceptable sequences), and a success predicate on the final environment state. Then compute task completion rate, the fraction of expected tools called, the number of unexpected calls, and the step count against the budget.

    Managed options

    Bedrock Evaluations lets you evaluate model and RAG sources. For agents, Amazon Bedrock AgentCore Evaluations provides LLM-as-a-judge evaluators with built-in names such as Builtin.GoalSuccessRate, Builtin.ToolSelectionAccuracy, Builtin.ToolParameterAccuracy, Builtin.Correctness, Builtin.Faithfulness, and Builtin.Helpfulness, operating at tool-call, trace, or session level, with on-demand and online (sampled live traffic) modes and scores published to CloudWatch. Custom evaluators can be defined with your own instructions and rating scale. These are AgentCore features (control-plane client bedrock-agentcore-control), so for classic Bedrock Agents you score the trace yourself. Confirm current evaluator names and Region availability in the AgentCore documentation before relying on them.

    Exam tip

    Pick the answer that evaluates the path as well as the destination. "Check only that the final answer matches" misses wrong-tool and wasteful paths. "Capture the agent trace, score tool selection and parameters, and measure task completion and steps" is the framework answer.

    Evaluation results only change decisions when the right people see them in a form they understand. Engineers want per-case diffs and failing examples. Product owners want trends and trade-offs. Executives want one page: are we better or worse than last month, what does it cost, and what is the risk. Plan three views over the same data.

    The data path

    Write every evaluation run as a row-per-case file to S3 (Parquet or JSON Lines), partitioned by run date, with columns for run id, dataset version, model id, prompt version, case id, category, each metric score, tokens, latency, and cost. Then choose the visualisation layer by audience and effort:

    • Amazon QuickSight for business dashboards. Query the S3 data through Amazon Athena (define a table over the S3 prefix with AWS Glue, then point a QuickSight dataset at it). Good for trend lines, per-category heat maps, and side-by-side model comparisons that stakeholders can filter. Supports scheduled email reports.
    • Amazon CloudWatch dashboards for operational metrics. Publish aggregate scores as custom metrics (put_metric_data) at the end of each run, then chart them next to latency and error metrics and put alarms on them. Good for engineers and for a quality-over-time widget next to production health.
    • Notebook or static report. A Jupyter notebook run in Amazon SageMaker AI, or a script that writes an HTML or Markdown report to S3, is the lowest-effort comparison report and fits the CI stage (attach it as a build artifact).

    Useful visuals for model comparison: a table of mean score per metric by model, a quality versus cost scatter (the Pareto frontier shows which models are never worth choosing), a latency distribution per model, a per-category heat map (rows are categories, columns are model or prompt versions), and a line chart of the gate metrics across releases.

    Automated reporting

    Automate so nobody has to remember. An Amazon EventBridge schedule (or an S3 event when a new results file lands) invokes an AWS Lambda function that aggregates the latest run, compares it with the previous baseline, writes a summary to S3, and publishes it through Amazon SNS (email or chat webhook) or Amazon SES. Include the gate verdict, the biggest regressions, the three worst cases with links, and the cost delta.

    import json, boto3

s3 = boto3.client("s3")
sns = boto3.client("sns")
cw = boto3.client("cloudwatch")
TOPIC = "arn:aws:sns:us-east-1:111122223333:genai-eval-reports"

def handler(event, context):
    # event from S3 notification: new results file for a run
    rec = event["Records"][0]["s3"]
    run = json.loads(s3.get_object(Bucket=rec["bucket"]["name"],
                                   Key=rec["object"]["key"])["Body"].read())
    summary = run["summary"]            # {"faithfulness": 0.91, "correctness": 0.84, ...}
    cw.put_metric_data(
        Namespace="GenAI/Evaluation",
        MetricData=[{"MetricName": m, "Value": v, "Unit": "None",
                     "Dimensions": [{"Name": "PromptVersion", "Value": run["prompt_version"]}]}
                    for m, v in summary.items()],
    )
    lines = [f"{m}: {v:.3f}" for m, v in summary.items()]
    sns.publish(TopicArn=TOPIC,
                Subject=f"GenAI eval {run['run_id']}: {'PASS' if run['gate_passed'] else 'FAIL'}",
                Message="\n".join(lines))

    Watch out

    Evaluation outputs often contain real user text. Dashboards and report emails can leak it. Report aggregates and ids, keep raw text in the access-controlled bucket, and restrict QuickSight datasets with row-level security where needed.

    Deployment validation (Skill 5.1.9)

    The offline gate tests a candidate before release. Deployment validation tests the release itself, in the real environment, and keeps testing it afterwards. Foundation model updates are the sharp edge here: a model alias may point to a new version, a model may be deprecated and replaced, an inference profile may route differently, and your own infrastructure (permissions, quotas, a knowledge base sync) may differ from staging.

    Synthetic user workflows

    A synthetic workflow is a scripted end-to-end scenario that behaves like a user: sign in, ask a multi-turn question, upload a document, trigger a tool call, expect a particular kind of answer. Run it continuously against production and staging. On AWS, Amazon CloudWatch Synthetics runs scheduled canary scripts (Node.js or Python on Selenium or Puppeteer runtimes, and API-style canaries) and publishes success rate and duration metrics you can alarm on. For GenAI you add output assertions to the canary, since an HTTP 200 proves nothing:

    • The response parses and matches the schema.
    • It contains a required fact, or cites a known source id, for a fixed question about a stable document.
    • It refuses a fixed out-of-scope or injection prompt.
    • Latency (time to first token and total) is inside the budget.
    • Optionally a small judge call scores faithfulness on a sample, which is the semantic check.

    Hallucination and semantic drift checks

    • Hallucination rate on a fixed question set with known answers: the share of responses the judge marks unfaithful or incorrect. Track as a percentage and alarm on a rise.
    • Semantic drift is a change in the meaning of outputs for the same inputs. Keep a reference set of prompts with approved answers, embed the new outputs and the references, and alarm when mean cosine similarity falls under a threshold or when the distribution of similarity shifts. Production drift on live traffic is covered in Domain 4. The deployment-time version uses a fixed set so a change is attributable to the release.
    • Response consistency: the repeat-and-compare test from the metrics section, run before and after the release.

    Safe rollout mechanics

    flowchart LR
  N["New version"] --> SH["Shadow: run beside prod, log only"]
  SH --> CN["Canary: 5% of traffic"]
  CN --> SY["Synthetic canaries + judge sample"]
  SY --> AL{"CloudWatch alarms OK?"}
  AL -->|"yes"| RP["Ramp to 100%"]
  AL -->|"no"| RB["Automatic rollback"]

    Shadow deployment sends a copy of real requests to the new version and discards or only logs its responses, so you can score the candidate on real traffic without user impact. It doubles the model cost for the shadowed share, so sample. Canary then exposes a small user share. Implement the shift with a Lambda alias weighted routing, an API Gateway canary stage, a weighted ALB target group, an AWS AppConfig deployment with a CloudWatch alarm for automatic rollback, or AWS CodeDeploy traffic shifting for Lambda and ECS. Name the alarms that matter: error rate, p95 latency, guardrail intervention rate, synthetic canary failure, and the quality metric (judge score or thumbs-up rate).

    Exam tip

    For "validate a new FM version before full release", the strong answer layers: offline regression on the golden set, synthetic workflow canaries with output assertions, a limited canary or shadow phase, hallucination and drift checks, and automated rollback on alarm. "Deploy and watch the error rate" is incomplete, because FM regressions rarely raise errors.

    Chapter recap

    • GenAI evaluation scores open-ended, non-deterministic output on several dimensions: relevance, factual accuracy, faithfulness, consistency, fluency, safety, format validity, plus cost and latency. Use programmatic checks first, similarity metrics as a coarse signal, and an LLM judge for open-ended quality.
    • The golden dataset is versioned, categorised, grows from production failures, and carries reference answers and gold source ids where possible.
    • Bedrock Evaluations runs automatic, model-as-a-judge, and human jobs for models and RAG sources through create_evaluation_job on the bedrock client, using JSONL datasets in S3 and an IAM service role. Read a console-built job back with get_evaluation_job to learn the exact request shape.
    • RAG evaluation separates retrieve-only (context relevance, coverage) from retrieve-and-generate (correctness, completeness, faithfulness, citation metrics).
    • Custom judges need anchored rubrics, temperature 0, a different judge family when possible, order swapping for pairwise tests, and calibration against human labels.
    • Choose models on a quality, cost, and latency table, then confirm online with A/B (which variant users prefer) or canary (safe rollout) testing.
    • Close the feedback loop: implicit signals, ratings joined to request context, and expert annotation feeding the golden set. Choose Bedrock human evaluation, Ground Truth, A2I, or a custom UI by workflow shape.
    • Quality gates compare scores with a baseline and floors in CodePipeline and CodeBuild (or Step Functions for long jobs) and block promotion on regression.
    • Test retrieval alone with recall@k, precision@k, hit rate, MRR, nDCG, and latency. Evaluate agents on outcome and trajectory: completion, tool selection and parameters, efficiency, reasoning, recovery.
    • Report by audience through QuickSight, CloudWatch, or static reports, automated with EventBridge, Lambda, and SNS. Validate deployments with synthetic workflows, hallucination and drift checks, shadow and canary phases, and alarm-driven rollback.

    Knowledge check

    1. A team must compare three foundation models on their own 500 support questions with reference answers, using the least custom code, and receive per-metric scores and a report. Which approach fits best?

      Answer

      Create a Bedrock model evaluation job (automatic, or model-as-a-judge if open-ended quality matters) with the questions as a JSONL dataset in S3, the candidate models in the job, and results written to S3. Writing a custom harness is more work for the same outcome, A/B testing in production needs live traffic and does not use the reference answers, and human evaluation alone is too slow and costly for a first pass over 500 cases.

    2. A RAG assistant sometimes gives confident answers that contradict the retrieved documents. Which metric should the team track and gate on first?

      Answer

      Faithfulness (groundedness): whether each claim is supported by the retrieved context, measured by a judge in a Bedrock RAG evaluation or a custom judge. Fluency does not detect contradictions, context relevance measures retrieval rather than the generated answer, and ROUGE against a reference rewards word overlap instead of support.

    3. A team uses the same model that produces answers to grade them, and scores keep rising after each prompt tweak while users complain more. What is the best fix?

      Answer

      Move to an independent judge (a different or stronger model), use an anchored rubric, control for answer length, and calibrate the judge against a sample of human labels. Lowering temperature on the same judge does not remove self-preference, adding more cases does not fix a biased scorer, and dropping automation entirely ignores that humans cannot review every case.

    4. The company wants to roll out a new prompt and model version to production with minimal user risk, and automatic reversal if quality drops. Which design is best?

      Answer

      Pass the offline golden-set gate, then send a small share of traffic to the new version through weighted routing (Lambda alias, API Gateway canary, or an AppConfig deployment), monitor error rate, latency, guardrail rate, and a quality metric, and roll back automatically on a CloudWatch alarm. A full cutover watching only HTTP errors misses quality regressions, and an A/B test with a 50 percent split exposes too many users to risk when the goal is safe rollout.

    5. An agent passes every final-answer check, but cost per task has doubled. What evaluation was missing?

      Answer

      Trajectory and efficiency evaluation: capture the trace, measure steps, tool calls, and tokens per task against a reference, and score tool selection and parameter accuracy. Final-answer correctness cannot see redundant or looping tool calls. Retrieval metrics and a stronger judge do not address the path the agent took.

    6. After a model provider updates the model version behind an alias, error rates are flat but support leads report subtly different answers. Which validation would have caught it earliest?

      Answer

      A scheduled evaluation and synthetic canary with output assertions and a semantic drift check on a fixed reference set (similarity to approved answers, hallucination rate by judge), alarming on a shift. Error-rate alarms see only exceptions, user thumbs-down arrive late and are noisy, and a one-time pre-release test cannot detect a change that happens after release.

    Problem statement

    The scenario

    A mid-sized insurer runs a claims-policy assistant. It answers staff questions from a policy knowledge base and, for a few intents, calls tools to look up a claim status or open a ticket. The team changes something almost every week: a new prompt version, a cheaper model, a different chunk size. Last month a prompt tweak raised helpfulness ratings in a demo but quietly made the assistant cite the wrong policy section in one question out of six. Nobody noticed for nine days. Leadership now wants no change reaching production unless it passes a measured gate, and wants a one-page report each week.

    Requirements:

    • A golden dataset of at least 60 question and reference-answer records, each tagged with the policy passages that should be retrieved and, for agent cases, the expected tool calls. Keep it in version control in JSON Lines.
    • A runner that executes a candidate (model ID, prompt version, retrieval settings) against the golden set and records answer, retrieved passages, tool calls, token usage, and latency for every case.
    • Scoring along several axes: an automatic metric, a Bedrock evaluation job, and a custom LLM-as-a-judge with a written rubric for faithfulness, relevance, and fluency. Judge scores must be checked against at least 15 human-labelled cases.
    • Retrieval scoring (recall at k, mean reciprocal rank, and p95 retrieval latency) separate from generation scoring, so a failure can be placed in the right layer.
    • Agent scoring: task completion rate, tool-selection accuracy, and a check on the number of steps.
    • A feedback endpoint that stores thumbs and a free-text reason per answer, and a small review queue where a human labels sampled answers.
    • A gate script that fails with a non-zero exit code when any metric drops by more than an agreed margin against the stored baseline, or when cost per answer rises beyond a limit. Run it from a pipeline.
    • A deployment validation step: after a release candidate is deployed, a scheduled synthetic workflow sends fixed requests, compares output to the golden set with an embedding similarity check, and raises an alarm when semantic drift or the failure rate crosses a threshold.
    • A report that compares candidates in one chart and one table, produced on a schedule and written where stakeholders can open it.

    Build the harness so the same code can be run by a developer, by a pipeline, and on a schedule.

    The exam phrases this as "the team needs to compare several foundation models objectively", "a prompt change must not reduce answer quality", "evaluate the retrieval component separately", "minimize operational overhead when judging open-ended output at scale", or "validate a new model version before full rollout". Managed Bedrock evaluation jobs fit repeatable comparisons with little code. A custom judge fits a rubric the built-in metrics do not cover. Human review fits calibration and subjective quality. A quality gate in the pipeline fits "must not regress". Canary or synthetic checks fit validation after deployment. Most questions reward the answer that combines two of these and keeps cost and effort low.

    The data path starts with the golden dataset, which is the contract for correct behavior. The runner calls the candidate for every case and writes one result record per case, including the retrieved passages and the tool calls, because later scorers need them. Scoring is a separate step that only reads stored results. That separation is the main design decision: you can add a new metric, or re-judge with a different judge model, without paying for generation again.

    The scorers work on different layers. Automatic metrics are cheap and deterministic. The Bedrock evaluation job and the custom judge score open-ended text. Retrieval and agent scorers look at passages and tool calls, so a wrong answer can be traced to retrieval, to prompt, or to tool selection. The gate reads the scorecard and compares it to the stored baseline. The trade-off is judge cost and bias: a judge is a model call per case per metric, and it tends to prefer longer and more confident answers, so the harness keeps a small human-labelled set to measure agreement. Feedback from real users flows back as new golden cases, which keeps the dataset from going stale.

    A triage method: from symptom to layer

    A traditional service fails loudly. A stack trace, a 500, or a failed health check tells you where to look. A GenAI application fails in two different ways. Some failures are loud: the API returns an error and your code logs it. Others are silent: the call succeeds with HTTP 200, the model returns fluent text, and the text is wrong, truncated, off-format, or built on the wrong context. Silent failures are the ones the exam keeps returning to, because no alarm fires on them unless you built one.

    A useful way to work is to place the symptom in a layer before you touch anything. A GenAI request passes through the same stages every time, and each stage has its own evidence.

    flowchart LR
  A["1. Request building: template, variables, token budget"] --> B["2. API call: validation, auth, quota, timeout"]
  B --> C["3. Model behavior: stop reason, format, reasoning"]
  C --> D["4. Retrieved context: relevance, chunking, freshness"]
  D --> E["5. Post-processing: parsing, schema, guardrails"]
  E --> F["User-visible answer"]

    The method has four steps, and the order matters because each step is cheaper than the next.

    1. Reproduce with the exact request. Pull the failing request from your logs: the rendered prompt, the model ID, the inference parameters, the retrieved chunks. If you cannot reconstruct it, that is the first finding, and the fix is to log it (see invocation logging in Domain 4).
    2. Read the cheap signals first. The HTTP status or exception name, the stopReason in the response, and the token counts in usage. These three fields settle a large share of cases in seconds.
    3. Isolate one layer. Replay the same prompt with the retrieved context fixed, or the same context with a different prompt, or the same prompt on a different model. Change one thing at a time. This is the same discipline as bisecting a regression.
    4. Fix, then lock it in with a test. Add the failing case to your golden set (see the regression testing section of Chapter 1) so it cannot silently return.

    Backend analogy

    Think of the stop reason and token counts as the HTTP status line and the Content-Length header of a model call. You read them before you read the body. A 200 with stopReason: max_tokens is the model equivalent of a 200 whose body was cut off mid-JSON: the transport succeeded, the payload is broken.

    Content handling: context windows, truncation, and chunking (5.2.1)

    Every model has a context window: the maximum number of tokens it can handle across input and output together. Your system prompt, the conversation history, retrieved chunks, tool definitions and results, and the generated answer all share that budget. Content handling problems are what happens when you exceed it, or when you stay under it but waste it. They appear in four recognizable forms.

    Form 1: the request is rejected

    When the input alone is larger than the model accepts, the Converse and InvokeModel APIs return a ValidationException (HTTP 400) with a message about the input being too long or exceeding the maximum number of tokens. The exact wording varies by model, so match on the exception class and then read the message, not on a fixed string. A ValidationException is a client error. Retrying the same request returns the same error, so your retry policy must exclude it. The fix is always to shrink or restructure the input.

    Form 2: the answer is cut off

    The request is accepted, but generation stops early. The Converse response carries a stopReason field. The values defined in the current Bedrock runtime API model are end_turn, tool_use, max_tokens, stop_sequence, guardrail_intervened, content_filtered, malformed_model_output, malformed_tool_use, and model_context_window_exceeded. Two matter here:

    • max_tokens: generation reached the maxTokens you set in inferenceConfig (or the model's own output ceiling). The text is truncated by your own limit. The fix is a higher maxTokens if the answer genuinely needs the room, or a prompt that asks for a shorter answer. Raising it blindly has a cost: Bedrock reserves quota based on maxTokens, so an oversized value can trigger throttling (see the next section).
    • model_context_window_exceeded: the model ran out of context window while generating, which means input plus output hit the window. The fix is to reduce the input so more room remains for output. Whether a given model returns this value or returns a ValidationException up front depends on the model, so handle both.

    A truncated JSON answer is the classic downstream symptom: your parser throws JSONDecodeError, and the real cause is two layers earlier. This is why the triage method reads stopReason before anything else.

    Form 3: the answer ignores part of the input

    Nothing errors and the stop reason is end_turn, yet the answer ignores a fact that was in the prompt. Two causes dominate. The first is a framework or your own code silently trimming history to fit a budget, so the fact never reached the model. Check the rendered prompt, not the template. The second is positional: models attend less reliably to material buried in the middle of a very long prompt. Moving the instruction and the key facts to the start or end, and trimming low-value text, often fixes it without any model change.

    Form 4: the budget is wasted

    The request fits, but 70 percent of the tokens are repeated boilerplate, duplicate retrieved chunks, or a tool schema the model does not need. This shows up as cost and latency problems, and as lower quality because the signal is diluted.

    Diagnosing overflow with token accounting

    The most reliable overflow diagnostic is to count tokens per prompt component before the call and log the breakdown. Bedrock offers a CountTokens operation on the runtime client that returns the input token count for a given request body without running inference, so you can check a request against the model's window ahead of time. Availability varies by model and Region, so confirm it for your model in the documentation, and keep a character-based estimate as a fallback. After the call, usage.inputTokens and usage.outputTokens in the Converse response give the exact figures that were billed.

    import boto3

bedrock = boto3.client("bedrock-runtime")

MODEL_ID = "us.anthropic.claude-sonnet-4-6"   # use a model ID you have access to
CONTEXT_WINDOW = 200_000                       # check the model's documented window
OUTPUT_RESERVE = 2_000                         # tokens you want left for the answer


def check_budget(system: str, history: list[dict], context_chunks: list[str], question: str) -> dict:
    """Return a per-component token estimate using CountTokens, with a coarse fallback."""
    def count(text: str) -> int:
        try:
            r = bedrock.count_tokens(
                modelId=MODEL_ID,
                input={"converse": {
                    "messages": [{"role": "user", "content": [{"text": text}]}],
                }},
            )
            return r["inputTokens"]
        except Exception:
            return max(1, len(text) // 4)          # rough fallback, about 4 chars per token

    parts = {
        "system": count(system),
        "history": sum(count(m["content"][0]["text"]) for m in history),
        "retrieved": sum(count(c) for c in context_chunks),
        "question": count(question),
    }
    total = sum(parts.values())
    parts["total_input"] = total
    parts["headroom"] = CONTEXT_WINDOW - total - OUTPUT_RESERVE
    parts["will_overflow"] = parts["headroom"] < 0
    return parts

    Each per-text count includes a small fixed overhead from the message wrapper, so the sum slightly overstates the real total, which is the safe direction for a budget check. Log the returned dictionary with every request. When a user reports "it forgot what I said earlier," the log shows whether history was trimmed to zero.

    Remediation techniques

    Once the diagnosis names the bloated component, pick the matching fix.

    Bloated componentSymptomFix
    Conversation historyLong chats start failing or lose early factsKeep the last N turns verbatim and replace older turns with a rolling summary produced by a small, cheap model. Store the summary alongside the session (for example in DynamoDB)
    Retrieved chunksMany near-duplicate passages, answer buriedLower numberOfResults, deduplicate by source and overlap, rerank and keep the top few, or compress each chunk to the sentences that matter
    Single huge documentOne document exceeds the window on its ownDynamic chunking: split on structure, run map-reduce summarization or per-chunk extraction, then merge. See below

    Dynamic chunking

    Static chunking, covered in Domain 1, fixes one chunk size at ingestion time. Dynamic chunking decides the split at request time based on the document and the task. For a long contract that must be summarized, you split on section headings, summarize each section independently (these calls can run in parallel), then run one final call that merges the section summaries. For a question over a long document, you split, score each piece against the question, and keep only the best few. The exam wording to recognize is "document exceeds the context window": the answer is a chunk-and-combine pattern, or a retrieval step that selects the relevant parts, and not a bigger maxTokens.

    from concurrent.futures import ThreadPoolExecutor
import re


def split_on_headings(doc: str, max_chars: int = 12_000) -> list[str]:
    """Split on markdown-style headings, then pack sections up to max_chars."""
    sections = re.split(r"\n(?=#{1,3} )", doc)
    chunks, current = [], ""
    for s in sections:
        if len(current) + len(s) > max_chars and current:
            chunks.append(current)
            current = ""
        current += s + "\n"
    if current.strip():
        chunks.append(current)
    return chunks


def ask(prompt: str, max_tokens: int = 600) -> str:
    r = bedrock.converse(
        modelId=MODEL_ID,
        messages=[{"role": "user", "content": [{"text": prompt}]}],
        inferenceConfig={"maxTokens": max_tokens, "temperature": 0},
    )
    if r["stopReason"] != "end_turn":
        raise RuntimeError(f"unexpected stop reason: {r['stopReason']}")
    return r["output"]["message"]["content"][0]["text"]


def summarize_long(doc: str) -> str:
    chunks = split_on_headings(doc)
    with ThreadPoolExecutor(max_workers=4) as pool:           # map step, in parallel
        partials = list(pool.map(lambda c: ask(f"Summarize in 5 bullets:\n\n{c}"), chunks))
    return ask("Merge these partial summaries into one summary:\n\n" + "\n\n".join(partials))   # reduce step

    Watch out

    Do not raise maxTokens to "be safe." Bedrock reserves quota for the output limit you request, so an inflated value consumes tokens-per-minute headroom even when the answer is short, and it can cause ThrottlingException under moderate load. Set maxTokens to a value sized to the task, and treat a max_tokens stop reason as a signal to review the prompt, not only the limit.

    Exam tip

    If a scenario says a response is cut off mid-sentence or the JSON will not parse, look for stopReason: max_tokens first. If it says the request fails immediately with a validation error on long input, the input exceeded the window: shrink it with summarization, chunking, or retrieval. A distractor to avoid is "switch to Provisioned Throughput," which changes capacity and has no effect on context size. Another distractor is "increase the temperature," which changes randomness and not length.

    Prompt design optimization

    Prompt design is the cheapest lever for content handling. Put the task instruction first, then the data, then a short restatement of the output format. Delimit untrusted or bulky content with tags such as <document>...</document> so the model can tell data from instructions. Ask for the shortest form that satisfies the use case ("answer in at most three sentences", "return only the JSON object"). For structured output, prefer the tool-use or structured-output features of the model over free text that you parse, because they constrain the format and reduce malformed responses. Whether a specific model supports a given structured-output mode is model-dependent, so check the model's documentation.

    "Retry everything" is the wrong answer. Retrying a ValidationException or AccessDeniedException wastes time and, for validation errors, repeats the failure forever.     Error logging that makes diagnosis possible

    The AWS SDK for Python raises botocore.exceptions.ClientError for service errors, and each client exposes typed exceptions under client.exceptions. Catch typed exceptions only where you have something useful to do, and let the rest propagate to one top-level handler that logs a structured record. A good record carries the fields you will want at 2 a.m.: the exception class, the AWS request ID, the model ID, the Region, the token counts you computed, the stop reason if any, and a hash of the prompt so you can correlate without storing sensitive text.

def invoke(model_id: str, system: str, user_text: str, max_tokens: int = 500) -> dict:

            "http_status": meta.get("HTTPStatusCode"),

        "event": "bedrock_ok",
        "request_id": resp["ResponseMetadata"]["RequestId"],
        "stop_reason": resp["stopReason"],
        "usage": resp["usage"],
        "latency_ms": resp["metrics"]["latencyMs"],
        "wall_ms": int((time.perf_counter() - started) * 1000),
        "model_id": model_id,
        "prompt_hash": prompt_hash,
    }))

    Request validation before the call

    Many ValidationExceptions are predictable, so catch them in your own code with a clear message and no network call. A small pre-flight validator covers the common causes.

    • Message structure. Converse requires alternating user and assistant roles, starting with user. A transcript with two consecutive user turns, or an empty text block, is rejected.
    • Parameter ranges. temperature and topP have model-specific ranges, and some models do not accept both together or do not accept certain parameters at all. Model-specific extras go in additionalModelRequestFields, and passing a field the model does not know is a validation error.
    • Model ID form. Some models cannot be called with the base model ID for on-demand use and require an inference profile ID or ARN. The error message says so explicitly. List what exists with list_inference_profiles on the control-plane client.
    • Input size. Use the token accounting from the previous section.
    • Content type. Images and documents must use supported formats and sizes. Check the model's documentation for limits rather than assuming them.
    def validate_request(messages: list[dict], max_tokens: int, temperature: float | None) -> list[str]:
    problems = []
    if not messages or messages[0]["role"] != "user":
        problems.append("first message must have role 'user'")
    for prev, cur in zip(messages, messages[1:]):
        if prev["role"] == cur["role"]:
            problems.append(f"two consecutive '{cur['role']}' messages")
    for m in messages:
        for block in m["content"]:
            if "text" in block and not block["text"].strip():
                problems.append("empty text block")
    if not (1 <= max_tokens <= 8192):          # set your own ceiling; model limits differ
        problems.append("max_tokens outside your configured range")
    if temperature is not None and not (0.0 <= temperature <= 1.0):
        problems.append("temperature outside 0..1 (check the model's documented range)")
    return problems

    Response analysis

    A successful call is not a successful answer. Treat the response as untrusted data and check it in this order:

    1. stopReason: anything other than end_turn (or tool_use when you expect a tool call) needs a branch. max_tokens means truncated. guardrail_intervened or content_filtered means a safety control replaced or blocked content, and the text you see may be your configured blocked message. malformed_model_output and malformed_tool_use mean the model produced something the service could not parse, which is worth a retry.
    2. usage: compare inputTokens to your pre-flight estimate. A large gap means your accounting is wrong.
    3. Content shape: the output is a list of content blocks. Do not assume content[0] is text. A model with extended reasoning can return a reasoning block before the text block, and a tool call is a toolUse block.
    4. Guardrail trace: if you attached a guardrail with trace enabled, the response carries which policy fired.

    Watch out

    Streaming changes where errors appear. With ConverseStream, the initial call can succeed and a failure arrives later as an exception inside the event stream (for example ModelStreamErrorException, or a throttling error). Wrap the whole read loop in your error handling, not only the call that opens the stream, and discard partial output on failure.

    Backend analogy

    The retry split is the same rule you apply to HTTP: retry 429 and 5xx with backoff, never retry a 400 or 403. Adaptive retry mode is close to a client-side token bucket in a resilient HTTP client.

    Prompt engineering problems: testing, comparison, and systematic refinement (5.2.3)

    When the API behaves and the context fits but the answers are inconsistent, wrong in format, or wrong in judgment, the prompt is the usual suspect. "Beyond basic prompt adjustments" in the exam wording means you do not tweak wording and hope. You treat the prompt as code under test: fixed inputs, measured outputs, and one change at a time.

    A prompt testing framework

    A prompt testing framework has four parts: a test set (inputs with expected properties), a runner that renders the prompt and calls the model, a set of checks, and a report that compares versions. The checks come in three strengths, and a good suite uses all three.

    • Deterministic checks: JSON parses, schema validates, required keys exist, forbidden strings are absent, the length is within bounds. These are fast, free of judgment, and should run on every output.
    • Reference checks: exact match or similarity against a known good answer, for tasks with a single right answer such as classification labels or extracted fields.
    • Judged checks: an LLM-as-a-judge scores qualities that code cannot measure, such as faithfulness to context. See LLM-as-a-judge in Chapter 1.

def run_case(model_id: str, template: str, case: dict, runs: int = 5) -> dict:
    outputs, schema_ok, labels = [], 0, []
    for _ in range(runs):
        prompt = template.format(**case["inputs"])
        r = bedrock.converse(
            modelId=model_id,
            messages=[{"role": "user", "content": [{"text": prompt}]}],
            inferenceConfig={"maxTokens": 300, "temperature": 0.3},
        )
        text = r["output"]["message"]["content"][0]["text"]
        outputs.append(text)
        try:
            obj = json.loads(text)
            jsonschema.validate(obj, TRIAGE_SCHEMA)
            schema_ok += 1
            labels.append(obj["category"])
        except (json.JSONDecodeError, jsonschema.ValidationError):
            labels.append(None)
    expected = case["expected_category"]
    return {
        "case": case["id"],
        "schema_pass_rate": schema_ok / runs,
        "label_accuracy": sum(1 for l in labels if l == expected) / runs,
        "consistency": max(labels.count(l) for l in set(labels)) / runs,   # share of runs agreeing with the mode
    }

    Three numbers come out per case: how often the output was valid, how often it was right, and how stable it was. A prompt can be right on average and still unstable, and the consistency number is what shows it.

    Version comparison

    Never judge a new prompt on a handful of hand-picked examples. Run the old and new versions against the same test set, with the same model and parameters, and compare the aggregate metrics and the per-case differences. The cases where the new version got worse matter as much as the average. Two practical rules apply: keep sample sizes large enough that a difference is not noise (for non-deterministic outputs, repeat each case several times), and change one variable per experiment. If you change the prompt and the temperature together, you cannot say which helped.

    Amazon Bedrock Prompt Management gives you the versioning half of this. You create a prompt, save immutable numbered versions, and refer to a version by its ARN or ID from your code. That means "version 4 versus version 5" is a real, addressable comparison, and a rollback is a one-line change to the version you reference. The prompt authoring and versioning mechanics are in Domain 1, and the Prompt Management console includes a side-by-side compare view for trying variants interactively. Use the console for exploration and your test runner for the decision.

    Systematic refinement

    Refinement is a loop, and the discipline is in the order.

    1. Collect failures from production feedback and logs, and add each one to the test set with the expected behavior.
    2. Cluster the failures by cause (format, grounding, constraint violation, edge case). Fix the largest cluster first.
    3. Make one targeted change: add an example, clarify one rule, reorder one section.
    4. Run the whole suite. Accept the change only if the target metric improved and no other metric dropped beyond your tolerance.
    5. Save a new prompt version with a note on what changed and why, and record the test results next to it.

    Exam tip

    Questions in this area reward the answer that adds measurement: a golden test set, a versioned prompt, an automated comparison across versions, and a regression gate. Distractors tend to be "fine-tune the model" or "switch to a bigger model" before any evidence shows the prompt is the limit, or "edit the production prompt in place" with no version to roll back to.

    Retrieval system issues (5.2.4)

    When a RAG application gives a wrong or vague answer, the model is blamed first and is guilty less often than you would expect. In most cases the model answered faithfully from the passages it was given, and the passages were wrong. The principle to carry into every retrieval investigation is that generation quality is capped by retrieval quality. Test the retriever alone before you touch the prompt or the model.

    Step one: separate retrieval from generation

    Take a failing question and call retrieval directly, without the model. With Amazon Bedrock Knowledge Bases that is the retrieve operation on the bedrock-agent-runtime client. It returns ranked chunks with scores and source locations. Read the top five by hand and ask one question: does any passage contain the answer?

    • The answer is in the top results but the final answer is wrong. Retrieval worked. The fault is in generation: the prompt, context ordering, or too much noise around the right chunk.
    • The answer is in the corpus but not in the top results. A retrieval fault. Continue below.
    • The answer is not in the corpus at all. A coverage fault: the document was never ingested, failed parsing, or does not exist. No tuning will fix it.

    Relevance analysis

    Build a small labeled set: 30 to 100 real questions, each with the document or passage that should answer it.     Embedding quality diagnostics

    An embedding model turns text into a vector so that similar meanings land near each other. Problems show up as unrelated passages scoring close to relevant ones. Check four things.

    • The same model for documents and queries. Vectors from two different embedding models, or from two different dimension settings of the same model, are not comparable. Mixing them is a quiet and common fault, especially after someone "upgrades" the query side only. A dimension mismatch usually fails loudly at index time, but a model mismatch with the same dimension does not.
    • Language and domain fit. A model trained mostly on English prose can rank poorly on code, legal text, or another language. Test with a few labeled pairs from your domain before committing. Models such as Amazon Titan Text Embeddings V2 and Cohere Embed are available on Bedrock, and the multilingual and domain behavior differs by model, so measure rather than assume.
    • Input truncation. Each embedding model has a maximum input length. Text beyond it is truncated or rejected, so a long chunk may be embedded from its first part only. Keep chunks within the model's documented limit.
    • Similarity sanity check. Embed a handful of paraphrase pairs and unrelated pairs and look at the cosine similarity. Paraphrases should score clearly higher than unrelated pairs. If the gap is small, the model is a poor fit.

def cosine(a: list[float], b: list[float]) -> float:
    dot = sum(x * y for x, y in zip(a, b))
    return dot / (math.sqrt(sum(x * x for x in a)) * math.sqrt(sum(y * y for y in b)))

    Drift monitoring

    Retrieval quality changes without any code change, and that is drift. Three kinds matter. Data drift: new documents change the corpus mix, so old queries now compete with more distractors. Query drift: users start asking about new topics the corpus covers poorly. Model drift: someone changes the embedding model or parser. The defense is the same for all three: keep the labeled question set, run it on a schedule (a nightly EventBridge rule that starts a job is enough), publish hit rate and mean reciprocal rank as custom CloudWatch metrics, and alarm when they fall below a baseline. Also log the top retrieval score per live query. A downward trend in the median top score, or a rise in queries whose best score is below a threshold, shows the corpus no longer serves the questions people ask. Domain 4 covers the vector store monitoring side.

    Vectorization issues

    Vectorization is the pipeline from file to stored vector, and it can fail without anyone noticing. In a Knowledge Base, check the ingestion job: get_ingestion_job on the bedrock-agent client returns statistics such as documents scanned, indexed, failed, and deleted, and failure reasons. A document that was skipped for an unsupported format or an oversize file is simply absent from search, and the user sees "the system does not know about it." Alert when numberOfDocumentsFailed is above zero. For a self-managed index, the usual faults are a schema mismatch (vector field name or dimension differs from the index mapping), a changed embedding dimension without a rebuild, and partially failed bulk writes that your code did not check.

    Vector search performance

    Retrieval can also be correct and slow. For Amazon OpenSearch Service and OpenSearch Serverless, performance follows from the approximate nearest-neighbor settings (for example the HNSW parameters for index build effort and search effort, trading recall against speed), the number of shards and replicas, the vector dimension (higher dimensions cost memory and time), and filter strategy (filtering after the search can return too few results, and filtering during the search is more accurate but costs more). For Aurora PostgreSQL with pgvector, the equivalents are the index type and its parameters, and keeping the index in memory. Measure first: record retrieval latency at the 50th and 99th percentile, change one setting, and re-measure both latency and hit rate, because a faster setting that loses recall has not helped. Lower the dimension only after confirming accuracy holds on your labeled set. The tuning knobs and their names are product-specific, so use the documentation for your vector store.

    Exam tip

    When a RAG answer is wrong, the best first action is to inspect what was retrieved, not to change the model or the prompt. Match the symptom to the fix: exact codes missing means hybrid search, answers split across boundaries means chunking changes, stale results means re-sync, results from the wrong tenant means metadata filtering, uniformly poor scores means embedding model fit. Remember that changing chunking or the embedding model requires re-ingesting the data.

    Watch out

    Changing the embedding model or its dimension means the existing vectors are unusable for the new model. Plan a full re-embed into a new index and switch over, instead of mixing old and new vectors in one index. Re-embedding a large corpus costs real money in embedding calls, so estimate it first.

    Prompt maintenance: template testing, observability, and schema validation (5.2.5)

    Prompts are not write-once. Templates accumulate edits, variables change names, upstream data changes shape, and a model update shifts behavior. Prompt maintenance issues are the slow failures: a prompt that worked in March produces malformed output in June and nobody edited it. The tools here are testing for the template itself, logs and traces that expose the rendered prompt, validation of the output shape, and a refinement workflow with versions.

    Template testing

    A prompt template is a string with variables. Most template bugs are mechanical, and you can test them without calling a model.

    • Unfilled or misnamed variables. A literal {customer_name} or {{customer_name}} left in the final prompt means a variable was missing, and the model dutifully tries to answer with the placeholder in view.
    • Empty or oversized values. An empty retrieved context renders a prompt that says "use the context below" followed by nothing. A 50,000-character variable blows the budget.
    • Escaping and injection. A user value that contains your delimiter tags or instructions ("ignore the above") changes the prompt's meaning.
    • Whitespace and ordering. Changes that look cosmetic can shift behavior and also break prompt-cache hits.
    import re

PLACEHOLDER = re.compile(r"\{\{?\s*[\w.]+\s*\}?\}")


def render_checked(template: str, variables: dict[str, str], max_chars: dict[str, int] | None = None) -> str:
    """Render a template and fail loudly on the mechanical errors."""
    missing = [k for k in re.findall(r"\{(\w+)\}", template) if k not in variables]
    if missing:
        raise ValueError(f"missing template variables: {missing}")
    for name, value in variables.items():
        if not value.strip():
            raise ValueError(f"variable '{name}' is empty")
        limit = (max_chars or {}).get(name)
        if limit and len(value) > limit:
            raise ValueError(f"variable '{name}' is {len(value)} chars, limit {limit}")
    rendered = template.format(**variables)
    if PLACEHOLDER.search(rendered):
        raise ValueError("unrendered placeholder left in prompt")
    return rendered

    Put these checks in unit tests that render every template with representative, empty, and hostile inputs, and run them in the same CI job that runs your prompt regression suite. If you use Bedrock Prompt Management, the same discipline applies to the variables you define in a prompt: test the version you intend to deploy with realistic values.

    Diagnosing prompt confusion with CloudWatch Logs

    "Prompt confusion" is when the model misreads which part of the prompt is an instruction, which is data, and which is a previous answer. It shows up as the model answering the retrieved document instead of the user's question, repeating the examples, or following an instruction that was inside user data. You cannot diagnose it without seeing the exact rendered prompt. Two logging sources provide it.

    • Bedrock model invocation logging writes full request and response bodies to CloudWatch Logs, S3, or both, once you enable it in Bedrock settings. It is off by default, it can contain sensitive data, and the log group needs encryption and tight access. Setup and the privacy implications are in Domain 3, and analysis is in Domain 4.
    • Your own application logs record the template ID and version, the variable names (and hashed or truncated values), the rendered token count, the stop reason, and a request ID that links to the invocation log.

    With both in CloudWatch Logs, a CloudWatch Logs Insights query can group failures by prompt version and find the pattern. A query like the one below counts malformed outputs per template version over the last day, assuming your application emits JSON log lines with these fields.

    fields @timestamp, template_id, template_version, stop_reason, schema_ok
| filter event = "prompt_result"
| stats count() as calls,
        sum(schema_ok = 0) as bad_format,
        sum(stop_reason = "max_tokens") as truncated
  by template_id, template_version
| sort bad_format desc

    If bad_format jumps for one version, you have a regression with an address. If it rises across all versions at the same moment, suspect an upstream change such as a model update or a data shape change.

    Prompt observability with AWS X-Ray

    A multi-step GenAI request (rewrite the query, retrieve, rerank, generate, validate) has one prompt per step, and a failure in step 2 can look like a bad answer in step 4. AWS X-Ray, or OpenTelemetry traces sent to X-Ray through the AWS Distro for OpenTelemetry, shows the whole chain as one trace with a span per step. To make it a prompt observability pipeline, attach the right attributes to each span: template ID and version, model ID, input and output token counts, stop reason, retrieval top score, and a validation pass or fail flag. X-Ray annotations are indexed key-value pairs you can filter on, and metadata is not indexed, so put the fields you want to search by (template version, validation result) in annotations, and larger context in metadata. Never put raw prompts containing personal data into spans. With that in place, a filter expression on annotation.schema_ok = false lists exactly the failing traces, and the trace map shows which step introduced the fault. Details on tracing GenAI applications are in Domain 4.

    Schema validation for format inconsistencies

    Downstream code expects a shape. A model that returns a field called urgency_level today and urgency tomorrow breaks the consumer without any exception from Bedrock. Validate every model output against a schema at the boundary, using JSON Schema or Pydantic, and treat a validation failure as a first-class event: log it with the template version, count it as a metric, and decide on a response. A reasonable response ladder is: retry once with the validation error appended to the prompt ("your last answer failed validation because ..."), then retry with a stricter or different model, then return a safe default or route to a human. Publish a SchemaValidationFailures custom metric so an alarm can catch a spike, which is the earliest sign of a prompt or model regression. Using the model's tool-use or structured-output feature to enforce the shape at generation time cuts these failures further, where the chosen model supports it.

    Systematic prompt refinement workflows

    Treat prompts like source code. Keep them in a registry (Bedrock Prompt Management or files in version control), review changes, run the regression suite on every change, and deploy through stages. A workable pipeline is: edit, unit-test the template, run the golden set on the candidate, compare against the current production version, deploy to a small traffic share (a canary), watch the format-failure and quality metrics, then promote or roll back. Because Prompt Management versions are immutable and your code references a version, rollback is a configuration change and not a redeploy. The deployment gate side of this pipeline is in Chapter 1.

    Exam tip

    For "format inconsistencies" and "prompt confusion," the expected components are: invocation logs or application logs in CloudWatch Logs to see the rendered prompt, X-Ray (or OpenTelemetry) spans with prompt version annotations to locate the failing step, schema validation at the output boundary with a metric and alarm, and versioned prompts with a regression suite. "Retrain the model" is almost never the right answer to a prompt maintenance problem.

    Chapter recap

    • Triage by layer: request building, API call, model behavior, retrieved context, post-processing. Read the exception, stopReason, and token counts before anything else.
    • Context problems come in four forms: rejected input, truncated output, ignored input, and wasted budget. Fix them with token accounting, history summaries, fewer and better chunks, and chunk-and-combine for large documents. Do not inflate maxTokens.
    • Retry only transient errors (throttling, timeout, unavailable, internal, model not ready) with backoff. Never retry validation, access, or not-found errors. Throttling at low volume often means an oversized maxTokens.
    • Log structured records with the request ID, model ID, stop reason, usage, and a prompt hash. Validate requests before sending and responses after receiving.
    • Treat prompts as versioned code: a test set, deterministic, reference, and judged checks, one change at a time, immutable versions, and a regression gate.
    • Debug retrieval separately from generation with a direct retrieve probe, a labeled set, hit rate, and MRR. Match symptoms to fixes: hybrid search, chunking, parsing, filters, sync, embedding fit.
    • Never mix vectors from different embedding models or dimensions. A change to either means a full re-embed into a new index.
    • Prompt maintenance relies on template tests, CloudWatch Logs queries by prompt version, X-Ray annotations for step-level tracing, schema validation with a metric and alarm, and a staged refinement pipeline.

    Knowledge check

    1. A support assistant summarizes long chat transcripts. Some summaries end in the middle of a sentence, and a downstream JSON parser fails. The API calls all return HTTP 200. What should the team check first, and what is the most appropriate fix?

      Answer

      Check the stopReason in the Converse response. A value of max_tokens means the output hit the configured limit. The fix is to ask for a shorter, structured summary and, if the content really needs more room, raise maxTokens to a value sized to the task. Switching to Provisioned Throughput changes capacity and does nothing for truncation. Raising temperature changes randomness, not length. Retrying the same request returns the same truncated result.

    2. An application retries every Bedrock exception three times. During an incident, a deployment sends requests with an unsupported inference parameter and the error rate and latency spike. Which change to the retry logic is best?

      Answer

      Classify exceptions and retry only transient ones (ThrottlingException, ModelTimeoutException, ServiceUnavailableException, InternalServerException, ModelNotReadyException) with exponential backoff and jitter. The unsupported parameter produces a ValidationException, which is a client fault that fails identically each time, so retrying only multiplies load. Add request validation before the call and alert on validation error rates. Retrying more times, adding a longer timeout, or switching Regions does not fix a malformed request.

    3. Users report that the RAG assistant cannot answer questions about specific part numbers such as "XK-4471-B", although the manual that contains them was ingested. General questions work well. What is the best change?

      Answer

      Pure semantic vector search is weak on rare exact tokens. Enable hybrid search (vector plus keyword), and consider adding a reranker. First confirm with a direct retrieve call that the literal string is not found. Increasing maxTokens or changing the generation model does not help when the right passage is not retrieved. Re-embedding with a larger dimension may help somewhat but does not address exact-match behavior as directly. Fine-tuning the generation model does not add document knowledge.

    4. After a data team replaced the query-side embedding call with a newer embedding model, retrieval quality fell sharply, but the index still accepts queries without errors. What is the most likely cause and the correct remediation?

      Answer

      Documents and queries now use different embedding models, so their vectors are not comparable even if the dimensions match. Use one model for both sides. If the newer model is preferred, re-embed the whole corpus into a new index and switch over. Adding replicas, lowering the number of results, or tuning the nearest-neighbor search parameters cannot repair a model mismatch.

    5. A team ships weekly prompt edits. This week the proportion of outputs that fail schema validation rose from 1 percent to 12 percent, but only for one of three prompt templates. Which combination of mechanisms finds the cause fastest and prevents a repeat?

      Answer

      Structured application logs in CloudWatch Logs carrying template ID, version, and a schema-pass flag, queried with Logs Insights to group failures by version. X-Ray or OpenTelemetry spans with template-version annotations locate the failing step in multi-step flows. Then roll back to the previous immutable prompt version (for example in Bedrock Prompt Management), add the failing cases to the regression suite, and add a quality gate and a schema-failure metric alarm. Retraining the model or enabling model invocation logging alone, without version-tagged records, does not isolate the template. Scaling out the service does not affect output format.

    6. A chat feature starts returning errors for conversations longer than about 40 turns, with a validation error mentioning input length. The team wants to keep recent detail and keep costs low. Which design is best?

      Answer

      Keep the most recent turns verbatim and replace older turns with a rolling summary generated by a small, inexpensive model, and track the token budget before each call (for example with CountTokens or the previous response's usage). A model with a larger window delays the problem and raises cost. Provisioned Throughput does not change the window. Dropping all history loses needed context. Retrying does not help because the error is a deterministic validation failure.

    The scenario

    A logistics company runs a shipment-exceptions assistant. Dispatchers paste long carrier emails and ask what to do. It retrieves from a runbook knowledge base, calls a model with a versioned prompt template, and returns structured JSON that a downstream system reads.     • A request validator that runs before every model call, estimates tokens, compares them to the model's context window and the output reserve, and reports the exact reason a request would fail or be truncated.     • An error classifier that maps Bedrock exceptions and stop reasons to a cause and an action (retry, shrink, fix a permission, fix a request, report). It records the request ID, model ID, Region, and token counts for every failure.
    • A prompt testing tool that runs two prompt template versions over a fixed case set, diffs outputs, and reports which cases got better, worse, or flipped, with a decision at the end.
    • A retrieval diagnostic that, for a failing question, shows what was retrieved, the scores, whether the expected passage exists in the index, how it was chunked, and whether the query and document embeddings are being made the same way.
    • A template and schema checker that renders every template with edge-case variables, validates the model's JSON output against a schema, and counts format failures per template version.
    • A trace pipeline that records each prompt stage (template render, retrieval, model call, parse) as spans with the prompt version and token counts, so one request can be followed end to end in AWS X-Ray and in CloudWatch Logs.
    • A fault drill: five injected faults (oversized input, a wrong parameter, a weak prompt edit, a mis-chunked document, a template variable bug) that the toolkit must identify, each with a written root cause and fix.

    Build the toolkit so the output of each tool names a cause, not just a symptom.

    The exam phrases this as "users report that responses cut off", "the application intermittently returns a ValidationException", "a recent prompt change reduced quality", "the model answers from the wrong document", or "the team needs to trace a prompt through the pipeline". The pattern is the same each time: find the layer first, then the cause. Context problems point to token counts and chunking. Integration problems point to error codes, quotas, and request shape. Prompt problems point to versioned tests. Retrieval problems point to chunks, embeddings, and index settings. Format problems point to schema validation. The best answer names the cheapest diagnostic that separates the possible causes.

The validator sits first because it is the cheapest place to catch a problem: it knows the input size before any money is spent. The parser sits last and validates the output against a schema, so a format failure is counted instead of discovered downstream.

    The second diagram is the triage tree the toolkit encodes. Start from the symptom and ask the question that cuts the space in half. An error code goes to the classifier. A malformed but successful response goes to the schema check. A wrong answer splits on whether the right passage was retrieved, which separates retrieval faults from prompt faults. The trade-off is overhead: spans and structured logs add small latency and storage cost, and full prompt text in logs raises a privacy concern. The toolkit therefore logs sizes, IDs, versions, and hashes by default, and full text only in a debug mode with a short retention.

    Definition of done

    • The validator rejects an oversized request without calling the model and names the largest contributor to the token count.
    • A response that stops with max_tokens is flagged as truncated in the output and in the logs.
    • The dynamic chunking path handles the long-email case and prints a list of omitted parts.
    • The error classifier correctly labels a validation error, an access denied error, and a throttling error that you produced on purpose, and each log line contains the request ID, model ID, Region, and token counts.
    • The prompt tester reports the weakened template version as worse and lists the affected cases.
    • The retrieval report shows retrieved chunks with scores and states whether the expected passage exists in the index.
    • Schema validation runs on every response, and the format failure counter by template version is visible in a Logs Insights query.
    • One request appears in X-Ray as a trace with a span for each stage, and each span carries the prompt version.
    • The written drill report identifies all five injected faults with evidence taken from the toolkit.

    Cost, Region, and account notes

    Watch out

    Run everything in your project's assigned Region, and confirm there that your chosen model, CountTokens, Prompt Management, and Knowledge Bases are available. Some of these are limited to certain models or Regions, so check the console or documentation first.

    The throttling and quota experiments are the cost and risk trap. Looping against a model to trigger throttling burns tokens and can exhaust your account's quota for other work. Use a small model, a short prompt, and a low request cap, and stop at the first throttle. Do not try to hit a quota on a shared account.

    Logs can leak data. Prompts may contain customer text, so log sizes, hashes, and versions by default, set a short retention on the log group, and encrypt it. X-Ray and CloudWatch Logs bill by volume, so sample traces in anything beyond a lab. If you use a vector store that bills while it exists, such as an OpenSearch Serverless collection, delete it after the retrieval milestone.

    With a small model, short prompts, and a handful of test runs per milestone, the whole build should cost a few dollars, and most of it will come from the vector store if you leave it running. Check current prices before you start.
